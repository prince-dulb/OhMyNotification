# 救救我的通知！开发计划书

## 0. 一句话定义

> 为个人可靠保存可回开的 Android 通知，并承载后续后台工具模块。

状态：`[已确认]` 项目启动与 `plan-v1.0` 详细计划；用户于 2026-08-22 通过 G0，项目进入 Phase 0。

## 1. 核心愿景

### 为什么做

`[已确认]` 用户经常误划掉 B 站通知，而目标手机的现有通知历史只能保留有限数量，导致 UP 主视频、动态和直播推送被遗漏。

已经真机试用的三款工具都不满足完整需求：

| 方案 | 真机观察 | 结论 |
|---|---|---|
| NotificationLog | 能记录可跳转通知，但存在漏记、排序混乱和大量重复记录 | 核心跳转机制可作为参考，产品不可直接依赖 |
| Notification Vault | 能记录通知，但历史记录不能跳回原内容 | `[排除]` |
| FilterBox | 历史记录不能跳回原内容 | `[排除]` |

因此，问题不是单纯“保存通知文字”，而是把通知变成一个可靠、可处理、可回到原内容的个人收件箱。

### 成功的样子

`[已确认]` 第一阶段成功意味着：

1. 默认检测所有应用的通知；用户可把不想监控的应用加入排除列表。
2. 未排除应用的通知到达后被可靠归档，用户划掉系统通知也不会丢失。
3. 用户可只查看一个或多个指定应用的记录，不改变后台监控范围。
4. 应用外常驻一条低打扰状态通知，展示监听状态和最近记录摘要。
5. 应用内通知沿纵向时间轴排列；相近时间内同一应用的通知可折叠成小抽屉。
6. 时间轴用蓝色实线表示已确认运行，用黄色虚线表示未确认运行，并提供文字或无障碍说明。
7. 同一通知的系统更新不会制造一串重复收件箱条目。
8. 最新通知始终按稳定、可解释的顺序显示。
9. 点击归档通知能够进入原来的视频、动态或直播目标；不能跳转时明确说明原因，不伪装成功。
10. 用户能看见通知监听、通知权限和状态通知渠道是否正常，并能发现监听中断或权限异常。
11. 通知数据默认仅保存在本机。
12. 在没有通知且用户未打开应用时，后台工作保持事件驱动，CPU、唤醒和写盘尽可能接近零；任何常驻成本都有真机数据和必要性依据。

`[已确认]` 性能占用是产品硬约束，但不能以漏记、损坏数据或失去原内容跳转为代价。在满足核心正确性的方案之间，始终选择红魔 11 Pro+ 真机实测资源占用更低的一种。

`[候选]` 长期成功意味着：通知收件箱成为个人 Android 后台工具宿主的第一个模块，后续需求能共享权限中心、模块管理、诊断、存储和设置框架，而不把所有任务硬塞进一个常驻线程。

### 不做的事

- `[已确认]` v0 不做通知拦截、自动回复、自动点击或营销规则引擎。
- `[已确认]` v0 不依赖 B 站账号登录、私有 API 或服务端抓取来替代系统通知监听。
- `[已确认]` 默认不上传通知正文、跳转目标或使用行为。
- `[已确认]` 不提供已读/未读状态；本项目兜住被划掉的通知，不要求用户处理一套新的未读队列。
- `[已确认]` v0 不引入额外数据库加密或应用锁，依赖 Android 应用沙箱与设备加密；锁屏通知默认脱敏。
- `[已确认]` v0 不同时实现其他后台工具模块，只为它们保留清楚的扩展边界。
- `[排除]` 不把“永不退出的 Android 通用后台进程”作为可实现承诺。
- `[排除]` 不以美化系统通知栏为目标。

## 2. 用户与场景

### 核心用户

`[已确认]` 当前核心用户是项目所有者本人。先解决一台真实 Android 手机上的个人问题，不为假想的大众市场提前增加账号、云同步、遥测、付费或多租户能力。

`[已确认]` 项目使用 GitHub 管理版本并全部开源。v0 仍以个人侧载和红魔 11 Pro+ 真机使用为目标；建立公开仓库、推送代码和发布 APK 时分别执行公开发布检查，不把真实通知样本或签名材料带入仓库。

### 首要验收设备

`[已确认]` 首要真机基线：

| 项目 | 信息 | 对项目的影响 |
|---|---|---|
| 机型 | 红魔 11 Pro+ | 后台存活、开机恢复和通知权限均以该机实测为首要证据 |
| 内存 | 16 GB | 足以承载本地索引，但不得以此替代分页、惰性加载和资源约束 |
| 存储 | 1 TB | v0 可先不自动清理，但仍需统计占用并避免无界日志膨胀 |
| 系统 | Android 16 | 按当前 Android 官方行为和权限模型设计并真机验证 |
| 应用兼容 | 不支持 32 位应用 | 不得依赖仅有 32 位原生库的组件；实际 ABI 在 Phase 0 用设备信息确认 |

### 场景故事

一条 B 站 UP 主推送到达。系统通知可能被手误划掉，也可能很快被后续通知挤出系统历史。通知记录器在通知到达时保存它，并把后续系统更新合并到同一个收件箱条目。应用的常驻状态通知更新为“已记录：哔哩哔哩”，让用户在应用外看见最近活动。用户稍后打开应用，看到沿时间轴稳定排列且没有重复刷屏的通知；同一应用在相近时间内的多条记录收进一个小抽屉，展开后仍保持各自的时间。点击其中一条，进入当初对应的视频、动态或直播页面。

默认情况下，通知记录器检测所有应用的通知。用户可以在设置中排除不想监控的应用；排除影响未来采集。收件箱顶部的应用筛选只改变当前视图，允许同时查看一个或多个应用，不改变后台监控配置。

如果监听权限断开、状态通知被关闭，或系统在某段时间内没有把事件交给应用，应用必须显示可理解的健康状态和时间范围。左侧时间轴在有正面运行证据的区间显示蓝色实线，在没有足够证据的区间显示黄色虚线。黄色代表“未确认运行”，不是对停机时刻的精确断言；应用不能在没有证据时声称“绝不漏记”。

## 3. 竞品与差异化

### 已有方案

| 方案 | 做得好 | 做得差 |
|---|---|---|
| 手机系统通知历史 | 无需额外安装 | 当前目标手机保留量不足，不能承担长期收件箱 |
| NotificationLog | 轻量，并已真机证明部分归档通知可跳转 | 漏记、重复、排序和界面均不满足日用 |
| Notification Vault | 能保存通知记录 | 无法从历史记录回到原内容 |
| FilterBox | 通知管理能力丰富 | 对本项目最关键的历史跳转不成立，整体也偏重 |

### 本质区别

本项目的区别不是“界面更漂亮”，而是同时建立六项结构性能力：

1. **动作保真**：把“是否还能回到原内容”作为一等数据和验收结果，而非附带功能。
2. **条目与事件分离**：底层保留通知生命周期事件用于诊断，收件箱只展示合并后的可读条目。
3. **可靠性可观察**：记录监听连接状态、最后事件时间和异常，不用沉默的后台黑盒掩盖漏记。
4. **运行覆盖可视化**：应用外用常驻状态通知呈现当前状态，应用内用时间轴呈现历史运行证据。
5. **可扩展边界**：通知功能不绑死未来后台需求，但也不提前实现尚未提出的模块。
6. **低闲置成本**：真实通知驱动采集和写入，不以轮询、频繁心跳或无限事件日志换取表面可靠性。

## 4. 功能拆解

优先级含义：`[A]` 首个可用版本必须有；`[B]` 应该有；`[C]` 后续再考虑。

| 优先级 | 功能 | 输入 → 输出 | 主要边界与依赖 |
|---|---|---|---|
| `[A]` | 首次授权与全量监听 | 通知使用权 → 开始接收所有可见通知 | 权限被撤销时必须可见；自动排除本应用状态通知 |
| `[A]` | 应用排除列表 | 用户选择不监控的应用 → 后续通知不持久化 | 与查看筛选分离；已有记录保留，删除必须单独明确操作 |
| `[A]` | 通知事件采集 | Android 通知回调 → 本地原始事件 | 需处理连接、断连、更新、移除和进程重建 |
| `[A]` | 条目归一化 | 原始事件 → 可展示的通知条目 | 不假设所有应用都提供相同字段 |
| `[A]` | 更新合并与去重 | 同一通知的多次回调 → 一个收件箱条目 | 不能只靠标题或正文去重 |
| `[A]` | 稳定排序 | 发布时间与接收时间 → 确定的倒序列表 | 按首次收到时间倒序；更新不把旧条目重新顶上来；同时间使用稳定次级键 |
| `[A]` | 时间窗应用抽屉 | 短时间跨度内同一应用的条目 → 可展开折叠组 | 初始窗口 15 分钟、最多跨越 3 条其他应用通知；超出阈值恢复严格时间序 |
| `[A]` | 本地持久化 | 条目与事件 → 重启应用后仍存在 | 通知内容属于敏感数据 |
| `[A]` | 原内容跳转 | 用户点击条目 → 执行有效通知动作或持久目标 | 不设置人为 TTL；动作取消、一次性、应用 stopped、进程重建和重启后的行为需验证 |
| `[A]` | 常驻状态通知 | 监听状态与最近记录 → 通知栏低打扰状态卡 | Android 13+ 需要通知权限；实现是否使用前台服务待验证 |
| `[A]` | 健康状态时间轴 | 连接、真实通知回调与进程事实 → 蓝色已确认区间、黄色未确认区间 | 不能精确观测自身被杀瞬间；颜色外必须有语义说明 |
| `[A]` | 多应用查看筛选 | 一个或多个应用 → 当前列表子集 | 只影响视图，不改变监控和持久化 |
| `[A]` | B 站端到端真机验收 | 真实推送 → 归档、划除、查看、跳转 | 投稿、动态和开播三类必须验证精确跳转；其他类型先保证通用归档 |
| `[A]` | 性能基线与回归门槛 | release 构建、真机工作负载 → CPU、内存、唤醒、写盘、耗电报告 | 无通知长待机、突发通知和万级历史均须覆盖 |
| `[B]` | 关键词与时间筛选 | 关键词、时间 → 结果列表 | 不影响核心采集链路 |
| `[B]` | 保留与清理策略 | 保存期限或容量 → 可预测清理 | v0 不自动删除通知条目；只显示占用并限制诊断事件，不得静默删除 |
| `[B]` | 诊断导出 | 用户主动操作 → 去隐私化诊断文件 | 默认不得包含通知正文或可执行目标 |
| `[C]` | 本地备份与恢复 | 用户选择的文件 → 可迁移归档 | 动作句柄未必能跨设备恢复 |
| `[C]` | 后续后台模块 | 新需求 → 独立模块 | 每个模块单独选择 Android 调度机制 |

## 5. 界面与交互规范

### 设计基线

`[已确认]` 界面遵循 Android 官方 Material 3 体系，优先使用标准组件、状态和交互语义。现代化在本项目中具体意味着：edge-to-edge、正确处理系统 inset、适配深浅色与字体缩放、支持预测返回与不同窗口尺寸、触控范围不小于 48dp，并为自定义时间轴与抽屉补齐无障碍语义。

界面不追求与功能无关的装饰。它的视觉特征来自“通知飞行记录器”这一真实用途：左侧运行覆盖轨道是整个收件箱的识别元素，其余控件保持 Material 3 的克制和一致性。

`[候选]` 初始视觉令牌：

| 角色 | 浅色模式 | 深色模式 | 用途 |
|---|---|---|---|
| 已确认运行蓝 | `#315DA8` | `#A8C7FA` | 时间轴蓝色实线、已连接状态 |
| 未确认运行黄 | `#8A5A00` | `#FFB95C` | 时间轴黄色虚线、未知区间 |
| 表面与文字 | Material 3 主题角色 | Material 3 主题角色 | 页面、卡片、文本和分隔 |
| 错误状态 | Material 3 `error` 角色 | Material 3 `error` 角色 | 权限撤销、明确故障 |

蓝色和黄色是固定的状态语义，但具体色值可在视觉与对比度测试后调整。系统动态配色只影响普通主题角色，不得把两种健康状态变成无法区分的近似颜色。

字体使用 Material 3 系统字阶。时间戳使用等宽数字特性，正文优先保证扫描速度，不引入额外字体依赖。

### 收件箱时间轴

手机紧凑窗口的主界面结构：

```text
┌ 通知记录器                         [筛选]
│ 全部应用 · 监听正常
│
│ 10:42  ┃  ┌ 哔哩哔哩  3 条  10:31–10:42  [展开]
│        蓝  └ 最新：你关注的 UP 主发布了视频
│ 10:18  ┃  ┌ 短信
│        蓝  └ ……
│ 10:05  ┊  未确认运行
│        黄
│ 09:47  ┃  ┌ 系统界面
│        蓝  └ ……
└────────────────────────────────────
```

- `[已确认]` 通知按时间纵向排列，最新在上。
- `[已确认]` 时间轴同时承载运行覆盖状态：蓝色实线为已确认运行，黄色虚线为未确认运行。
- `[已确认]` 同一应用在一定时间内的多条通知折叠成小抽屉；抽屉头显示应用图标、名称、数量、时间范围和最新一条摘要。
- `[已确认]` 采用混合排序：同一应用的两条通知时间跨度较小时，可以跨越少量其他应用记录折叠进同一抽屉；跨度超过阈值时不再聚合，所有通知恢复严格按时间排列。
- `[已确认]` 被压缩的抽屉必须显示起止时间，并在展开后按真实时间排列内部通知；这样局部聚合不会抹掉原始时间事实。
- `[已确认]` 首版默认以 15 分钟为分组窗口，最多跨越 3 条其他应用记录；该值作为可测试的初始参数，若真机样本证明体验不合理，再通过计划变更调整。
- `[已确认]` 展开抽屉后，每条通知保留自己的时间、正文、跳转状态和点击目标。
- `[候选]` 抽屉展开使用一次短暂的尺寸变化动画；关闭动画后仍可完整操作。

在较大窗口中，采用列表—详情自适应布局：时间轴保留在列表侧，选中通知的完整内容和诊断信息显示在详情侧。

### 应用外常驻状态通知

`[已确认]` 通知栏常驻一条低打扰状态通知，目标体验类似用户提到的 FlClash 运行状态卡：

- 标题示例：`正在抢救通知`。
- 内容示例：`已救回 126 条 · 最近：哔哩哔哩（2 分钟前）`。
- 状态异常时改为明确行动文案，例如：`救援中断，点此检查`。
- 点击通知进入应用内收件箱。
- 默认静音、无震动、无悬浮提醒，使用独立的“运行状态”通知渠道。
- 锁屏只显示应用状态和来源应用，不显示原通知标题、正文或动作。
- 解锁状态默认显示最近来源应用和通知标题，但不显示完整正文。
- 文案使用“记录到”而不是“拦截到”，因为应用不会阻止原通知送达。
- 状态通知不运行独立刷新计时器；只在监听状态改变、收到真实通知或摘要确需变化时更新。通知突发时合并短时间内的多次刷新。

`[待验证]` 常驻通知是否由独立前台服务承载。若使用前台服务，必须声明与真实用途匹配的 foreground service type；Android 14 及以上不允许省略类型，`specialUse` 还需要在清单中说明用途，并在进入 Google Play 时接受审核。若不用前台服务，普通常驻通知本身不足以严格证明进程仍在运行。

Android 13 及以上若用户拒绝 `POST_NOTIFICATIONS`，前台服务通知不会出现在通知抽屉，因此首次引导必须把“通知使用权”和“显示运行状态通知”作为两项独立权限状态展示。

### 监控范围与查看筛选

- `[已确认]` 默认监控系统交付给本应用的全部通知。
- `[已确认]` 用户可在设置的“排除应用”页面选择不监控哪些应用；本应用自身始终自动排除。
- `[已确认]` 收件箱筛选支持同时选择一个或多个应用；清除筛选后恢复查看全部已保存记录。
- `[已确认]` 查看筛选只改变当前界面，不改变后台采集。
- `[候选]` 顶部用 Material 3 筛选控件显示当前范围；应用较多时打开可搜索的多选底部面板，不横向堆满应用标签。
- `[已确认]` 应用被加入排除列表后，既有历史保持不变；若用户希望删除，必须通过单独且明确的删除操作完成。

### 无障碍与状态表达

- 健康状态同时使用颜色、实线/虚线、文本和可访问描述，不能只靠蓝黄颜色。
- 时间轴不追求以高频心跳换取分钟级精度；没有正面运行证据的区间宁可诚实显示黄色，也不为补蓝条唤醒设备。
- 抽屉头、筛选入口和通知条目均满足至少 48dp 触控范围。
- 折叠组件向无障碍服务报告应用名、条数、时间范围及展开状态。
- 通知跳转失效时显示明确的失效状态和可用降级动作，不只改变颜色。

## 6. 技术决策

### 技术栈

- `[已确认]` 原生 Kotlin：通知监听、`PendingIntent`、权限和生命周期均为 Android 原生能力，跨平台框架不会减少核心风险。
- `[已确认]` Jetpack Compose：Android 官方的现代声明式界面方案，适合实现 Material 3、edge-to-edge、自适应布局和自定义时间轴，避免同时维护 XML 视图体系。
- `[已确认]` Material 3 是控件、主题、状态和无障碍行为的设计基线；自定义时间轴和应用抽屉建立在标准组件与语义之上。
- `[已确认]` Room：持久化通知条目、事件、监控策略和健康证据；最终 schema 在 Phase 0 样本分析后确定。
- `[已确认]` v0 保持纯 Kotlin/Java/AndroidX 实现，不引入 NDK 或第三方原生库，从源头避免 32 位 ABI 兼容问题。若后续确需原生依赖，必须先验证目标设备支持的 ABI。
- `[已确认]` v0 最低支持 Android 16，采用个人侧载；不为旧系统增加兼容分支，是否进入 Google Play 留待以后重新决策。
- `[已确认]` `NotificationListenerService` 负责通知事件入口。
- `[候选]` `WorkManager` 只用于可延迟的维护任务，例如保留期清理；不用于冒充实时监听。
- `[待验证]` 常驻状态通知是否需要独立前台服务。若使用，当前用途没有明显对应的标准类型，必须核实 `specialUse` 的平台与分发约束，不能错报为 `dataSync` 等无关类型。

### 性能策略与测量

`[已确认]` 性能优化顺序不是事后清理，而是先从架构上消除无意义工作：

1. 通知采集完全由 `NotificationListenerService` 回调驱动，不轮询通知栏。
2. 不持有唤醒锁，不使用精确闹钟，不为了健康时间轴运行高频心跳。
3. 先比较“仅通知监听服务”和“通知监听 + 前台服务”，选择满足可靠性与状态通知要求的较低开销方案；前台服务内部不得空转。
4. 状态通知更新按真实事件触发，并对突发通知做短时合并。
5. 长期保存压缩后的 `NotificationItem`；原始事件只保留最小诊断字段并设置上限，不重复保存正文、图标和动作。
6. 列表采用惰性加载或分页、稳定键和增量分组；筛选、排序和抽屉计算不得每次扫描全部历史。
7. 默认不保存通知大图；应用图标按包名获取并使用有界缓存。
8. 默认无网络请求、无遥测和无远程心跳。

首轮实现前先建立测量方法，Phase 0 后再锁定绝对数值预算，避免编造脱离设备的指标。结构性验收如下：

| 场景 | 记录指标 | 通过原则 |
|---|---|---|
| 8 小时息屏、无通知 | 进程存活、CPU 时间、唤醒、写盘、耗电 | 稳定后不应由应用主动产生周期性唤醒或数据库写入 |
| 100 条突发通知及更新 | 漏记、逻辑条目数、数据库事务、状态通知刷新数 | 不漏记；写入随真实逻辑变化增长，状态卡刷新明显少于原始回调数 |
| 10,000 条历史记录 | 后台内存、首屏加载、滚动与分组耗时 | 不全量载入内存；数据规模增加时后台内存不按总记录数线性增长 |
| 长待机与重启 | 监听恢复时间、健康证据、额外唤醒 | 不以主动高频唤醒换取蓝色时间轴 |
| 监听服务与前台服务 A/B | 漏记、后台 PSS、CPU、耗电 | 两者都满足正确性时选择占用较低者 |

`[已确认]` 一旦建立可重复基线，同场景无说明的 CPU、唤醒、写盘或后台内存回退超过 10% 即视为性能回归；绝对门槛在首轮真机数据后写入详细开发计划。

### 数据模型

以下是待 Phase 0 验证的概念模型，不是已定数据库 schema。

#### NotificationEvent

保存有界、最小化的系统回调事实，用于诊断漏记和验证合并算法。它不是永久保存的第二份通知正文：

- 内部事件 ID
- 来源应用包名和 Android 用户
- 系统通知身份：`key`、`id`、`tag`
- 事件类型：发布、更新、移除、补扫
- `postTime`、本机接收时间
- 内容指纹和动作能力摘要，不重复保存完整正文或动作
- 诊断保留截止时间或容量序号

#### NotificationItem

收件箱展示的逻辑条目：

- 内部条目 ID
- 当前关联的通知身份与生命周期代次
- 首次收到、最近更新、用于展示排序的时间
- 来源应用、标题、正文、图标引用
- 归档、动作可用或失效等状态
- 当前可用的跳转策略及最后验证结果

`NotificationItem` 是长期数据主表。应用图标默认只保存来源包名或共享缓存引用，通知大图不进入 v0 的默认持久化范围。

#### ActionTarget

描述用户点击后采用的动作，不预设所有动作都能永久持久化：

- 原通知点击动作
- 从通知字段中提取的持久 URI 或内容 ID
- 仅打开来源应用的降级动作
- 动作可用性和失效原因

`[已确认]` 本应用不会按记录年龄主动判定动作过期；只要条目未被删除，就保留所有通过受支持方式获得的动作或持久目标。`[待验证]` 原通知的 `PendingIntent` 是系统维护的令牌，创建方进程死亡并不自动使其失效，但创建方可以取消令牌、将其设为一次性，Android 15 及以上还会在创建方进入 stopped 状态时取消其全部 `PendingIntent`。Android 官方同时明确禁止把 `Parcel` 数据当作磁盘持久化格式。因此，“不删除引用”不能被写成“永久有效”的承诺；Phase 0 必须验证可支持的持有方式、资源成本和失效边界，并优先寻找可长期保存的 B 站 URI 或内容 ID。

#### MonitoringPolicy

描述哪些来源应被持久化以及当前视图如何筛选：

- 自动排除的本应用包名
- 用户排除的应用集合
- 当前查看筛选的应用集合
- 规则修改时间和适用范围

监控排除规则与查看筛选必须分开存储，不能因为用户只查看 B 站就停止记录其他应用。

#### HealthEvidence 与 HealthInterval

健康状态先保存可证明的事实，再派生时间段：

- 监听连接、断开和重连事件
- 进程或服务启动、正常停止事件
- 监听生命周期、真实通知回调或进程自然活跃时产生的运行确认及其时间
- 通知使用权、`POST_NOTIFICATIONS` 和状态通知渠道状态
- 派生区间：`CONFIRMED_RUNNING` 或 `UNCONFIRMED`

应用无法在自己被系统突然终止的瞬间写入“已停止”，因此黄色区间边界只能从最后一次正面证据和下一次恢复证据推断。界面必须把这种不确定性保留下来，且不得为提高区间精度而单独高频唤醒设备。

#### TimelineGroup

时间窗应用抽屉是由通知条目动态派生的界面模型，不作为事实来源覆盖原条目：

- 来源应用
- 组内条目 ID 列表
- 最早和最晚时间
- 分组时间阈值与跨越的其他应用条目数量
- 展开状态仅属于界面状态
- 分组策略版本，便于算法调整后重新计算

### 关键架构决策

1. `[候选]` **保留可扩展边界**：通知收件箱先独立完成；是否建立正式的宿主和模块框架，等出现第二个真实后台需求时再决定。
2. `[候选]` **紧凑条目 + 有界诊断事件**：收件箱长期保存合并后的条目；原始事件只保留最小字段和有限周期，兼顾漏记诊断与资源占用。
3. `[待验证]` **双轨跳转**：短期保留原通知动作，同时尽可能提取可持久化的目标；Phase 0 必须证明 B 站实际通知提供了什么。

### 排除的方案

- `[排除]` Flutter 或 Flutter 与原生混合栈：项目仅面向 Android，核心能力仍必须落在原生层；额外运行时、平台桥接和生命周期增加了后台资源与可靠性风险，却没有足够的跨平台收益。
- `[排除]` 以 Notification Vault 或 FilterBox 作为项目基础：真机核心跳转测试失败。
- `[排除]` 原样复刻 NotificationLog：它已经暴露了漏记、重复和排序问题。
- `[候选]` NotificationLog 源码只作为动作保留与跳转行为的参考；引用或复用代码前必须重新核对仓库、许可证和实现质量。
- `[排除]` 只存通知文字后用标题搜索 B 站：可作为最后降级，不能冒充精确跳转。
- `[排除]` 用一个无限循环或单一前台服务承载所有未来后台任务。

## 7. 阶段与完成定义

### Phase 0：验证致命假设

目标不是做完整界面，而是回答项目能否成立：

1. 采集真实 B 站视频、动态、直播等通知的身份、更新序列和可用动作。
2. 验证动作在通知划除后、短期与长期等待后、本应用进程重建后、B 站被强行停止或更新后，以及手机重启后的表现；不预设固定时间 TTL。
3. 判断能否从通知中提取稳定的 B 站 URI、内容 ID 或其他精确备用目标。
4. 用可控通知样本验证基于系统身份的更新合并，不误合并不同内容。
5. 验证目标手机上的监听连接、断开、重连和开机恢复行为。
6. 比较“通知监听服务直接维护状态通知”和“独立前台服务”两种方案，验证常驻通知、通知权限、服务类型和重启恢复边界。
7. 验证可采集哪些自然运行证据、这些证据在待机中的可靠性，以及蓝黄时间区间能达到的时间精度。
8. 用包含多应用交错通知的样本验证混合排序：短跨度 A→B→A 可压缩为 A 抽屉，长跨度 A→B→A 必须恢复严格时间序；展开后原始顺序可核对。
9. 在红魔 11 Pro+ 上记录系统版本、设备报告的 ABI、通知权限和厂商后台策略，验证所有依赖均可在 64 位环境运行。
10. 用 release 构建完成无通知长待机、100 条突发通知、10,000 条历史记录和前台服务 A/B 测量，建立 CPU、后台内存、唤醒、写盘、耗电及数据库增长基线。

完成定义：形成一份带真机证据的技术验证报告；跳转、去重、监听可靠性、常驻状态通知、健康时间轴精度和资源占用都有明确结论，并据此锁定首版性能预算。若无法提供满足实际查看周期的精确跳转、常驻运行方案无法符合 Android 平台规则，或闲置成本明显不合理，则回到产品边界重新决策，不直接进入 MVP。

### Phase 1：通知收件箱 MVP

完成定义：在目标手机上，应用默认记录所有未排除来源；用户能完成“收到 B 站通知 → 在常驻通知看到最近记录 → 划掉原系统通知 → 稍后在时间轴或应用抽屉中找到唯一且排序正确的条目 → 点击进入原内容”的完整路径，并能按一个或多个应用筛选记录、查看蓝黄运行覆盖区间；release 构建同时满足 Phase 0 锁定的资源预算。

### Phase 2：日用可靠性

完成定义：覆盖长待机、重启、权限异常、状态通知渠道关闭和长期数据量；完成字体放大、深浅色、edge-to-edge、无障碍和不同窗口尺寸验证；建立自动或可重复的性能回归流程，形成可持续日用版本。

### Phase 3：宿主扩展

只有出现第二个真实后台需求后才启动。完成定义：第二个模块能复用宿主公共能力，同时使用适合自身任务的 Android 后台机制，且不破坏通知模块可靠性。

## 8. 风险清单

| 风险 | 影响 | 最小验证方式 |
|---|---|---|
| 原通知动作无法长期保存或在重启后失效 | 核心“稍后打开”能力不成立 | 真机测试划除后、进程重建后、延时后和重启后跳转 |
| B 站通知不提供稳定目标 URI/内容 ID | 动作失效后无法精确降级 | 检查多类真实通知字段和目标动作 |
| 目标手机限制通知监听进程 | 产生静默漏记 | 长锁屏、重启、系统回收和权限切换测试，并记录监听生命周期 |
| 通知 `key` 被复用或更新语义复杂 | 错误合并或重复 | 采集完整发布/更新/移除序列，构造生命周期代次测试 |
| 只用内容指纹去重 | 不同 UP 主或不同内容被误合并 | 用相同标题、不同目标的样本反例测试 |
| 时间窗或允许跨越数量设置过大 | 抽屉掩盖重要的中间通知，时间轴失真 | 分别测试短跨度和长跨度 A→B→A；抽屉显示时间范围且展开恢复逐条时间 |
| 依赖只提供 32 位原生库 | 红魔 11 Pro+ 无法安装或运行 | v0 优先无 NDK；构建后检查 APK 原生库并在目标机安装验证 |
| 普通常驻通知残留但进程已经停止 | 用户把通知存在误认为实时存活证据 | 验证前台服务方案；状态卡显示最近确认时间，应用内用健康证据补充 |
| Android 13+ 通知权限被拒绝或渠道被关闭 | 应用外健康状态不可见 | 首次引导与应用内健康页分别检测并给出系统设置入口 |
| Android 14+ 前台服务类型不匹配 | 启动异常或分发审核失败 | Phase 0 核对服务类型；不得用无关类型绕过要求 |
| 心跳在待机中延迟或应用突然被杀 | 黄蓝区间边界不精确 | 记录证据来源和最后确认时间，用“未确认”而非“已停止”表达 |
| 为填满蓝色时间轴而高频心跳 | 增加唤醒和耗电，违背性能硬约束 | 不持有唤醒锁；仅用真实事件和自然活跃证据，接受黄色未知区间 |
| 原始事件、日志或通知图片无限保存 | 数据库、写盘和存储持续膨胀 | 长期只保存紧凑条目；诊断事件设上限；默认不存大图 |
| 每条回调都刷新状态通知 | 突发期间产生大量 Binder 与系统 UI 更新 | 对摘要更新做短时合并，并统计刷新次数 |
| 时间轴或抽屉每次全量重算 | 万级记录时 CPU 和内存突增 | 惰性加载、稳定键、增量分组和基准测试 |
| 盲目追求低占用而延迟持久化 | 进程被杀时漏记或丢失动作 | 先满足正确性测试，再在安全边界内合并事务 |
| 全量监听保存敏感应用通知 | 暴露短信、验证码或金融信息 | 本地存储、排除列表、锁屏脱敏和无正文诊断日志 |
| 宿主概念导致 v0 范围膨胀 | 核心通知功能迟迟不可用 | v0 只实现公共最小骨架和通知模块 |
| 通知数据泄露 | 暴露个人兴趣、消息和跳转凭据 | 本地存储、最小日志、无默认遥测、诊断主动导出 |

- 默认检测所有通知，允许排除不监控的应用。
- 查看范围可同时筛选一个或多个应用，且不改变后台监控范围。
- 通知栏常驻一条低打扰运行状态通知，显示监听状态和最近记录摘要。
- 应用内通知按时间纵向排列，相近时间内同一应用的通知折叠成小抽屉。
- 时间轴左侧用蓝色表示已确认运行区间，用黄色表示未确认运行区间。
- 时间窗内允许同一应用的通知跨越少量其他应用记录压缩为抽屉；跨度较大时恢复严格时间排序。
- 首要验收设备为红魔 11 Pro+，16 GB RAM、1 TB 存储、Android 16，不支持 32 位应用。
- 性能占用是硬约束：不牺牲可靠记录和跳转的前提下，无通知闲置时 CPU、唤醒和写盘应尽可能接近零，并持续做真机性能回归。

## 11. Android 官方基线资料

核对日期：2026-08-22。实施时若目标 SDK、AndroidX 或平台政策变化，需要重新核对。

- [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService)：监听连接、断开、回调与重新绑定边界。

- [Android 14 前台服务类型](https://developer.android.com/about/versions/14/changes/fgs-types-required)：目标 API 34+ 必须声明真实服务类型，`specialUse` 需要说明用途。

- [Compose Material 3](https://developer.android.com/develop/ui/compose/designsystems/material3)：Material 3 组件、主题与无障碍基线。
- [Compose edge-to-edge 与 inset](https://developer.android.com/develop/ui/compose/system/insets)：Android 15+ edge-to-edge 及系统栏避让要求。

- [Storage Access Framework 文档访问](https://developer.android.com/training/data-storage/shared/documents-files)：`ACTION_CREATE_DOCUMENT` 让用户通过系统选择器决定保存位置，不需要广泛系统存储权限。
