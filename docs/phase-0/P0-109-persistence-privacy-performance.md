## 1. 当前结论

生产候选已经具备本地 Room、诊断事实 10,000 条上限、Paging 有界窗口、64 项图标缓存、数据提取全排除、无网络/遥测和普通 ongoing 状态卡，但尚未完成本 Spike 要求的 release 三次有效短场景、两次 8 小时待机、100 回调、10,000 条历史、持续增长和普通/FGS A/B。因此当前任何 Debug 数值都只用于定位问题，不能锁定绝对预算或宣称 P0-109 通过。

## 2. 去敏诊断方法

Debug 统计接收器只输出计数、布尔值和发生变化的字段名。为了定位重复写入，它对最近提交条目的受管字段在进程内保存不可逆值指纹，前后比较时只返回字段名；不返回包名、标题、正文、URI、内容 ID、动作令牌或字段哈希。该诊断入口由 production/test APK 边界扫描证明不进入 release APK。

## 3. 首轮红魔短窗口

构建为脏工作树 Debug，设备为红魔 11 Pro+ / Android 16，以下结果均为诊断而非正式基线：

| 窗口 | 结果 | 解释边界 |
|---|---|---|
| 锁屏点亮但未解锁，19 秒、每 1.9 秒一次去敏统计 | 3 次 Room 通知提交；1 次状态卡发布；变化字段仅 `body`、`bodyOriginalCodePoints`、`contentFingerprint` | 证明剩余写入来自真实可见正文变化，不是 `postTime`、进程会话或动作能力抖动；诊断广播自身污染 CPU，故不报告 CPU |
| 息屏 20 秒、不调用 Debug 广播，但 OMN Activity 仍为 focused/resumed | OMN 进程 PID 稳定；进程 CPU 增量 67 ticks；数据库文件总分配从 740,072 B 到 744,168 B，增长 4,096 B | 这不是后台空闲基线。它只说明“屏幕熄灭”不等于 UI 已退到后台，并与上方动态正文更新诊断相符 |
| 先返回桌面再熄屏，确认 Activity 非 resumed 且进程 `frozen=true` 后计时 20 秒 | OMN 进程 PID 稳定；进程 CPU 增量 0 ticks；数据库文件总分配保持 778,240 B，增长 0 B | 这是目前唯一有效的真正后台短窗口；只支持“该 20 秒 Debug 样本无可见 CPU/写盘活动”，不能外推 8 小时耗电或 release 预算 |

此前修复已让完全相同的活动通知补扫不再改写 Room，并保留第一份有效来源 `postTime`。本轮字段诊断说明剩余热点不是无意义重复，而是一条活动通知持续改变正文；当前逐观察事务会按每次正文变化更新归档。

真正后台采样结束时，系统将 OMN 标记为 frozen、cached、empty，`killed=false`；监听服务 Binder 和常驻状态卡仍存在。同期未发现归属 OMN 的活动 WakeLock、计划 Job 或 Alarm。冻结进程无法直接取得 `dumpsys meminfo`；一次通过去敏 Debug 统计唤醒进程但不恢复 Activity 后的单点为总 PSS 96,276 KiB、`oom_score_adj=250`。该数值来自 Debug 单点，既不是稳态分布，也不能作为 release 内存预算。

## 4. 待决减写方案

进一步减写必须引入明确取舍，不能伪装成无风险优化。根据本轮约 6 秒一次的正文变化，5 秒静默窗无法形成有效合并，候选已调整为：新通知首次提交立即落库；同一活动身份的后续更新使用 10 秒静默窗口并设 60 秒最长间隔；移除、断连和用户点击前立即冲刷最新待提交更新。这样可保住“通知已到达”的首份事实，并把持续进度类正文从逐次写入降为最多每分钟一次；代价是 OMN 进程若在窗口内被杀，归档正文可能落后于来源通知最后状态，且运行时动作只保证到最近一次已提交或移除冲刷点。

该候选尚未启用。纯 JVM 参考模型已经覆盖首次立即提交、约 6 秒连续更新的静默延长、60 秒强制冲刷、移除前冲刷和无待更新时不虚构冲刷；它不进入 APK，也不证明 Android 定时、进程终止或真实 Room 成本。进入生产前必须用相同真实动态通知和受控更新序列 A/B，至少核对事务数、CPU ticks、文件增长、最终正文、移除前冲刷、精确跳转和进程终止窗口，并由用户接受“首份可靠、末次可能在进程突死时稍旧”的语义。
