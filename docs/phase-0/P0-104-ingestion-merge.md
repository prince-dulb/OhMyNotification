# P0-104 / SP-04 摄取队列、事务与归并

状态：`[已验证] LOGIC_GO / ROOM_DEVICE_PARTIAL`

验收时间：2026-08-23（Asia/Shanghai）

## 1. 范围与结论边界

本 Spike 已用纯 Kotlin 参考模型验证：有界单消费者队列、每个回调终态对账、同活动代次更新归并、精确重放、补扫、移除后重发、单调摄取顺序及写入故障原子性。

参考存储通过不可变快照替换模拟事务，只证明领域命令可以做到完整旧状态或完整新状态。它不是 Room schema，也不能替代真实 SQLite 崩溃、进程终止、写盘量、release CPU/PSS 或红魔回调耗时；这些项目保持 `NOT_RUN`。

## 2. 固定数据与候选边界

版本化数据集：`ingestion-events-v1`

```text
seed=2026082304
sha256=ff42a8919ab005e88401c21ced7bba2b7088e44253424ad55c81fa89ca5c24d8
```

100 回调负载由 25 个独立基础身份组成，每个身份依次产生：首次发布、精确重放、内容更新、移除。

当前结论：

- 单写者按实际出队顺序分配 `ingestSequence`，不按可跳变的壁钟重排；
- 默认正确性基线保持每观察一个事务，不提前启用批量等待窗；
- 容量 128 是“容纳 100 条完全不消费的最坏突发”的候选下限，不是已锁定生产数值；
- 队列满时必须为每个未接纳观察产生显式 `INGESTION_BACKPRESSURE` 终态，不允许静默丢弃；
- `RotateLifecycle` 暂不启用；活动基础身份出现 ID/tag 佐证冲突时保存去内容失败事实并拒绝覆盖，等待 SP-01 真实 key 复用证据；
- 内容变化增加 `contentRevision`，仅持久目标变化更新条目但不增加内容修订；
- 运行时 `PendingIntent` 不进入本参考持久模型。

## 4. 生命周期与反例

已验证：

- 同一活动代次的正文变化只更新原条目，`itemId`、`firstReceivedAt` 和创建序列不变；
- 完全相同发布重放和匹配的 `RECOVERY_SNAPSHOT` 各写一条最小事件，不新增条目、不增加修订；
- 相同文本但不同 `systemKey` 或 Android 用户形成独立条目；
- 移除保留归档，随后相同基础身份重发创建 `generation=1`，不覆盖 `generation=0`；
- 孤立移除不创建空通知；身份佐证冲突不覆盖活动条目；
- 观察壁钟按 `5000, 1000, 9000, -1` 跳变时，事件摄取序列仍严格为 `1..4`。

## 5. 原子性故障矩阵

分别在以下位置注入失败：

1. 分配摄取序列后；
2. 写条目后；
3. 写事件后；
4. 写健康事实后。

四种结果均为：提交失败，条目、事件、健康事实和所有序列计数完整回到事务前快照。只有完整提交后才产生用户可见的 `Committed` 结果。

## 6. 决策与待验证项

`SP-04 LOGIC_GO`：采用“回调快速复制 → 有界队列 → 单消费者 → 正确性优先的单观察原子事务”作为进入 Room 候选的逻辑形态。

红魔私有事件流补充了一个真实重复输入反例：30 个 B 站系统 key 在三次监听连接中各产生三条 `RECOVERY_SNAPSHOT`，合计 90 条回调但只有 30 个逻辑身份。该结果直接否定“每次补扫都新增条目”，并与参考模型的精确重放/补扫幂等规则一致；由于尚未观察这些 key 的移除后复用，它不锁定生命周期代次判定的全部物理字段。

以下内容仍阻止锁定生产实现：

- SP-01 的真实身份、key/ID/tag 复用和 B 站字段矩阵；
- 可控通知通过真实 debug 监听器形成 100 回调的红魔时间线；
- Room 事务在进程终止、存储不足和陈旧决策下的真实回滚；
- 容量 128 的字段体积、峰值 PSS、回调耗时和背压策略；
- 单观察事务与小批量候选的写盘、耗时和进程终止损失窗对照；
- 诊断事件上限与持久化失败事实的独立可靠存放方式。

在上述证据形成前，不创建生产 Room schema，不把 128、批量 1 或当前身份冲突策略写成最终物理约束。

## 7. 生产 Room 与排除策略的真机接入

经 G3 批准 schema v1 后，`excluded_sources` 成为监控排除集合的唯一持久真相。应用 `onCreate()` 在返回前先于 IO 线程读取该表并发布不可变热路径快照，之后系统才可能创建监听服务；用户修改时先完成 Room 写入，再更新进程内快照。旧版 `omn-monitoring-policy` 私有偏好不再参与读取，但未执行删除。

红魔目标机上的 Debug-only 合成来源验证依次执行：读取原状态 → 切为排除 → 核对 Room/快照计数 → 强停并重建进程 → 再次核对 → 恢复原状态 → 再次重建核对。六个阶段中 Room 与热路径计数始终一致，测试来源在重建后保持排除，恢复后保持未排除；最终没有留下测试策略，也没有发布、删除或改写通知条目。

这项结果证明当前正常写入与进程重建路径，没有覆盖存储失败注入、写满、进程恰好终止于 Room 提交和快照发布之间、工作资料粒度或 UI 错误提示。因此状态只从 `ROOM_DEVICE_NOT_RUN` 提升为 `ROOM_DEVICE_PARTIAL`。
