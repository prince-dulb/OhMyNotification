# 救救我的通知！任务拆分

状态：`[已确认] plan-v1.0；G0 已通过`

## 1. 执行规则

本任务表从“详细计划获用户确认”开始，不把当前规划阶段误算为已进入开发。

### 1.1 状态

| 状态 | 含义 |
|---|---|
| `PENDING` | 前置未齐或尚未开始。 |
| `READY` | 前置与授权齐全，可以开始。 |
| `IN_PROGRESS` | 正在执行；同一执行者原则上只保留一个主任务。 |
| `BLOCKED` | 有明确外部阻断，记录证据和下一动作。 |
| `DONE` | 交付物、测试、文档和证据全部满足。 |

### 1.2 工作量

| 尺寸 | 预期范围 |
|---|---|
| XS | 单一机械任务，通常不超过半个工作日。 |
| S | 一个边界清晰的小能力，通常 0.5—1 个工作日。 |
| M | 一项完整能力或 Spike，通常 1—3 个工作日。 |
| L | 跨多个 Android 生命周期/真机场景，通常 3—5 个工作日。 |
| XL | 必须继续拆分；不能直接进入执行。 |

工作量是相对规划值，不是交付日期承诺。等待真实 B 站推送、8 小时待机、设备重启和用户决策不计入编码工时。

### 1.3 每个任务的统一完成定义

- 只实现该任务引用规格的范围，没有顺手扩张。
- 领域错误、空态、权限拒绝和生命周期边界已覆盖。
- 运行了与风险相称的自动化/真机验证，并记录实际命令、构建和结果。
- 没有把真实通知、密钥、路径或签名材料写入仓库和日志。
- 相关 README、规格状态、路线图和变更记录同步。
- `git diff --check`、相应测试、lint/release 构建通过；若命令尚未建立，任务不能标 `DONE`。
- 失败或未观察项原样保留，不用注释、跳过标记或降低断言伪装完成。

未来“个人常驻后台宿主”只有在出现第二个真实需求后另行立项。v0 的任务不预埋通用守护进程、插件系统、共享轮询器或多模块数据库。

## 12. 任务表维护规则

1. 开始任务前把状态、实际分支和依赖检查写入工作记录。
2. 发现规格无法实现时先将任务标 `BLOCKED` 或输出 Spike `REDIRECT`，先改文档再改实践。
3. 任务尺寸膨胀到 XL 时必须拆分并更新本表。
4. 任何性能数字只有 A14 有效 run 与用户确认后才能从“待锁定”改为绝对预算。
5. 任何数据库 schema 变更/迁移、CI、push、发布、全局安装或秘密配置都不能靠任务状态绕过审批门。
6. 每个版本完成后更新 README 索引、路线图状态、变更记录和已知限制；未通过真机门不能用“代码完成”替代版本完成。
