# A06 稳定排序

状态：`[候选] plan-v1.0`

## 1. 规格元数据

| 项目 | 值 |
|---|---|
| 功能 ID | `A06` |
| 优先级 | `[A]` |
| 主交付版本 | `v0.2` |
| 前置功能 | `A03 通知事件采集`、`A05 更新合并与去重`、`A08 本地持久化` |
| 被依赖功能 | `A07 时间窗应用抽屉`、`A12 多应用查看筛选`、`A13 B 站端到端真机验收`、`B01 关键词与时间筛选` |
| 相关 Spike | `SP-04（架构 S3）摄取队列、事务与归并`、`SP-08（架构 S7）排序、抽屉、筛选与分页` |

## 2. 目标与非目标

### 2.1 目标

- 为任意可见通知条目建立跨重复查询、分页、更新、进程重建和时区变化都一致的严格全序。
- 最新首次收到的条目在前；通知更新不把旧条目重新顶到顶部。
- 相同首次收到时间使用持久且不可变的次级键消除数据库返回顺序不确定性。
- 排序在查询层执行，支持分页，不全量读取后在内存重排。

### 2.2 非目标

- 不按来源应用声明的 `originalPostTime` 排序。
- 不按 `lastUpdatedAt`、标题、正文、应用名称或动作状态排序。
- 不实现时间窗抽屉；A07 只消费本规格输出的基础全序。
- 不承诺设备壁钟被手工回拨后，后来收到的条目一定显示在更早收到的条目前；本规格保证使用已存事实得到确定结果，并保留时钟异常诊断。

## 3. 术语与不变量

| 术语 | 精确定义 |
|---|---|
| 基础全序 | 对当前查询命中的每个 `NotificationItem` 按三个不可变键进行的唯一顺序。 |
| `firstReceivedAt` | OMN 首次观察并创建逻辑条目的 UTC 时刻；创建后不可修改。 |
| `ingestSequence` | OMN 在创建该条目时分配的同一安装内单调递增 `StableSequence`；创建后不可修改。 |
| `itemId` | 不变且唯一的 `ItemId`；其规范表示必须在 Room 查询和 Kotlin 比较器中形成相同的确定全序。 |
| `ItemId` 规范顺序 | 比较非空 `canonicalBytes` 的无符号逐字节字典序；公共前缀相同时较短序列更小。`DESC` 取该顺序的逆序。 |
| 排序代 | 一次 Paging 查询生成；数据或筛选变化使旧代失效，新代从首屏重新建立一致顺序。 |

基础排序键固定为：

```text
firstReceivedAt DESC
ingestSequence  DESC
itemId          DESC
```

全局不变量：

1. `firstReceivedAt`、创建时 `ingestSequence`、`itemId` 在条目生命周期内不可变。
2. `lastUpdatedAt`、`contentRevision`、`lifecycleState` 或 `actionState` 的变化不得改变排序键。
3. `originalPostTime` 只用于展示或诊断，不参与任何排序级别。
4. 同一查询条件和同一条目集合必须得到相同顺序，不依赖 Room 未声明顺序、Map/Set 迭代顺序或当前 locale。
5. 分页大小、页边界和进程重建不得改变相对顺序。

## 4. 输入与输出契约

本规格定义逻辑查询契约，不锁定 Room 主键、索引或 Paging 实现细节。

### 4.1 `NotificationItemSortKey`

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `firstReceivedAt` | `InstantUtc` | 是 | 条目创建时写入，更新禁止修改。 |
| `ingestSequence` | `StableSequence` | 是 | 条目创建事务分配，同一安装内单调递增。 |
| `itemId` | `ItemId` | 是 | 全局唯一、不可变、可用规范比较器全序比较。 |

`ItemId.canonicalBytes` 是逻辑标识的稳定规范表示；同一 `itemId` 在进程重建后必须逐字节相同。该契约不锁定 ID 生成算法或 Room 物理列，但 Room 比较与 Kotlin 参考比较器必须实现上述同一无符号字典序。

### 4.2 `NotificationItemSummary`

排序层至少接收以下字段；其他展示字段不影响比较结果。

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `itemId` | `ItemId` | 是 | 同时是稳定 UI 键。 |
| `sourcePackage` | `PackageName` | 是 | 仅供展示与筛选。 |
| `sourceUser` | `AndroidUserRef` | 是 | 与包名构成来源键。 |
| `sourceLabelSnapshot` | `String?` | 否 | 仅供展示与 B01 搜索；不参与排序。 |
| `firstReceivedAt` | `InstantUtc` | 是 | 主排序键。 |
| `ingestSequence` | `StableSequence` | 是 | 次排序键。 |
| `title` | `String?` | 否 | 不参与排序。 |
| `body` | `String?` | 否 | 不参与排序。 |
| `lastUpdatedAt` | `InstantUtc` | 是 | 不参与排序。 |
| `actionState` | `ActionStateSummary` | 是 | 不参与排序。 |

### 4.3 `SortCursor`

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `lastFirstReceivedAt` | `InstantUtc` | 是 | 上一页最后一条的主键值。 |
| `lastIngestSequence` | `StableSequence` | 是 | 上一页最后一条的次键值。 |
| `lastItemId` | `ItemId` | 是 | 上一页最后一条的最终键值。 |
| `generationId` | `PagingGenerationId` | 是 | 只能用于创建它的查询条件和排序代。 |

### 4.4 `OrderedPageRequest`

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `queryCriteria` | `InboxQueryCriteria` | 是 | 先筛选再排序；不得修改采集策略。 |
| `loadSize` | `PositiveInt` | 是 | 大于 0；上限由查询实现和性能规格锁定。 |
| `after` | `SortCursor?` | 否 | 空表示首屏；非空必须属于当前排序代。 |

### 4.5 `OrderedPage`

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `items` | `List<NotificationItemSummary>` | 是 | 已按基础全序排列；不含重复 `itemId`。 |
| `nextCursor` | `SortCursor?` | 否 | 有更旧数据时指向本页最后一条；末页为空。 |
| `generationId` | `PagingGenerationId` | 是 | 与请求排序代一致。 |
| `endReached` | `Boolean` | 是 | `true` 时 `nextCursor` 必须为空。 |

## 5. 比较规则、查询与状态

### 5.1 确定比较器

对条目 A 与 B，A 排在 B 前，当且仅当第一条满足的条件为真：

1. `A.firstReceivedAt > B.firstReceivedAt`；
2. 两者 `firstReceivedAt` 相等，且 `A.ingestSequence > B.ingestSequence`；
3. 前两键都相等，且 `A.itemId > B.itemId`（使用 `ItemId` 规范比较器）。

三个键全部相等只允许发生在 A 与 B 是同一条目时。不同条目出现相同 `itemId` 是数据完整性错误，不得依赖输入顺序打破平局。

### 5.2 分页规则

- 查询顺序必须等价于 `ORDER BY firstReceivedAt DESC, ingestSequence DESC, itemId DESC`。
- 下一页只返回排序键严格小于 `SortCursor` 三元组的条目；游标本身不重复返回。
- 任一条目插入、删除，或查询条件变化时，当前 Paging 代失效；UI 不得把新代数据接到旧游标后。
- 普通通知更新只修改非排序字段时，可以刷新对应行但不得改变其位置。
- 同一完整数据集使用不同 `loadSize` 拼接后，结果必须与一次性逻辑全序完全相同。

### 5.3 UI 状态

| 状态 | 必填数据 | 行为 |
|---|---|---|
| `INITIAL_LOADING` | `queryCriteria` | 显示加载状态，不显示旧条件的残留结果。 |
| `CONTENT` | `generationId`、已加载页 | 使用 `itemId` 稳定键增量渲染。 |
| `EMPTY` | `generationId` | 显示当前条件无结果；不解释为没有采集。 |
| `APPEND_LOADING` | 当前内容、游标 | 保持现有顺序，页尾显示加载状态。 |
| `QUERY_ERROR` | `SortErrorCode` | 保留已成功页并提供明确重试；不得局部乱序补数据。 |

## 6. 用户故事与数据流

### 6.1 用户故事

- 作为用户，我要最新收到的通知始终在前，以便快速找到刚被划掉的内容。
- 作为用户，我不要旧通知因为正文更新而跳到顶部。
- 作为用户，我要在同一时间收到多条通知时仍有固定次序，重开应用后不会换位。
- 作为用户，我要翻页、切换筛选和展开抽屉时不出现重复、漏项或顺序漂移。

### 6.2 数据流

```text
NotificationIngestionCoordinator
  → 创建 NotificationItem 时一次性写入
      firstReceivedAt + ingestSequence + itemId
  → 更新时保持三键不变
  → Room / InboxQuery 先应用查看条件
  → 按三键 DESC 产生 Paging 数据
  → A07 TimelineGrouper 消费基础全序
  → Compose 以 itemId 作为稳定键渲染
```

## 7. Given / When / Then 验收

### AC-A06-01 主排序

- Given 条目 A、B 的 `firstReceivedAt` 分别为 10:01 和 10:00 UTC
- When 查询基础列表
- Then A 必须排在 B 前
- And 两者 `originalPostTime` 的任何值都不改变结果

### AC-A06-02 更新不顶置

- Given A 首次收到于 09:00，B 首次收到于 10:00
- When A 在 11:00 更新正文且 `lastUpdatedAt` 变为 11:00
- Then B 仍排在 A 前
- And A 的 `firstReceivedAt` 与 `ingestSequence` 不变

### AC-A06-03 同时间使用摄取序列

- Given A、B 的 `firstReceivedAt` 完全相同，A 的 `ingestSequence=101`，B 为 100
- When 查询或重建进程后重新查询
- Then A 始终排在 B 前

### AC-A06-04 最终以 itemId 打破平局

- Given A、B 的前两键相同，`A.itemId.canonicalBytes=[0x01,0xFF]`，`B.itemId.canonicalBytes=[0x01,0x7F]`
- When 在 Room 查询和纯 Kotlin 比较器中排序
- Then 两处都得到 A 在 B 前
- And 重复执行结果不变化

### AC-A06-05 分页大小不改序

- Given 100 个包含相同时间键的固定条目
- When 分别用 `loadSize=10`、25、100 读取全部页
- Then 三种拼接结果的 `itemId` 序列完全相同
- And 不重复、不遗漏任何条目

### AC-A06-06 失效排序代不混用

- Given UI 已加载 generation G 的两页
- When 新通知插入并使查询失效
- Then 后续数据来自新 generation G+1
- And 旧 G 的 `SortCursor` 不用于 G+1

### AC-A06-07 时区和格式不影响事实

- Given 已保存固定 UTC 排序键
- When 设备切换时区、12/24 小时制或 locale
- Then 显示文本按新设置格式化
- And 条目 `itemId` 顺序完全不变

### AC-A06-08 进程重建保持顺序

- Given 包含更新、相同时间与不同来源的 10,000 条固定数据
- When 记录顺序、终止进程并重新打开同一查询
- Then 首次加载及逐页拼接顺序与重建前完全相同

### AC-A06-09 查看筛选只缩小集合

- Given 全部列表顺序为 A、B、C、D，筛选命中 B、D
- When 应用查看筛选
- Then 输出为 B、D
- And B 与 D 的相对顺序保持
- And 排序查询不修改 `MonitoringPolicy`

### AC-A06-10 来源时间异常不替代接收时间

- Given A 的 `originalPostTime` 晚于 B，但 A 的 `firstReceivedAt` 早于 B
- When 查询默认列表
- Then B 排在 A 前
- And UI 可在详情显示来源时间，但不能用它重排

## 8. 边界条件与错误状态

| 场景/错误码 | 用户可见状态 | 系统行为 |
|---|---|---|
| `MISSING_SORT_KEY` | 显示列表暂时不可用及重试入口 | 记录不含正文的完整性错误；不得退回 `postTime` 或数据库自然顺序。 |
| `DUPLICATE_ITEM_ID` | 显示数据完整性错误 | 停止受影响查询，不静默去重或随机排序。 |
| `CURSOR_GENERATION_MISMATCH` | 重新加载当前条件首屏 | 丢弃旧游标，不拼接跨代页面。 |
| `QUERY_FAILED` | 保留已成功内容并显示加载失败与“重试”操作 | 只在用户点击后重新发起一次查询；不得自动循环、忙等或全表载入兜底。 |
| 空结果 | 显示“当前查看条件没有记录” | 返回 `EMPTY`，不修改筛选或采集。 |
| 极长标题/正文 | 正常按键排序 | 比较器不读取内容，内容长度不影响顺序。 |
| 壁钟回拨 | 可在诊断中说明时间调整 | 不重写既有键；新条目仍按存储的三键确定排序。 |
| 来源应用卸载 | 历史条目仍可显示 | 包名和排序键保持，不因标签缺失改序。 |

## 9. 隐私与性能要求

- 比较器只读取三个非正文排序键，不读取标题、正文、URI 或动作。
- 排序和分页完全本地执行，不联网、不遥测、不写搜索日志。
- Room 查询必须直接提供基础全序；不得把 10,000 条历史载入 Kotlin 集合后排序。
- 查询索引和物理游标方案由 `SP-08` 基准锁定，但无论实现如何都必须满足本规格的全序与分页结果。
- 10,000 条场景记录查询范围、已加载条目数、PSS、首屏、翻页和快速滚动耗时；绝对预算由 Phase 0 写回非功能需求。
- 列表局部更新只重组受影响页面/节点；无解释的首屏、筛选、分组耗时或后台内存回退超过 10% 时不得通过。
- 排序不创建周期任务、数据库写入、唤醒或状态通知刷新。

## 10. 测试要求

### 10.1 自动化测试

- 比较器性质测试：全序性、反对称性、传递性、相等一致性；使用随机和固定种子数据。
- 固定夹具：主键不同、同时间、同序列、更新、移除、补扫、来源时间逆序和相同正文不同条目。
- 仓储测试：Room 查询顺序与纯 Kotlin 参考比较器完全一致。
- 分页性质测试：不同页大小、页边界、空页、末页、新代失效后均无重复、遗漏或改序。
- 持久化测试：进程重建后 `firstReceivedAt`、`ingestSequence`、`itemId` 不变。
- 筛选组合测试：A12 与 B01 缩小结果集合后保持基础相对顺序。
- Compose 测试：稳定键下局部更新不造成焦点丢失或可见条目换位。

### 10.2 真机测试

- 红魔 11 Pro+、release 构建注入含相同时间和更新的 100 条数据，核对最终顺序。
- 使用 10,000 条生成数据执行冷启动、连续翻页、快速滚动、进程重建、时区和 12/24 小时切换。
- 报告记录不同 `loadSize` 下完整 `itemId` 序列哈希、查询数量、PSS 和耗时。
- 真机数据不得包含真实通知正文；使用去隐私化生成夹具。

## 11. Spike 决策门

- `SP-04` 必须锁定 `ingestSequence` 的分配与事务语义，证明更新、补扫、进程中断不会覆盖首次排序键。
- `SP-08` 必须证明相同输入在不同页大小、查看筛选和页边界下得到同一全序，且 10,000 条不全量载入。
- 若 Room 与 Kotlin 无法对 `ItemId` 使用一致比较器，必须在 schema 实施前修订逻辑标识表示；不得保留随机数据库顺序。
