# A02 应用排除列表

状态：`[候选] plan-v1.0`

## 1. 规格元数据

| 项目 | 值 |
|---|---|
| 功能 ID | `A02` |
| 优先级 | `[A]` |
| 主交付版本 | `v0.2` |
| 前置功能 | `A01 首次授权与全量监听`、`A03 通知事件采集`、`A08 本地持久化` |
| 被依赖功能 | `A13 B 站端到端真机验收` |
| 相关 Spike | `SP-04（架构 S3）摄取队列、事务与归并`、`SP-09（架构 S8）持久化、隐私与性能基线` |

本规格只控制“哪些来源的未来通知可以进入采集与持久化链路”。它不控制用户当前看见哪些历史记录。

## 2. 目标与非目标

### 2.1 目标

- 默认监控 Android 交付给 OMN 的所有通知，但始终自动排除 OMN 自身。
- 用户可以按 Android 用户与来源包名选择不再监控的应用。
- 设置页把平台当前可枚举应用、既有通知来源和已保存策略来源合并成来源目录；若 Android 包可见性使目录不完整，必须明确说明，不能伪装成“全部应用”。
- 新策略有确定的生效边界；生效后的被排除回调不复制标题、正文、动作或内容指纹。
- 排除和恢复监控只影响未来回调，不删除、不隐藏、不补采历史记录。
- 策略在进程重建后保持，并可在监听回调热路径用内存快照完成判断。

### 2.2 非目标

- 不删除被排除来源的既有 `NotificationItem`。
- 不提供“只查看某些应用”；该能力属于 `A12 多应用查看筛选`。
- 不按标题、关键词、通知渠道或通知内容建立排除规则。
- 不拦截来源通知在系统通知栏中的送达。
- 不保存被排除回调的来源级计数、正文、动作、指纹或可还原内容的诊断事实。
- 不为让列表看起来完整而静默声明 `QUERY_ALL_PACKAGES`，也不把系统当前不可见的应用当作“不存在”。

## 3. 术语与不变量

| 术语 | 精确定义 |
|---|---|
| `PackageName` | Android 来源应用包名的逻辑类型，非空。 |
| `AndroidUserRef` | Android 用户或工作资料的稳定逻辑引用。 |
| `AppUserKey` | `sourceUser + sourcePackage` 的复合来源键；同一包名在不同 Android 用户下是两个来源。 |
| `MonitoringPolicy` | 采集策略；只包含自动排除与用户排除来源及其修订信息。 |
| `MonitoringPolicySnapshot` | 与当前已生效策略一致的进程内不可变快照，供监听回调读取。 |
| `InboxFilter` | 只影响收件箱查询的查看筛选；与 `MonitoringPolicy` 没有写入依赖。 |
| `AppSourceCatalog` | 设置页的本地来源目录；由平台可见应用、既有条目来源和已保存策略来源合并，不参与热路径判断。 |
| `SourceCatalogCompleteness` | `COMPLETE`、`PLATFORM_LIMITED` 或 `UNKNOWN`；只描述来源目录覆盖度，不描述监听能力。 |
| 生效点 | 新策略持久化成功并发布为新的 `MonitoringPolicySnapshot` 的时刻。 |
| 未来回调 | 在生效点之后开始排除判断的监听回调。 |

全局不变量：

1. `alwaysExcludedPackages` 至少包含 `io.github.prince_dulb.ohmynotification`，用户不能移除。
2. `MonitoringPolicy` 与 `InboxFilter` 使用不同状态对象、不同仓储端口和不同持久化键。
3. 修改 `MonitoringPolicy` 不得修改 `InboxFilter`；修改 `InboxFilter` 不得改变策略 `revision`。
4. 排除判断必须发生在复制标题、正文、动作、完整 extras 或内容指纹之前。
5. 排除来源不产生 `NotificationItem`、来源级 `NotificationEvent` 或 `RuntimeActionHandle`。
6. 既有条目只能由独立、明确的用户删除操作删除；排除操作没有删除副作用。
7. 来源目录是否完整不得改变“未排除即默认监控”的采集语义；目录缺项只限制用户能否预先配置该来源。
8. `QUERY_ALL_PACKAGES` 或其他扩大包可见性的声明必须经 Phase 0 证明必要性、平台合规性与隐私代价，并先更新计划获得用户确认。

## 4. 输入与输出契约

本节类型为跨层逻辑契约，不锁定 Room 表、列或 TypeConverter。

### 4.1 `AppUserKey`

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `sourceUser` | `AndroidUserRef` | 是 | 不得以当前前台用户隐式替代。 |
| `sourcePackage` | `PackageName` | 是 | 非空，按 Android 包名精确比较。 |

### 4.2 `MonitoringPolicy`

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `alwaysExcludedPackages` | `Set<PackageName>` | 是 | 至少包含 OMN 自身包名；集合不可由用户编辑。 |
| `userExcludedSources` | `Set<AppUserKey>` | 是 | 初始为空；集合去重。 |
| `changedAt` | `InstantUtc` | 是 | 最近一次实际策略变化的 UTC 时刻；界面按设备时区显示。 |
| `revision` | `StableSequence` | 是 | 持久、单调递增；无变化操作不递增。 |

### 4.2.1 `AppSourceCatalogSnapshot`

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `generatedAt` | `InstantUtc` | 是 | 用户打开设置页或明确刷新时的生成时刻。 |
| `sources` | `List<AppSourceDescriptor>` | 是 | 按本地化标签、包名和用户资料形成稳定显示顺序；`AppUserKey` 不重复。 |
| `completeness` | `SourceCatalogCompleteness` | 是 | 只有 Phase 0 在目标机证明覆盖完整时才能为 `COMPLETE`。 |
| `limitationReason` | `SourceCatalogLimitation?` | 条件 | `PLATFORM_LIMITED` 或 `UNKNOWN` 时必填；使用固定枚举，不写异常原文。 |

`AppSourceDescriptor`：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `source` | `AppUserKey` | 是 | 行的稳定来源身份。 |
| `sourceLabel` | `String` | 是 | 平台标签或最近保存标签；都没有时回退包名。 |
| `profileLabel` | `String?` | 否 | 区分个人资料与工作资料。 |
| `provenance` | `Set<SourceCatalogProvenance>` | 是 | `PLATFORM_VISIBLE`、`SAVED_ITEM`、`SAVED_POLICY` 或 `AUTOMATIC_SELF`，至少一个。 |
| `availability` | `SourceAvailability` | 是 | `CURRENTLY_VISIBLE`、`NOT_CURRENTLY_VISIBLE` 或 `UNKNOWN`；不据此删除策略。 |

目录固定使用以下并集：

1. Android 支持 API 在当前可访问用户资料中返回的可见/可启动应用；
2. 长期条目中已有的不同 `AppUserKey`；
3. `MonitoringPolicy.userExcludedSources` 中仍保存的来源；
4. OMN 自身自动排除行。

目录只在用户打开页面或明确刷新时构建，不进入通知回调热路径，不联网，也不读取标题、正文、动作或完整 extras。`[待验证]` Phase 0 必须在红魔 11 Pro+ 上核对平台可见列表与真实可发通知应用；如果不扩大包可见性便无法满足可接受的预先排除体验，先形成 `QUERY_ALL_PACKAGES` 与受限目录两案的权限、分发和隐私对比，再由用户拍板，不能由实现自行加入清单声明。

### 4.3 `SetSourceExclusionCommand`

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `source` | `AppUserKey` | 是 | 目标来源。 |
| `excluded` | `Boolean` | 是 | `true` 为排除，`false` 为恢复未来监控。 |
| `expectedRevision` | `StableSequence` | 是 | 必须等于提交时已知策略修订；防止并发覆盖。 |

### 4.4 `SetSourceExclusionResult`

| 结果 | 输出字段 | 含义 |
|---|---|---|
| `APPLIED` | `policy: MonitoringPolicy` | 策略已持久化并发布内存快照；返回后新回调使用新策略。 |
| `NO_CHANGE` | `policy: MonitoringPolicy` | 请求状态已存在；不写盘、不更新时间、不递增修订。 |
| `REVISION_CONFLICT` | `currentPolicy: MonitoringPolicy` | `expectedRevision` 已过期；调用方必须用当前策略重绘，不得覆盖。 |
| `AUTOMATIC_EXCLUSION_LOCKED` | `source: AppUserKey` | 用户试图取消 OMN 自身自动排除；策略不变。 |
| `PERSISTENCE_FAILED` | `errorCode: PolicyErrorCode` | 未达到生效点；界面不得显示修改成功。 |

每个结果变体列出的输出字段均为该变体必填；未列出的变体字段不得返回。

### 4.5 热路径判断

`EvaluateMonitoringInput`：

| 字段 | 类型 | 必填 | 约束 |
|---|---|---:|---|
| `sourcePackage` | `PackageName` | 是 | 从系统回调的外层身份读取。 |
| `sourceUser` | `AndroidUserRef` | 是 | 从系统回调身份读取。 |

`MonitoringDecision`：

| 字段 | 类型 | 必填 | 取值 |
|---|---|---:|---|
| `action` | `MonitoringAction` | 是 | `MONITOR` 或 `EXCLUDE`。 |
| `policyRevision` | `StableSequence?` | 否 | 使用已加载快照判断时必填；仅 `POLICY_UNAVAILABLE` 时为空。 |
| `reason` | `MonitoringDecisionReason` | 是 | `DEFAULT_MONITOR`、`ALWAYS_EXCLUDED`、`USER_EXCLUDED` 或 `POLICY_UNAVAILABLE`。 |

## 5. 规则与状态

### 5.1 判断顺序

对每个系统回调按以下顺序执行，命中后停止：

1. 若 `sourcePackage` 在 `alwaysExcludedPackages` 中，返回 `EXCLUDE / ALWAYS_EXCLUDED`。
2. 若当前进程尚未成功加载任何持久策略快照，返回 `EXCLUDE / POLICY_UNAVAILABLE`，并报告采集暂停；不得用默认全量覆盖未知的用户排除项。
3. 否则构造 `AppUserKey(sourceUser, sourcePackage)`；若它在 `userExcludedSources` 中，返回 `EXCLUDE / USER_EXCLUDED`。
4. 否则返回 `MONITOR / DEFAULT_MONITOR`。

只有 `MONITOR` 可以继续进入 `NotificationSnapshotFactory`。`EXCLUDE` 必须直接返回，不复制内容与动作，也不查询 Room。

### 5.2 修改状态机

```text
READY(revision=N)
  ├─ 提交相同状态 ───────────────→ READY(N) + NO_CHANGE
  ├─ expectedRevision 不匹配 ────→ READY(current) + REVISION_CONFLICT
  └─ 提交实际变化 → SAVING
                         ├─ 持久化失败 → ERROR + PERSISTENCE_FAILED
                         └─ 持久化提交 → 原子发布快照 → READY(N+1) + APPLIED
```

- UI 每次切换一个来源后立即提交 `SetSourceExclusionCommand`；该行在结果返回前显示保存中并禁止重复提交。
- 只有 `APPLIED` 或 `NO_CHANGE` 可以显示最终开关状态。
- `PERSISTENCE_FAILED` 后恢复到仓储重新读取的实际策略，不保留“看起来已排除”的假状态。
- 回调若已在生效点前取得旧快照，按旧 `policyRevision` 完成；生效点后的回调必须取得新修订。
- 快照发布是提交后的进程内原子引用替换，不定义可继续运行的“发布失败”分支。进程若在持久化成功、快照发布前终止，命令不会返回 `APPLIED`；下次启动必须先从持久策略重建快照，再启用监听回调。

### 5.3 历史与恢复监控

- 排除来源后：既有条目仍可在“全部”或查看筛选中出现。
- 恢复来源后：只采集生效点后的新回调，不补扫排除期间已经消失的通知，也不声称能够补回。
- 系统重连产生的活动通知补扫仍经过当前策略；被排除来源不得因补扫绕过规则。

## 6. 用户故事与交互

### 6.1 用户故事

- 作为用户，我要排除验证码、金融或噪声应用，使其未来通知不进入 OMN 私有数据库。
- 作为用户，我要在排除后继续查看该应用的既有记录，避免配置操作意外删除历史。
- 作为拥有工作资料的用户，我要分别控制同一包名在不同 Android 用户下的监控状态。
- 作为用户，我要能看到保存失败并保持真实状态，而不是开关变了但后台仍在采集。

### 6.2 页面与行模型

`AppPolicyRow`：

| 字段 | 类型 | 必填 | 用途 |
|---|---|---:|---|
| `source` | `AppUserKey` | 是 | 行的稳定键。 |
| `sourceLabel` | `String` | 是 | 系统可用名称；未知时显示包名。 |
| `profileLabel` | `String?` | 否 | 区分个人/工作资料；只有一个用户时可不显示。 |
| `iconRef` | `PackageName` | 是 | 按包名加载有界缓存图标，不持久化逐行位图。 |
| `exclusionKind` | `ExclusionKind` | 是 | `NONE`、`USER`、`AUTOMATIC`。 |
| `saveState` | `RowSaveState` | 是 | `IDLE`、`SAVING`、`ERROR`。 |
| `provenance` | `Set<SourceCatalogProvenance>` | 是 | 供详情解释该行来自系统可见列表、历史还是已保存策略。 |
| `availability` | `SourceAvailability` | 是 | 当前不可见时保留行并给出文字说明。 |

- `AUTOMATIC` 行保持开启且禁用切换，并用文本说明“为防止循环记录，始终排除”。
- 每个开关及整行有效触控范围至少 48dp；无障碍描述包含应用名、资料、当前状态和是否可修改。
- 应用已卸载或标签不可用时仍以包名展示已持久化策略，用户可恢复监控。
- 页面搜索只过滤设置页中的应用选项，不读取通知正文，也不是 `B01` 的收件箱关键词筛选。
- `completeness != COMPLETE` 时，页面顶部显示“受 Android 限制，列表可能不完整；未列出的应用仍会按默认规则记录”，并说明首次形成历史后可从目录中排除。

## 7. Given / When / Then 验收

### AC-A02-01 默认全量与自动排除

- Given 全新安装且 `userExcludedSources` 为空
- When B 站通知和 OMN 自身状态通知分别到达
- Then B 站返回 `MONITOR`，OMN 返回 `EXCLUDE / ALWAYS_EXCLUDED`
- And OMN 自身通知不产生条目、事件正文或动作句柄

### AC-A02-02 排除从明确生效点开始

- Given 来源 A 当前未排除且策略修订为 7
- When 用户成功提交排除 A 并收到 `APPLIED(revision=8)`
- Then 生效点后的 A 回调返回 `EXCLUDE / USER_EXCLUDED / revision=8`
- And 监听热路径不复制该回调的标题、正文、动作或指纹

### AC-A02-03 生效点前回调不被重写

- Given A 的回调已用 revision 7 得到 `MONITOR`，但尚在摄取队列
- When 用户随后排除 A 并使 revision 8 生效
- Then 已接纳回调仍按 revision 7 完成事务
- And 生效点后的回调按 revision 8 排除
- And 两条结果均能用 `policyRevision` 解释

### AC-A02-04 排除不删除或隐藏历史

- Given A 已有 20 个长期条目
- When 用户排除 A
- Then 20 个条目数量、内容、排序键和动作目标均不改变
- And 查看全部历史时仍可见这些条目

### AC-A02-05 恢复不补造历史

- Given A 在一段时间内被排除，期间通知未持久化
- When 用户恢复监控 A
- Then 恢复生效点后的新回调可进入采集
- And OMN 不为排除期间构造条目或声称已经补回

### AC-A02-06 Android 用户隔离

- Given 个人资料与工作资料都安装包名 P
- When 用户只排除 `AppUserKey(work, P)`
- Then 工作资料 P 被排除
- And 个人资料 P 仍被监控

### AC-A02-07 与查看筛选完全分离

- Given `MonitoringPolicy.userExcludedSources={A}` 且 `InboxFilter.includedSources={A}`
- When 收件箱查询执行
- Then A 的既有条目仍可显示
- And A 的未来回调仍被排除
- When 用户清空 `InboxFilter`
- Then `MonitoringPolicy.revision` 与集合完全不变

### AC-A02-08 并发修改不覆盖

- Given 当前 revision 为 9
- When 两个命令都携带 `expectedRevision=9` 且第一个已成功生效
- Then 第二个返回 `REVISION_CONFLICT` 和 revision 10 的实际策略
- And 第二个不得覆盖第一个结果

### AC-A02-09 写入失败不伪装成功

- Given A 当前未排除
- When 持久化排除 A 失败
- Then 返回 `PERSISTENCE_FAILED`
- And UI 回滚到未排除
- And 后续回调继续使用最后成功发布的修订

### AC-A02-10 重连补扫遵守当前策略

- Given A 已排除且系统仍有 A 的活动通知
- When 监听重连并执行活动通知补扫
- Then A 的补扫回调在复制内容前被排除
- And 不产生重复或新条目

### AC-A02-11 首次加载失败时失败关闭

- Given 当前进程从未成功加载持久化 `MonitoringPolicy`
- When 第三方来源 A 的通知回调到达
- Then 返回 `EXCLUDE / POLICY_UNAVAILABLE`
- And 不复制 A 的标题、正文、动作、完整 extras 或内容指纹
- And 应用内健康状态明确显示“记录已暂停：无法读取排除列表”

### AC-A02-12 来源目录不虚报完整

- Given 平台包可见性隐藏来源 X，且 X 尚无长期条目和已保存策略
- When 用户打开排除设置页
- Then `completeness=PLATFORM_LIMITED`，页面明确提示列表可能不完整
- And X 未出现在列表不改变默认监控语义
- When X 的首条未排除通知成功形成长期条目并重新打开设置页
- Then X 以 `SAVED_ITEM` 来源出现，并可由用户排除未来回调

## 8. 边界条件与错误状态

| 场景/错误码 | 用户可见状态 | 系统行为 |
|---|---|---|
| `POLICY_LOAD_FAILED` | 页面显示“无法读取排除列表，记录已暂停”，提供“重试”操作 | 有旧快照时继续使用；当前进程从未成功加载时对第三方来源返回 `EXCLUDE / POLICY_UNAVAILABLE`，不复制内容；系统不自动循环重试。 |
| `POLICY_WRITE_FAILED` | 对应行显示“未保存，仍按原设置监控” | 不发布新快照，不显示成功。 |
| `REVISION_CONFLICT` | 重新载入实际状态；若用户仍要修改需再次操作 | 不自动重放旧命令，不覆盖新策略。 |
| `AUTOMATIC_EXCLUSION_LOCKED` | 说明 OMN 自身必须排除 | 集合与修订不变。 |
| 来源应用卸载/标签缺失 | 显示包名及资料，仍允许移除用户排除 | 不删除策略，不把未知来源合并到其他来源。 |
| Android 用户或工作资料不可用 | 标记来源当前不可用 | 保留策略；不将其应用到其他用户。 |
| 来源目录受包可见性限制 | 页面明确显示列表可能不完整 | 不申请未批准的广泛可见性、不把缺项视为已排除；默认监控语义保持。 |
| 空策略集合 | 显示“除本应用外，监控全部应用” | 仅 `alwaysExcludedPackages` 生效。 |
| 存储不足 | 显示策略未保存和存储修复入口 | 不改变内存策略，不进入无限重试。 |

## 9. 数据流

```text
用户切换来源
  → SetSourceExclusionCommand(expectedRevision)
  → MonitoringPolicyRepository 持久化
  → 发布 MonitoringPolicySnapshot(revision+1)
  → UI 收到 APPLIED 后显示成功

系统通知回调
  → 读取 sourceUser + sourcePackage
  → MonitoringPolicySnapshot O(1) 判断
     ├─ EXCLUDE：立即返回，不复制内容/动作
     └─ MONITOR：进入 NotificationSnapshotFactory 与摄取队列
```

查看路径独立为 `InboxFilter → InboxQuery → PagingSource`，不得调用 `MonitoringPolicyRepository` 写入方法。

## 10. 隐私与性能要求

- `MonitoringPolicy` 只保存在应用私有空间，并从 Android 自动云备份和跨设备迁移中排除。
- 被排除回调不得进入日志、诊断事件或来源级计数；监听连接健康只由独立生命周期事实表达。
- 设置页不得显示真实通知正文或根据正文推断来源。
- 来源目录的 `PackageManager`/用户资料查询只在前台页面打开或用户刷新时执行；结果使用有界短期缓存，不建立后台扫描。
- 热路径判断使用不可变 `Set` 快照，成员判断的平均时间复杂度必须为 O(1)；每个回调不得查询 Room、PackageManager 或 UI 状态。
- 策略更新只由用户操作写盘；无操作时不产生轮询、周期写入、网络或遥测。
- 100 条突发中被排除样本不应增加条目事务数；具体回调耗时、队列积压和内存预算由 `SP-04`、`SP-09` 锁定。
- 同场景 CPU、写盘或后台内存相对锁定基线无解释上升超过 10% 时不得通过。

## 11. 测试要求

### 11.1 自动化测试

- 纯领域测试：三步判断顺序、OMN 自动排除、`AppUserKey` 用户隔离、空集合默认监控。
- 仓储测试：修订递增、`NO_CHANGE` 不写盘、乐观并发冲突、进程重建恢复、写入失败回滚。

- 集成测试：`EXCLUDE` 分支不调用 `NotificationSnapshotFactory`、动作注册表或条目仓储。
- 回归测试：排除、恢复、重连补扫均不删除或修改既有 `NotificationItem`。

## 12. Spike 决策门

- `SP-04` 必须确认：策略判断与摄取队列的并发边界可重放；排除分支不静默影响已接纳事务；100 条突发无漏记或错误排除。
- `SP-09` 必须确认：策略持久化位置、自动备份排除、敏感字段扫描、热路径资源预算，以及目标机来源目录覆盖度；若提出 `QUERY_ALL_PACKAGES`，必须先给出必要性、平台分发和隐私证据并取得计划变更确认。
- 任一决策门未通过时，A02 保持未完成；不得用“最终一致”或“通常会生效”替代上述验收。
