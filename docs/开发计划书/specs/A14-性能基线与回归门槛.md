# A14 性能基线与回归门槛规格说明

- **主交付版本**：`v0.4`
- **优先级**：`[A]`
- **规格状态**：`[已确认] plan-v1.0 基线；Phase 0 未决项保持待验证`
- **Phase 0 依赖**：`SP-02 原始动作寿命与持有成本`、`SP-04 摄取队列、事务与归并`、`SP-05 监听可靠性与红魔后台策略`、`SP-06 状态通知与前台服务 A/B`、`SP-07 健康证据与区间精度`、`SP-08 排序、抽屉、筛选与分页`、`SP-09 持久化、隐私与性能基线`
- **功能依赖**：A01—A13 的可安装 release 路径、版本化测试数据、可重复真机测量步骤
- **被依赖**：`v0.4` 候选日用版本、`v0.5` 及以后每个版本的合并与发布质量门

## 1. 目标与范围

本功能建立可复现的红魔 11 Pro+ 真机性能基线，把“性能尽可能低”转化为可执行的固定工作负载、测量环境、指标、绝对预算和 10% 回归门。它先阻断不正确的候选方案，再在正确方案之间选择 CPU、内存、唤醒、写盘和耗电成本更低者。

`[已确认]` 当前文档不编造任何绝对 CPU、PSS、耗电、写盘或交互耗时数字。绝对预算必须由 Phase 0 release 真机测量产生，写回非功能需求与基线记录后才生效。

`[已确认]` 基线建立后，同设备、同构建类型、同配置、同数据集、同测量口径下，受管指标中任一中位数回退超过 10% 即阻断合并和候选发布。预期为零的结构性工作不适用百分比豁免：新增周期轮询、主动唤醒、周期写入、精确闹钟或前台服务空转直接失败。

### 1.1 本功能不做

- 不用 debug 构建、模拟器体感或单次截图锁定预算。
- 不为获得更漂亮数据关闭采集、延迟可靠持久化、减少测试通知或跳过异常路径。
- 不把 16 GB 内存和 1 TB 存储当作允许全量加载、无界缓存或无界日志的理由。
- 不自动修改 CI/CD、生成公开 release、推送 GitHub 或发布 APK。
- 不在 Phase 0 A/B 完成前预设前台服务；FGS 保持 `[待验证]`。

## 2. 术语与场景契约

### 2.1 `PerformanceScenarioId`

| 值 | 固定工作负载 | 主要目标 |
|---|---|---|
| `IDLE_SCREEN_OFF_8H` | 监听已就绪、界面后台、队列清空后息屏 8 小时且不发送测试通知 | 发现周期 CPU、唤醒、写盘、状态通知刷新和长待机耗电 |
| `BURST_100_CALLBACKS` | 按版本化清单交付恰好 100 个发布、更新、移除和自通知回调 | 验证不漏记、事务/刷新合并、处理 CPU 与峰值内存 |
| `HISTORY_10000_ITEMS` | 预置恰好 10,000 个去隐私化长期逻辑条目，执行固定首屏、翻页、滚动、筛选和抽屉操作 | 验证分页、增量分组、PSS 和交互耗时 |
| `LONG_STANDBY_AND_RESTART` | 执行计划记录的长待机、进程重建、监听重连和设备重启序列 | 验证可靠性不靠高频唤醒，健康证据与恢复一致 |
| `PRESENCE_MODE_AB` | 在其余相同条件下分别运行 `ORDINARY_ONGOING` 与 `FOREGROUND_SERVICE` 候选 | 选择状态通知承载方式；FGS 仅在合法类型已确认后参测 |
| `DATABASE_GROWTH` | 从空库起按固定批次增加去隐私化条目与诊断事件，直到覆盖上限触发 | 锁定单条增长、诊断上限和缓存上限 |

### 2.2 指标方向

| `MetricDirection` | 定义 | 判定方式 |
|---|---|---|
| `LOWER_IS_BETTER` | 数值越低越好 | 与绝对预算及 10% 相对门比较。 |
| `ZERO_STRUCTURAL` | 架构要求应用主动归因为零 | 任一可重复非零应用主动行为即失败，不用百分比。 |
| `EXACT_EXPECTED` | 必须等于测试清单期望值 | 例如漏记、误合并、重复条目均必须为 0。 |
| `INFORMATIONAL` | 当前测量尚不能稳定比较 | 仍记录；Phase 0 结束前必须升级为可比较指标或形成 `REDIRECT`，不能用它宣称通过。 |

### 2.3 基线、预算和回归

- **有效测量**：构建、设备、权限、工作负载和工具均符合本规格，且没有系统更新、充电状态变化、温控降频或无关应用异常活动污染。
- **基线值 `B`**：同一场景有效测量中指定指标的中位数。
- **绝对预算 `A`**：Phase 0 写回文档的带单位上限。默认锁定为 `B × 1.10`；离散整数指标向更严格方向取整。因可用性或平台要求设定的更严格上限优先。任何更宽松上限必须有原因、证据和用户确认。
- **回归比 `R`**：当 `B > 0` 时，`R = (currentMedian - B) / B`。`R > 0.10` 为回归失败。
- **零基线**：当 `B = 0` 时不计算比例。结构性零指标保持 0；其他指标须在 Phase 0 写入可解释的绝对单位上限，不能用除零或“增长百分比不适用”放行。
- **最近通过基线**：最后一个完整通过且没有被静默放宽的基线版本。失败构建不得成为新基线。

## 3. 用户故事

> 作为项目所有者，我想知道 OMN 在无通知待机、通知突发和万级历史下真实占用多少资源，并能比较普通状态通知与前台服务，以便只保留可靠且成本最低的方案。

> 作为后续维护者，我想每次改动都能用同一设备、同一工作负载和同一统计口径与已通过版本比较，以便超过 10% 的性能退化不会悄悄进入日用版本。

> 作为功能实现者，我想在性能测量前先通过数据正确性门，以免通过漏记或少做工作制造虚假的低占用结果。

## 6. 测量状态机与规则

### 6.1 状态机

```text
UNCONFIGURED
  → 环境、构建、清单、工具齐全 → READY
  → 开始 run                 → MEASURING
  → 原始结果完成              → VALIDATING
      ├─ 环境/数据/指标无效    → INVALID
      ├─ 正确性失败            → FAIL
      ├─ 波动未收敛            → UNSTABLE → 追加有效 run
      ├─ 尚无基线              → NEEDS_BASELINE_LOCK
      ├─ 预算或 10% 门失败     → FAIL
      └─ 全部通过              → PASS

NEEDS_BASELINE_LOCK
  → Phase 0 写回绝对预算 + 用户确认 → BASELINE_LOCKED
```

只有 `BASELINE_LOCKED` 后的场景可用于版本回归 `PASS`。`INVALID` 不是失败也不是通过，必须保留原因并重测。

### 6.2 有效 run 与统计

1. 短场景先执行至少 1 次预热，预热不进入统计；随后至少 3 次有效测量。
2. `IDLE_SCREEN_OFF_8H` 每种候选架构至少 2 次有效测量。
3. 每个指标的波动率定义为 `(max - min) / median`。`median > 0` 且波动率超过 10% 时状态为 `UNSTABLE`，追加测量并调查环境；不能选择性删除较差结果。
4. `median = 0` 时，任一非零值都须逐项归因。结构性零指标有非零应用主动行为直接失败；系统噪声只有在测量工具能证明不可归因于 OMN 时才能排除。
5. 比较使用有效 run 中位数，不用最佳值、最差值或任意挑选的一次结果。
6. 系统更新、充电状态变化、温控异常、数据集 hash 不同、必测指标缺失、无关应用异常负载或构建非 release 均使 run 无效。

### 6.3 正确性先行门

任何候选方案在下列任一项失败后，不计算“性能胜出”：

- 100 条清单有输入回调没有可核对结果；
- 未排除通知漏记；
- 不同通知误合并；
- 同一通知更新制造重复逻辑条目；
- 数据库事务中断后出现半条目或虚假成功计数；
- 状态通知摘要领先于数据库提交；
- 10,000 条分页出现丢失、重复、改序或错误抽屉；
- 权限、监听和健康状态被错误合并；
- 精确跳转被降级打开冒充成功。

正确性失败的低 CPU、低写盘或低内存结果不能成为基线。

### 6.4 绝对预算锁定

1. Phase 0 为每个场景和必测指标形成基线 `B`。
2. 对 `LOWER_IS_BETTER`，默认绝对预算 `A = B × 1.10`；整数计数向下取整到不会放过超过 10% 的最大整数。若任一有效 run 已超过该上限，则该基线不具备锁定条件，须调查噪声并按第 6.2 节追加测量，不能放宽预算覆盖较差 run。
3. 对 `ZERO_STRUCTURAL`，预算固定为 0 个可归因周期行为。
4. 对正确性指标，预算等于清单期望，漏记、重复、误合并和未处理队列数固定为 0。
5. 对交互耗时等用户体验指标，若固定操作无法完整完成，或用户明确拒绝把 Phase 0 实测值作为首版上限，即使 `B × 1.10` 也不能锁定为通过预算；先优化或输出 `REDIRECT`。
6. 将数值、单位、统计方法、设备/系统、环境指纹、数据 hash 和工具命令写入非功能需求或其受控基线记录，并获得用户确认。
7. 未完成上述写回的场景保持 `NEEDS_BASELINE_LOCK`，不能进入 `v0.4` 完成声明。

### 6.5 10% 回归门

1. 当前中位数必须同时满足 `current <= absoluteBudget` 和 `R <= 0.10`；任一失败即 `FAIL`。
2. 10% 适用于同口径的 CPU 时间、应用可归因唤醒次数/时长、数据库写入次数/量/增长、后台/峰值 PSS、状态通知刷新、突发处理耗时、万级首屏/筛选/分组/滚动耗时和达到可重复条件后的耗电。
3. 新增稳定的周期轮询、唤醒、数据库写入、精确闹钟、高频心跳或 FGS 空转直接失败，即使总耗电测量未超过 10%。
4. 超过 10% 只有两条路径：修复后重测；或证明 run 无效后按原协议重测。
5. 若资源增加来自明确的正确性/可靠性收益，记录根因、收益、成本和替代方案，由用户确认计划变更后建立新基线。旧结果不得删除，且新基线不能以失败构建自动覆盖。

## 7. 固定场景执行协议

### 7.1 8 小时息屏、无通知

前置条件：

- release 构建已安装并完成场景指定权限；
- 监听已连接，界面退到后台，摄取队列与待提交事务为空；
- 状态通知模式、渠道、红魔后台策略、网络、电源和充电状态已记录；
- 不向设备发送测试通知，不主动打开 OMN。

执行：息屏连续 8 小时，结束后收集 CPU 时间、PSS/进程存在时间、应用可归因唤醒、数据库事务/写入、状态通知发布、耗电和健康区间。

结构性通过：没有 OMN 主动周期轮询、唤醒锁、精确闹钟、高频心跳、周期数据库写入或前台服务空转。应用被系统终止、监听恢复或出现黄色区间按可靠性事实记录，不能通过主动保活修改测试。

### 7.2 100 条突发通知及更新

清单恰好包含 100 个有全序的系统回调，且必须覆盖：

- 新发布；
- 同一身份密集更新；
- 移除；
- 同标题/正文但目标不同；
- 多应用交错；
- OMN 自身状态通知。

清单记录每个回调的预期事件、逻辑条目、内容 revision、累计数和排序结果。执行后逐项对账，再统计完成耗时、CPU、峰值 PSS、队列峰值、事务数、写入量和状态发布次数。状态刷新必须合并，最大次数由 Phase 0 锁定，不能逐回调刷新。

### 7.3 10,000 条历史

预置恰好 10,000 个合成长期条目，覆盖同时间戳、长/空文本、15 分钟窗口、最多跨越 3 条其他来源、页边界和单应用极端突发。按清单执行：冷启动首屏、连续翻页、固定距离滚动、展开/折叠指定抽屉、切换固定多应用筛选、返回列表。

通过条件：不全表载入；加载峰值不随 10,000 总量等比例增长；页边界不丢失、不重复、不改序；分组结果不随页大小改变；每项耗时和 PSS 满足锁定预算。

### 7.4 承载方式 A/B

`ORDINARY_ONGOING` 与 `FOREGROUND_SERVICE` 在同构建源码、同权限、同渠道、同数据、同厂商策略下分别运行 idle、burst、重启场景。FGS 未确认合法真实服务类型前不作为可交付候选，只能在受控 Spike 中验证平台行为。

先比较漏记、恢复和状态语义。两者都满足正确性时，若一种模式在全部已锁定资源指标上不高于另一种、且至少一项更低，则选择该模式；指标互有胜负时报告每项差值与用户可感知收益，由用户决定，不用未定义“综合分”自动裁决。

## 8. 权限与生命周期边界

- 每个 run 分别记录通知使用权、`POST_NOTIFICATIONS`、渠道、监听连接和进程证据；缺一即环境不完整。
- 场景未要求权限切换时，任何维度在 run 中变化都须记录时间；变化导致工作负载不可比时 run 无效，但原始结果保留。
- `POST_NOTIFICATIONS` 被拒绝不能被记成监听失效；状态通知发布数需按不可见配置单独建立场景，不能与权限已授予基线比较。
- 普通状态通知残留不能被记成进程持续存在。进程存在时间、连接证据和通知可见时间分别测量。
- 进程被系统终止是可靠性结果，不自动使 run 无效；只有测试协议或环境被破坏才无效。
- 手机重启前后使用不同进程会话，单调时钟不跨重启；报告使用带时区 UTC 时间线。
- FGS 模式只有在服务类型合法、清单声明真实且无空转时可成为生产基线。

## 9. Given / When / Then 验收条件

1. **拒绝 debug 基线**<br>
   Given 构建类型为 `DEBUG`，When 尝试锁定基线，Then 输出 `INVALID(BUILD_NOT_RELEASE)`，不生成预算。

2. **正确性优先**<br>
   Given 候选方案在 100 条场景漏记 1 条，When 汇总性能，Then overall 为 `FAIL(CORRECTNESS_FAILED)`，即使 CPU 低于其他方案也不能胜出。

3. **短场景统计**<br>
   Given 1 次预热和至少 3 次有效测量，When 计算基线，Then只用有效测量中位数，预热和无效 run 不进入统计但仍保留记录。

4. **8 小时重复性**<br>
   Given 同一候选架构完成 2 次有效 8 小时测试且指标差异超过 10%，When 汇总，Then 状态为 `UNSTABLE` 并要求追加测量，不取较好一次。

5. **环境指纹不一致**<br>
   Given Android 构建、权限或红魔后台策略与基线不同，When 执行 10% 比较，Then 输出 `INVALID(ENVIRONMENT_MISMATCH)`，不宣称回归或通过。

6. **10% 边界**<br>
   Given 基线 `B>0`，When 当前中位数恰好为 `B×1.10` 且不超过绝对预算，Then 相对门通过；When 当前值大于 `B×1.10`，Then失败。

7. **零基线**<br>
   Given idle 基线没有可归因周期写入，When 新版稳定出现周期写入，Then结构性门失败，不计算“从 0 增长多少百分比”。

8. **绝对预算未锁**<br>
   Given已有测量但非功能需求尚未写入带单位预算和用户确认，When `v0.4` 验收，Then输出 `NEEDS_BASELINE_LOCK`，不得标记 A14 完成。

9. **状态通知刷新回归**<br>
   Given同一 100 条数据集和基线刷新数，When新版中位刷新数回退超过 10% 或超过绝对预算，Then阻断合并。

10. **万级不全载入**<br>
    Given 10,000 条历史，When执行固定操作，Then查询/内存证据显示没有把全部条目长期驻留，且排序与抽屉结果和清单一致。

11. **普通通知与 FGS A/B**<br>
    Given两种模式正确性都通过，When资源指标一方在所有受管项不高于另一方，Then选择该较低成本模式；若互有胜负，Then输出逐项取舍等待用户决策。

12. **FGS 未合规**<br>
    Given没有合法真实 foreground service type 结论，When尝试把 FGS run 锁为生产基线，Then失败并保持 FGS `[待验证]`。

13. **耗电不可重复**<br>
    Given耗电测量方法在同条件下持续高波动，When Phase 0 汇总，Then不得填入虚假预算或宣称通过，必须调整协议或 `REDIRECT`。

14. **敏感数据检查**<br>
    Given原始结果包含真实通知正文、完整 URI、Token 或本机敏感路径，When准备纳入公开基线记录，Then输出 `FAIL(PRIVACY_VIOLATION)` 并停止公开，不删除本地取证事实。

## 10. 错误状态

| 错误 | 触发条件 | 报告结果 | 处理 |
|---|---|---|---|
| `BUILD_NOT_RELEASE` | debug 或未知构建路径 | `INVALID` | 用 release/等价测量构建重跑。 |
| `ENVIRONMENT_MISMATCH` | 设备、系统、权限、渠道、连接、厂商策略、工具口径不一致 | `INVALID` | 恢复相同环境或建立经批准的新基线。 |
| `DATASET_MISMATCH` | 版本/hash/操作顺序不同 | `INVALID` | 使用基线数据重跑。 |
| `MISSING_METRIC` | 必测项或原始证据缺失 | `INVALID` | 补全观测后整次重跑。 |
| `NOISE_TOO_HIGH` | 按公式波动超过 10% | `UNSTABLE` | 查明噪声并追加有效 run。 |
| `CORRECTNESS_FAILED` | 漏记、重复、误合并、改序或状态错误 | `FAIL` | 修正确性；不得比较性能胜负。 |
| `STRUCTURAL_IDLE_WORK` | 出现周期轮询、唤醒、写入、精确闹钟、心跳或 FGS 空转 | `FAIL` | 删除无意义工作并重测。 |
| `ABSOLUTE_BUDGET_EXCEEDED` | 当前中位数超过 `A` | `FAIL` | 优化或用户确认计划变更。 |
| `REGRESSION_OVER_10_PERCENT` | `R>0.10` | `FAIL` | 修复或证明 run 无效后重测。 |
| `BASELINE_NOT_LOCKED` | 数值/单位/环境/用户确认缺失 | `NEEDS_BASELINE_LOCK` | 完成 Phase 0 写回。 |
| `FGS_COMPLIANCE_UNKNOWN` | FGS 类型或启动规则未确认 | `FAIL`（生产候选） | 保持 Spike，不进入生产方案。 |
| `PRIVACY_VIOLATION` | 报告含敏感通知或本机数据 | `FAIL` | 停止公开，脱敏并重新审查。 |

失败、无效和不稳定结果必须保留时间、环境和原因；不得删除较差 run 后重新计算中位数。

## 11. 交互与报告流程

A14 是工程质量能力，不向日常用户增加后台界面或周期任务。报告流程为：

```text
选择 commit + 固定场景
  → 记录 release 构建与五维运行配置
  → 校验设备/数据/工具
  → 执行预热和有效 run
  → 先核对功能正确性
  → 计算中位数与波动
  → 对照绝对预算和 10% 门
  → 输出 PASS / FAIL / INVALID / NEEDS_BASELINE_LOCK
  → 保存去隐私化证据与计划引用
```

任何展示性能结果的本地页面或报告都必须显示构建、设备、数据版本、有效 run 数和统计口径，不能只显示一个“性能良好”徽标。

## 12. 隐私、安全与资源约束

- 数据集使用合成标题、正文、包名和动作；真机 B 站功能样本与性能清单分开，不把真实原文写入报告。
- 原始命令输出公开前移除通知正文、完整 URI、内容 ID、`PendingIntent`、Token、签名材料、本机 SDK 路径和个人设备标识。
- 性能测量不得新增应用运行时网络、遥测或远程心跳。报告默认本地生成，公开发布另行授权。
- 测量插桩不得改变核心队列、事务、状态刷新和服务拓扑；若有差异，构建不能作为生产基线。
- 测量工具自身开销必须记录；同一比较组使用相同工具和采样设置。
- 基线记录有版本、不可静默覆盖；变更通过计划记录关联旧基线和用户决策。
- 运行测试不授权修改 CI/CD、系统全局配置、数据库 schema、公开发布或安装全局依赖。

## 13. 自动化与真机测试

### 13.1 自动化测试

- 中位数、波动率、10% 比例、恰好 10% 边界、零基线和整数预算取整算法。
- 环境指纹规范化：五个健康维度、presence mode、系统/工具/数据差异均能使不可比结果失配。
- 状态机从 `READY` 到 `PASS`、`FAIL`、`INVALID`、`UNSTABLE`、`NEEDS_BASELINE_LOCK` 的完整分支。
- 正确性失败优先于性能比较，失败 run 不进入基线。
- 100 条清单 expected result 对账；数据 hash 和操作顺序改变时拒绝比较。
- 10,000 条操作清单、分页正确性和查询加载峰值断言。
- 敏感字段扫描，公开报告夹具不得含正文、完整 URI、令牌或个人路径。
- 结构性检查能检测轮询、唤醒锁、精确闹钟、周期任务和 FGS 空转配置。

### 13.2 红魔 11 Pro+ 真机测试

- 两次以上 `IDLE_SCREEN_OFF_8H`；触发第 6.2 节波动条件时追加测量，直到获得可锁定结果或输出 `REDIRECT`。
- 至少 3 次有效 `BURST_100_CALLBACKS` 和 `HISTORY_10000_ITEMS`，另有预热 run。
- `LONG_STANDBY_AND_RESTART` 覆盖监听断连/重连、进程重建、手机重启和红魔后台策略。
- `PRESENCE_MODE_AB` 在 FGS 合法性确认后使用相同条件比较两种模式。
- `DATABASE_GROWTH` 记录空库、固定批次增量、诊断上限稳定态和缓存峰值。
- APK/依赖检查确认 v0 纯 Kotlin/Java/AndroidX 路径且无仅 32 位原生库。
- 所有结果来自 release 或记录差异的 release measurement 构建；模拟器不锁预算。

## 14. Phase 0 Spike 与决策门

### 14.1 `SP-09 持久化、隐私与性能基线` 必须回答

1. 每个必测指标使用什么工具、单位、采样窗口和噪声排除方法？
2. 8 小时、100 条、10,000 条、数据库增长场景的真实基线和绝对预算分别是多少？
3. 状态通知突发合并窗口、最大刷新数、摄取队列容量、诊断事件上限和图标缓存上限应锁定为何值？
4. 普通 ongoing 与合法 FGS 哪个在正确性、状态语义和资源成本上通过？
5. 耗电测量能否达到可重复口径；若不能，如何调整测试而不伪造数字？

### 14.2 证据产物

- 每个场景的 `ScenarioManifest`、数据 hash、工具和命令；
- 所有有效、无效、失败和预热 run 清单；
- 指标原始值、中位数、波动率、环境指纹和正确性对账；
- 两种承载模式 A/B 及平台合规结论；
- 带单位绝对预算、结构性零指标和 10% 门；
- 写回非功能需求的变更及用户确认引用。

### 14.3 决策门

- **GO**：所有固定场景正确性通过；测量可重复；绝对预算已锁定；空闲无结构性后台工作；一种合规承载模式通过；10% 门可自动或按固定步骤复现。
- **REDIRECT**：指标噪声、状态通知语义、厂商后台策略或资源取舍需要改变协议/产品边界；先更新计划并由用户确认。
- **STOP**：所有满足不漏记、数据完整和精确跳转的方案均至少违反一项用户已确认的绝对资源预算，或唯一可用后台方案依赖不合规 FGS、高频唤醒或空转。

A14 只有在 Phase 0 完成全部基线锁定，并在 `v0.4` 的生产路径 release 构建上重跑通过后，才可标记完成。此后每个版本都必须以最近通过基线执行同一回归门。
