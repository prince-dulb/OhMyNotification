# B02 保留与清理策略规格说明

- **主交付版本**：`v0.5`
- **优先级**：`[B]`
- **规格状态**：`[已确认] plan-v1.0 基线；Phase 0 未决项保持待验证`
- **Phase 0 依赖**：`SP-09 持久化、隐私与性能基线`
- **功能依赖**：A02 应用排除列表、A03 通知事件采集、A08 本地持久化、A09 原内容跳转、A14 性能基线与回归门槛
- **被依赖**：B03 诊断导出、`v0.5` 长期日用与存储质量门

`[已确认]` 2026-08-29 将“单条通知记录的明确删除”提前到当前 MVP：每条已记录通知提供可见的“删除记录”动作，确认后删除该条目和当前进程动作句柄。健康证据继续保留，避免用户删除通知后反向改写蓝黄运行时间轴。删除不改变监控设置；若来源应用随后重新发送或更新同一系统通知，OMN 仍可按正常采集规则再次形成记录。批量选择、存储占用和自动诊断清理仍属于本规格原定的 `v0.5` 范围。

## 1. 目标与范围

本功能定义不同本地数据的保留边界、存储占用展示、有界诊断清理，以及用户主动删除长期通知条目的确认流程。

`[已确认]` v0 对长期 `NotificationItem` 不按年龄、数量、数据库大小、存储压力或跳转状态自动删除。记录存在多久与动作是否可尝试无关。

`[已确认]` 诊断事件、内部故障记录和缓存必须有界。具体条数、时间、字节上限及测量方法由 `SP-09` 的 release 真机数据锁定；在取得基线前，本文不编造数字。

`[已确认]` 用户删除长期条目是独立、明确且需确认目标范围的操作。把应用加入排除列表、切换查看筛选、清理诊断或缓存、跳转失败和系统通知被划除都不得删除长期条目。

### 1.1 本功能不做

- 不提供按天数、条数或容量自动删除长期通知条目的开关。
- 不在存储不足时静默删除“最旧通知”。
- 不把“排除应用”或“只查看某应用”改造成删除命令。
- 不以动作失效、内容删除或来源应用卸载为删除理由。
- 不为执行清理增加周期 `WorkManager`、轮询、精确闹钟、唤醒锁或常驻服务。
- 不删除 B03 已由用户保存到外部位置的诊断文件；该文件由用户和目标文档提供方管理。
- 不在本文锁定或实施 Room entity、表、列、关系、索引、schema 版本或迁移。

## 2. 数据类别与保留契约

| `RetentionClass` | 内容 | v0 保留规则 | 可由谁清理 |
|---|---|---|---|
| `LONG_TERM_NOTIFICATION_ITEM` | 合并后的通知条目及其展示内容。 | 无限期保留，直到用户明确删除该条目。 | 仅用户确认删除。 |
| `PERSISTENT_ACTION_TARGET` | 与条目关联的精确持久目标及 `APP_LAUNCH` 能力摘要。 | 与所属条目同寿命；失败或年龄不自动删除。 | 随用户确认删除所属条目。 |
| `ACTION_ATTEMPT_SUMMARY` | 去敏动作层、结果枚举和时间。 | 有界诊断数据；不得保留 URI、内容 ID 或动作令牌。 | 上限执行或用户清理诊断。 |
| `DIAGNOSTIC_NOTIFICATION_EVENT` | 用于归并、漏记和事务诊断的最小事件事实。 | 按 `SP-09` 锁定的条数/时间规则有界。 | 上限执行或用户清理诊断。 |
| `HEALTH_DIAGNOSTIC_FACT` | 监听、权限、渠道、进程会话的最小事实。 | 按 `SP-09` 锁定规则有界；派生蓝黄区间所需的用户可见事实边界必须一并验证。 | 上限执行或用户清理诊断；不得制造虚假蓝段。 |
| `FAILURE_COUNTER` | 固定错误枚举的计数与最近时间。 | 枚举键集合固定；时间桶或历史明细有界。 | 上限执行或用户清理诊断。 |
| `ICON_CACHE` | 由包名可重新取得的应用图标缓存。 | 按 `SP-09` 字节上限有界；可随时重建。 | 自动容量淘汰或用户清缓存。 |
| `RUNTIME_ACTION_HANDLE` | 当前进程内 `PendingIntent` 句柄。 | 仅当前 `runtimeSessionId` 内存；不是磁盘保留数据。 | 进程结束、实际消费/取消，或用户删除所属条目。 |
| `USER_EXPORTED_DIAGNOSTIC` | 用户通过 B03 保存到选定位置的文件。 | 不纳入 OMN 私有存储保留策略。 | 用户或外部文档提供方。 |

全局不变量：任何自动诊断/缓存清理都不得级联删除 `LONG_TERM_NOTIFICATION_ITEM` 或 `PERSISTENT_ACTION_TARGET`。

## 3. 用户故事

- 作为长期使用者，我希望通知历史不会因为变旧、变多或跳转失败而悄悄消失。
- 作为关注存储的用户，我希望看到条目、诊断和缓存分别占用了多少空间，以及数字的测量口径。
- 作为需要排障的用户，我希望诊断数据不会无限增长，又不会因清诊断误删通知。
- 作为主动整理历史的用户，我希望删除前看到确切目标范围，并且只删除我确认的条目。

## 4. 输入契约

以下是逻辑输入，不是数据库 schema。

### 4.1 `RetentionPolicySnapshot`

| 字段 | 逻辑类型 | 必填 | 规则 |
|---|---|---:|---|
| `policyVersion` | `PolicyVersion` | 是 | 每次锁定规则变化必须变化，并同步测试与计划变更记录。 |
| `longTermItemMode` | `LongTermItemMode` | 是 | v0 固定为 `USER_DELETE_ONLY`。 |
| `diagnosticRule` | `DiagnosticRetentionRule` | 是 | 见 4.2；未锁定时为 `UNLOCKED`。 |
| `iconCacheMaxBytes` | `ByteCount?` | 否 | `SP-09` 锁定后必填；锁定前为空。 |
| `usageMeasurementMethodVersion` | `MethodVersion?` | 否 | `SP-09` 锁定后必填。 |
| `usageErrorBound` | `UsageErrorBound?` | 否 | 与测量方法一起锁定；UI 必须按该口径标识估算值。 |
| `lockedAt` | `InstantUtc?` | 否 | Phase 0 写入规则的时刻；未锁定为空。 |
| `evidenceRef` | `EvidenceRef?` | 否 | 指向去敏 Phase 0 报告，不含本机私有路径。 |

`longTermItemMode` 在 v0 不可通过普通设置修改。将来若引入长期条目自动清理，必须重新确认产品策略并修改本规格。

### 4.2 `DiagnosticRetentionRule`

| 字段 | 逻辑类型 | 必填条件 | 规则 |
|---|---|---:|---|
| `status` | `LimitLockState` | 总是 | `UNLOCKED` 或 `LOCKED`。 |
| `maxCount` | `PositiveLong?` | 按锁定结果 | 条数上限；不使用零或负值。 |
| `maxAge` | `PositiveDuration?` | 按锁定结果 | 从事件 `occurredAt` 计算的时间上限。 |
| `maxAllocatedBytes` | `PositiveByteCount?` | 按锁定结果 | 若 Phase 0 证明可稳定测量才使用。 |
| `triggerMode` | `DiagnosticTrimTrigger?` | `LOCKED` 时 | 固定为 `ON_DIAGNOSTIC_COMMIT` 或 `ON_EXPLICIT_MAINTENANCE_EVENT`；后者不是周期任务。 |
| `order` | `RetentionOrder?` | `LOCKED` 时 | 固定为 `retentionOrder ASC, eventId ASC`。 |

锁定规则：

1. `UNLOCKED` 时不得宣称 B02 完成，也不得用源码内魔法数字替代。
2. `LOCKED` 时 `maxCount`、`maxAge`、`maxAllocatedBytes` 至少一个非空，且所有非空限制同时生效；最先超出的限制触发清理。
3. 清理按固定顺序删除最旧的合格诊断事实，直到所有已锁定限制重新满足。
4. 若按字节限制无法稳定映射到单条诊断事实，`SP-09` 必须选择条数/时间规则，而不是假装精确字节淘汰。

### 4.3 `StorageUsageRequest`

| 字段 | 逻辑类型 | 必填 | 规则 |
|---|---|---:|---|
| `requestedAt` | `InstantUtc` | 是 | 用户打开存储页或手动刷新时产生。 |
| `categories` | `Set<StorageCategory>` | 是 | 非空；允许 `NOTIFICATION_ITEMS`、`DIAGNOSTICS`、`CACHE`、`TOTAL_PRIVATE_STORAGE`。 |
| `requestId` | `RequestId` | 是 | 当前请求唯一，用于丢弃过时结果。 |

存储占用只在用户打开页面或明确刷新时计算，不在后台周期更新。

### 4.4 `DeletePreviewRequest`

| 字段 | 逻辑类型 | 必填 | 规则 |
|---|---|---:|---|
| `itemIds` | `NonEmptySet<ItemId>` | 是 | 只包含用户在当前列表/详情明确选择的长期条目。 |
| `runtimeSessionId` | `RuntimeSessionId` | 是 | 预览仅在当前进程会话有效。 |
| `requestedAt` | `InstantUtc` | 是 | 记录用户请求时刻。 |

v0.5 不支持通过“早于某日”“超过某数量”或“某应用全部历史”等隐式规则直接删除；若界面将来提供批量条件，必须先扩充规格和验收。

### 4.5 `DeleteConfirmRequest`

| 字段 | 逻辑类型 | 必填 | 规则 |
|---|---|---:|---|
| `previewId` | `DeletePreviewId` | 是 | 来自当前会话成功预览。 |
| `selectionDigest` | `Digest` | 是 | 与预览中排序后的条目 ID 集合完全一致；不含正文。 |
| `runtimeSessionId` | `RuntimeSessionId` | 是 | 必须与预览一致。 |
| `confirmed` | `Boolean` | 是 | 只有用户点击明确“删除 N 条记录”按钮才为 `true`。 |
| `confirmedAt` | `InstantUtc` | 是 | 用户确认时刻。 |

## 5. 输出契约

### 5.1 `StorageUsageSnapshot`

| 字段 | 逻辑类型 | 必填 | 规则 |
|---|---|---:|---|
| `measuredAt` | `InstantUtc` | 是 | 快照完成时刻。 |
| `policyVersion` | `PolicyVersion` | 是 | 指明采用的测量与保留口径。 |
| `notificationItemCount` | `NonNegativeLong` | 是 | 长期逻辑条目数量。 |
| `diagnosticEventCount` | `NonNegativeLong` | 是 | 当前有界诊断事实数量。 |
| `measurements` | `List<StorageMeasurement>` | 是 | 每个请求类别恰有一项。 |
| `concurrentChangeObserved` | `Boolean` | 是 | 测量期间若有新提交或清理则为真，UI 显示“数据正在变化”。 |

`StorageMeasurement` 包含 `category`、`valueBytes`、`accuracy = EXACT | ESTIMATED | UNAVAILABLE`、`methodVersion` 和 `errorBound`。`UNAVAILABLE` 时 `valueBytes` 为空，并显示原因；不得以 0 代替未知。测量方法与误差界限由 `SP-09` 锁定。

### 5.2 `DeletePreview`

| 字段 | 逻辑类型 | 必填 | 规则 |
|---|---|---:|---|
| `previewId` | `DeletePreviewId` | 是 | 当前会话唯一。 |
| `selectionDigest` | `Digest` | 是 | 排序后条目 ID 集合的摘要。 |
| `itemCount` | `PositiveInt` | 是 | 与仍存在的选中条目数量一致。 |
| `oldestReceivedAt` / `newestReceivedAt` | `InstantUtc` | 是 | 用户按设备时区查看；不改变事实。 |
| `sourceSummaries` | `List<LocalSourceSummary>` | 是 | 本机界面显示来源和数量；不进入日志或导出。 |
| `associatedDataNotice` | `AssociatedDataNotice` | 是 | 明确说明同时删除的持久目标、动作尝试摘要和当前进程句柄。 |
| `isIrreversible` | `Boolean` | 是 | v0 固定为 `true`；不存在回收站或撤销承诺。 |

### 5.3 `DeletionResult`

| 字段 | 逻辑类型 | 必填 | 规则 |
|---|---|---:|---|
| `status` | `DeletionStatus` | 是 | `DELETED`、`CANCELED`、`STALE_PREVIEW`、`ITEM_SET_CHANGED` 或 `FAILED_NO_CHANGE`。 |
| `deletedItemCount` | `NonNegativeInt` | 是 | 只有事务成功后大于零。 |
| `deletedTargetCount` | `NonNegativeInt` | 是 | 所属持久目标数量。 |
| `deletedDiagnosticCount` | `NonNegativeInt` | 是 | 与选中条目直接关联且不应独立保留的去敏尝试/事件数量。 |
| `completedAt` | `InstantUtc` | 是 | UTC。 |
| `failureReason` | `RetentionFailureReason?` | 否 | 失败时必填。 |

删除必须是一个逻辑原子操作：选中条目及其内容型关联数据要么全部成功删除，要么保持原状。健康证据、其他条目、监控排除策略、查看筛选和外部导出文件不得受影响。

| 字段 | 逻辑类型 | 必填 | 规则 |
|---|---|---:|---|
| `cause` | `TrimCause` | 是 | `LOCKED_LIMIT_EXCEEDED` 或 `USER_REQUESTED_DIAGNOSTIC_CLEAR`。 |
| `policyVersion` | `PolicyVersion` | 是 | 必须是已锁定版本。 |
| `beforeCount` / `afterCount` | `NonNegativeLong` | 是 | 清理前后诊断事实数量。 |
| `trimmedCount` | `NonNegativeLong` | 是 | 等于成功删除的诊断事实数。 |
| `longTermItemCountBefore` / `longTermItemCountAfter` | `NonNegativeLong` | 是 | 必须相等。 |
| `status` | `TrimStatus` | 是 | `COMPLETED`、`NOT_NEEDED` 或 `FAILED_NO_ITEM_DELETION`。 |

## 6. 状态机与精确规则

### 6.1 长期条目

```text
PRESENT
  ├─ 年龄/数量/容量/动作失败/排除/筛选/诊断清理 → PRESENT
  ├─ 删除预览取消或过时 → PRESENT
  ├─ 删除事务失败 → PRESENT
  └─ 当前会话明确预览 + 同集合确认 + 原子删除成功 → USER_DELETED
```

`USER_DELETED` 是用户操作结果，不是已读、归档、来源移除或系统通知划除状态。

### 6.2 诊断上限执行

1. 新诊断事实先按生产事务规则提交；是否在同一事务或紧随其后的有界维护事件执行裁剪，由 `SP-09` 的正确性与写盘测量锁定。
2. 触发时读取已锁定规则；规则 `UNLOCKED` 则返回配置错误，不得临时选择数字。
3. 按 `retentionOrder ASC, eventId ASC` 计算合格诊断事实。
4. 删除最小数量的最旧事实，使所有已启用限制重新满足。
5. 清理结果必须对账长期条目前后数量相等；不相等立即失败并阻断版本。
6. 清理失败不允许通过删除长期条目“腾空间”，也不允许无界忙重试。

### 6.3 用户删除确认

1. 用户先明确选择一个或多个条目并请求预览。
2. 预览重新查询当前存在集合，显示数量、时间范围、来源汇总和关联数据说明。
3. 用户必须点击包含确切数量的确认动作；返回、手势关闭或进程重建均视为取消。
4. 确认时校验 `runtimeSessionId`、`previewId`、`selectionDigest` 及当前集合；任一不一致不删除。
5. 删除成功后移除当前进程相应运行时句柄并刷新列表；成功反馈只能使用事务返回数量。
6. 当前 MVP 的单条删除把当前可见条目作为仅有的选择集合；确认按钮固定为“删除 1 条记录”，并明确说明不可恢复、不改变后续监控以及来源再次发送或更新时可能重新出现。当前 schema 中的健康证据不随条目删除。

## 7. 权限与生命周期边界

- 存储占用查看、诊断清理和应用私有数据删除不请求广泛存储权限。
- 删除预览不跨 OMN 进程恢复；进程重建后用户必须重新选择和确认。
- 应用被系统终止时不能留下自动继续的删除任务；重新启动后以数据库已提交事实为准。
- 通知使用权、`POST_NOTIFICATIONS`、状态渠道和监听连接不影响既有条目保留，也不授权删除。
- 来源应用卸载、更新、stopped、内容删除或目标无处理程序均不触发长期条目清理。
- Android 低存储信号只能触发用户可见警告、缓存清理候选和写入错误处理；不得触发长期条目自动删除。
- 外部导出文件由用户选择的文档提供方管理；OMN 不扫描、轮询或删除这些文件。

## 8. Given / When / Then 验收条件

### 8.1 长期历史不按年龄自动删除

**Given** 一组条目跨越 `SP-09` 测试中的所有等待检查点
**When** 应用空闲、重启并执行诊断上限维护
**Then** 长期条目数量和身份不变，年龄不触发任何删除或跳转失效。

### 8.2 条目数量与数据库大小不触发自动删除

**Given** 数据库已包含 10,000 条历史且继续增长
**When** 超过任一诊断或缓存上限
**Then** 只清理对应有界类别，10,000 条长期历史及新增长期条目均不因容量静默删除。

### 8.3 排除与筛选不删除

**Given** 某应用已有历史条目
**When** 用户把它加入监控排除列表、仅查看其他应用或清空筛选
**Then** 既有条目与动作目标数量不变；排除只影响策略生效后的新通知。

### 8.4 诊断超限确定裁剪

**Given** 已锁定诊断上限，新增事实使至少一项限制超出
**When** 上限执行器运行
**Then** 按 `retentionOrder ASC, eventId ASC` 删除最小数量的最旧合格事实，所有限制恢复满足，长期条目计数前后相等。

### 8.5 未锁定上限不能宣称完成

**Given** `diagnosticRule.status = UNLOCKED`
**When** 候选版本运行上限测试
**Then** 测试失败并要求完成 `SP-09`，不得读取源码默认值或把无限增长标为通过。

### 8.6 用户取消删除

**Given** 删除预览显示 3 条记录及范围
**When** 用户返回或关闭确认界面
**Then** 输出 `CANCELED`，条目、目标、尝试摘要和运行时句柄均不改变。

### 8.7 明确删除所选条目

**Given** 当前会话预览确认 3 个仍存在条目，摘要与当前集合一致
**When** 用户点击“删除 3 条记录”
**Then** 原子删除这 3 个条目及其内容型关联数据，不删除其他条目、健康证据、监控策略、筛选或外部导出文件。

### 8.8 过时预览

**Given** 预览后选择集合改变、任一条目已不存在或 OMN 进程重建
**When** 旧确认请求到达
**Then** 输出 `STALE_PREVIEW` 或 `ITEM_SET_CHANGED`，不删除任何数据，并要求重新预览。

### 8.9 删除事务失败

**Given** 在删除事务提交前注入写入失败
**When** 用户确认删除
**Then** 输出 `FAILED_NO_CHANGE`，选中条目和关联目标全部仍可查询；不得显示已删除数量。

### 8.10 清诊断不影响健康真实性

**Given** 健康证据已派生蓝黄区间，且旧诊断事实达到上限
**When** 清理器裁剪诊断数据
**Then** 只按已锁定的健康保留边界操作；若不足以重建某段，界面变为 `UNCONFIRMED`，不得留下无证据蓝段。

### 8.11 缓存淘汰可重建

**Given** 图标缓存超过锁定字节上限
**When** 按缓存策略淘汰
**Then** 长期条目仍通过包名显示占位或重新加载图标，不丢正文、时间、来源或跳转目标。

### 8.12 存储不足

**Given** Android 拒绝新的数据库写入
**When** 一条通知到达
**Then** OMN 不删除旧条目换取成功，不增加“已记录”计数，显示该条可能未保存及受影响时间，并保留有界去敏故障事实。

### 8.13 存储占用口径

**Given** `SP-09` 已锁定测量方法与误差界限
**When** 用户打开存储页
**Then** 每个类别显示值、`EXACT/ESTIMATED/UNAVAILABLE`、测量时刻和口径；实际验证值落在锁定误差界限内，未知值不显示为 0。

### 8.14 并发通知与用户清理

**Given** 用户清理诊断或删除选中条目时有新通知到达
**When** 摄取与维护操作并发
**Then** 新通知按 A03/A08 正常提交，不被选择摘要误纳入删除；事务序列可对账且无漏记。

## 9. 错误状态

| `RetentionFailureReason` | 用户反馈 | 系统行为 |
|---|---|---|
| `LIMIT_NOT_LOCKED` | “诊断上限尚未由真机基线锁定。” | 阻止完成声明，不使用临时数字。 |
| `USAGE_MEASUREMENT_UNAVAILABLE` | 显示不可测类别和原因。 | 不显示 0 或伪精确值。 |
| `STORAGE_LOW` | 说明新通知可能未保存，提供存储页入口。 | 不自动删除长期条目，不无限重试。 |
| `STALE_DELETE_PREVIEW` | “记录范围已变化，请重新确认。” | 不删除。 |
| `DELETE_COMMIT_FAILED` | “删除未完成，现有记录保持不变。” | 回滚逻辑操作，保留原数据。 |
| `DIAGNOSTIC_TRIM_FAILED` | 说明诊断清理失败和当前上限状态。 | 不触碰长期条目；等待用户重试或下次真实维护事件。 |
| `CACHE_TRIM_FAILED` | 说明缓存清理失败。 | 不影响采集、条目或跳转。 |
| `UNKNOWN_RETENTION_FAILURE` | 提供去敏诊断入口。 | 无界重试禁止；长期条目保持。 |

## 10. 交互与无障碍

1. 存储页分开显示“通知记录”“诊断数据”“缓存”和“应用私有总量”，不得把有界诊断与长期历史混成一个数字。
2. 每项显示数量/字节、测量时刻、估算标识和保留说明；值不可用时显示原因。
3. “清理诊断数据”“清理缓存”和“删除所选通知”是三个独立动作，名称、结果和影响范围不得复用。
4. 删除确认按钮包含确切数量，例如“删除 3 条记录”；使用 Material 3 标准确认组件，取消为默认安全路径。
5. 删除是不可逆操作，确认页明确列出来源汇总、最早/最晚时间和关联数据影响，不显示“清理空间”模糊替代。
6. 控件至少 48dp；TalkBack 朗读数据类别、大小、估算状态、保留规则、选择数量和不可逆警告。
7. 最大字体、横竖屏、分屏、深浅色和减少动态效果下都能完成预览、取消和确认。

## 11. 隐私与性能约束

- 存储统计、诊断裁剪和删除全在本机进行，零网络、零遥测、零远程备份。
- 存储页不得把标题、正文、URI、内容 ID、动作、账号或本机路径写入日志；本机删除预览只显示完成确认所需的来源与时间范围。
- 清理器只由诊断提交越界或用户明确操作触发；无通知、页面关闭且无用户操作时不得产生周期扫描、数据库写入或额外唤醒。
- 10,000 条历史的存储统计、预览和删除不得一次加载全部正文或所有动作目标；按聚合查询、ID 批次或受控流处理。
- 批次大小、事务峰值、清理耗时、并发调度和测量误差由 `SP-09`/A14 在 release 红魔真机锁定；没有基线前不写绝对数字。
- 相对最近通过基线，CPU、唤醒、写盘或后台内存任一无解释回退超过 10% 阻断合并；新增周期工作、唤醒锁、精确闹钟或清理服务空转直接失败。

## 12. 测试要求

### 12.1 自动化测试

- 数据类别策略表测试证明长期条目只有 `USER_DELETE_ONLY`，诊断/缓存才有自动上限。
- 性质测试生成不同年龄、数量、动作状态和来源状态，证明这些变量不会自动删除长期条目。
- 诊断裁剪测试覆盖条数、时间、字节的单项/组合限制、相同顺序键、边界恰好等于上限及最小删除数。
- 关系不变量测试证明诊断/缓存清理前后长期条目和持久目标计数不变。
- 删除测试覆盖预览、取消、确认、集合变化、进程重建、事务失败、关联数据和无关数据保持。
- 并发测试覆盖新通知提交、用户删除和诊断裁剪的所有调度顺序，证明新条目不被旧预览误删。
- 存储占用方法测试使用固定文件/数据库夹具，结果满足 `SP-09` 锁定误差界限，`UNAVAILABLE` 不转为零。
- 敏感信息测试扫描日志、错误和统计结果，不含正文、标题、URI、内容 ID、动作或路径。

### 12.2 红魔 11 Pro+ 真机测试

- 使用 release 构建和 10,000 条历史验证无自动删除、占用展示、诊断上限、缓存淘汰和选中删除。
- 运行持续增长场景，确认诊断达到稳定上限而长期条目持续增长；记录数据库、WAL、缓存和 PSS 变化。
- 在诊断裁剪、缓存清理、存储统计和选中删除期间注入真实通知，逐条对账无漏记、误删或状态摘要领先。
- 模拟低存储/写入失败，确认旧历史不被自动删除且用户看到新记录风险。
- 8 小时息屏无通知且不打开存储页：不得出现清理轮询、周期写入、主动唤醒或网络。
- 重启、OMN 进程重建和来源应用卸载后，长期条目仍保持，旧删除预览不可继续使用。

## 13. Phase 0 Spike 与决策门

### 13.1 `SP-09 持久化、隐私与性能基线` 必须回答

1. 最小诊断事件、健康诊断、动作尝试、故障计数和缓存分别需要保留哪些事实？
2. 每类上限使用条数、时间、字节或组合中的哪一种，具体值和裁剪到何处才能同时满足排障价值与写盘预算？
3. 存储占用如何按通知、诊断、缓存和总量测量，误差界限和不可测情况是什么？
4. 上限执行放在提交事务内还是紧随其后的维护事件，哪种能保证 100 条突发不漏记且写盘更低？
5. 10,000 条历史、持续增长、用户删除和并发摄取的内存、事务、耗时与数据库增长预算是多少？
6. 去敏扫描能否证明诊断不含第二份正文、完整 URI、动作令牌、账号或本机路径？

### 13.2 证据产物

- 版本化的 `RetentionPolicySnapshot`，含所有单位、触发、排序、测量方法和误差界限；
- 8 小时无通知、100 条突发、10,000 条历史和持续增长的 release 原始数据；
- 诊断达到稳定上限、长期条目不自动删除的数量对账；
- 用户取消/确认/失败删除的原子性记录；
- 日志、数据库诊断样本和统计输出敏感字段扫描；
- 不锁定数据库 schema 或迁移的声明及后续用户授权入口。

### 13.3 决策门

- **GO**：诊断与缓存上限、存储测量口径和误差已锁定；长期条目只由用户明确确认删除；所有清理不级联；无周期后台工作；release 真机满足绝对预算与 10% 门。
- **REDIRECT**：诊断价值与资源成本无法用现有类别兼得，或存储分类不可按预期精度测量；先调整展示口径、诊断字段或触发方式并更新规格。
- **STOP**：控制资源只能依赖静默删除长期历史、周期唤醒/轮询，或用户删除无法保证范围原子性和隐私边界。

B02 只有在 `SP-09` 从 `UNLOCKED` 变为有证据的 `LOCKED` 策略，全部自动化/真机验收通过，且未锁定或实施未经授权的数据库 schema/迁移时，才可在 `v0.5` 标记完成。
