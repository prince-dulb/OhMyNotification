# A10 常驻状态通知规格说明

- **主交付版本**：`v0.3`
- **优先级**：`[A]`
- **规格状态**：`[候选] plan-v1.0`
- **Phase 0 依赖**：`SP-05 监听可靠性与红魔后台策略`、`SP-06 状态通知与前台服务 A/B`、`SP-07 健康证据与区间精度`、`SP-09 持久化、隐私与性能基线`
- **功能依赖**：A01 首次授权与全量监听、A03 通知事件采集、A08 本地持久化、A11 健康状态时间轴的当前健康摘要
- **被依赖**：A13 B 站端到端真机验收、A14 性能基线与回归门槛

## 1. 目标与范围

本功能在通知栏维护一条低打扰“运行状态”通知，让用户在应用外看到 OMN 最近一次可证明的监听状态、已提交逻辑条目数量和最近记录摘要。点击它进入收件箱或健康修复页。

`[已确认]` 状态通知的存在不是实时进程存活的充分证据。普通通知可能在发布进程终止后残留；`POST_NOTIFICATIONS` 被拒绝或渠道关闭时，即使某个后台组件仍在工作，通知也可能不出现在通知抽屉。通知使用权、`POST_NOTIFICATIONS`、渠道、监听连接和进程证据必须分开建模并在应用内显示。

`[待验证]` 状态通知由监听服务直接维护普通 ongoing 通知，还是由独立前台服务承载。两种实现都必须通过统一 `StatusPresenceDriver` 契约，Phase 0 完成平台合规与真机 A/B 后二选一；不得同时常驻两条状态通知。

### 1.1 本功能不做

- 不阻止或“拦截”原通知送达；用户文案使用“记录”“已救回”，不用“拦截”。
- 不把原始回调数当作已救回数量；只有新逻辑条目事务提交成功才增加累计数。
- 不为更新“2 分钟前”等相对文案启动计时器。
- 不在锁屏公开版本展示标题、正文、URI、内容 ID 或动作。
- 不因需要一条常驻通知就预设前台服务已经通过平台合规与资源门，也不伪报 `dataSync` 等无关 foreground service type。
- 不用状态通知替代 A11 的历史健康证据和蓝黄时间轴。

## 2. 术语与状态契约

### 2.1 五个独立事实

| 类型 | 值 | 与状态通知的关系 |
|---|---|---|
| `ListenerAccessState` | `GRANTED`、`NOT_GRANTED`、`UNKNOWN` | 决定系统是否授权监听；不能从状态通知存在反推。 |
| `StatusPermissionState` | `NOT_REQUESTED`、`GRANTED`、`DENIED`、`UNKNOWN` | 决定应用通知能否出现在通知抽屉；不决定监听是否连接。 |
| `StatusChannelState` | `NOT_CREATED`、`ENABLED`、`DISABLED`、`UNKNOWN` | 只描述固定“运行状态”渠道。 |
| `ListenerConnectionState` | `NEVER_OBSERVED`、`CONNECTED`、`DISCONNECTED` | 只由当前会话真实监听回调更新。 |
| `ProcessEvidenceState` | `CURRENT_SESSION_ACTIVE`、`NO_CURRENT_SESSION_EVIDENCE` | 当前运行代码或历史查询证据；不能代替监听连接。 |

### 2.2 状态通知专用类型

| 类型 | 值 | 精确定义 |
|---|---|---|
| `StatusPresenceMode` | `ORDINARY_ONGOING` | 监听服务通过 `NotificationManager` 维护一条普通 ongoing 通知。 |
|  | `FOREGROUND_SERVICE` | 经 Phase 0 证明合法且必要的独立前台服务承载同一通知；服务内部无循环。 |
| `StatusPresentationState` | `LISTENING` | 使用权为 `GRANTED`，当前会话监听为 `CONNECTED`。 |
|  | `WAITING_FOR_CONNECTION` | 已授权但当前会话没有连接事实。 |
|  | `LISTENER_INTERRUPTED` | 使用权仍授予但当前会话已断连。 |
|  | `ACCESS_REQUIRED` | 通知使用权未授予或已撤销。 |
|  | `STATE_UNKNOWN` | 权限或连接状态无法可靠读取。 |
| `StatusVisibilityState` | `VISIBLE` | 权限已授予、渠道启用且系统发布调用成功；只说明通知可见条件成立。 |
|  | `PERMISSION_REQUIRED` | `POST_NOTIFICATIONS` 未请求或被拒绝。 |
|  | `CHANNEL_DISABLED` | 固定渠道已被关闭。 |
|  | `VISIBILITY_UNKNOWN` | 权限/渠道读取失败或发布结果不可判定。 |
|  | `POST_FAILED` | 权限与渠道表面可用，但发布调用失败。 |
| `StableStatusNotificationKey` | `{ tag: String, id: Int }` | 安装内固定的通知标识；具体常量在单一配置处定义，升级不得另建第二条状态通知。 |
| `StatusDestination` | `INBOX`、`HEALTH_DETAILS(HealthFacet)` | 状态卡点击后的唯一允许目标。 |
| `StatusPublishFailure` | `PERMISSION_DENIED`、`CHANNEL_DISABLED`、`SYSTEM_REJECTED`、`UNKNOWN_FAILURE` | 不含系统通知正文或动作的发布失败分类。 |

`StatusPresentationState` 与 `StatusVisibilityState` 是正交状态。例如监听可为 `LISTENING`，同时状态通知可为 `PERMISSION_REQUIRED`。

## 3. 用户故事

> 作为经常误划通知的用户，我想在通知栏保留一条安静的 OMN 状态卡，看到应用最近是否有可证明的监听连接、累计救回多少逻辑通知以及最近来自哪个应用，以便不用打开应用也能发现活动或异常。

> 作为关心隐私的用户，我想让锁屏上的状态卡只显示来源应用，不显示原通知标题和正文，以免旁人看到通知内容。

> 作为需要排障的用户，我想点击异常状态卡直接进入对应健康页，以便分别处理通知使用权、状态通知权限、渠道或监听连接问题。

| 字段 | 逻辑类型 | 必填 | 来源 | 约束 |

| `listenerConnectionState` | `ListenerConnectionState` | 是 | 当前会话监听事实 | 只接受真实回调更新。 |
| `processEvidenceState` | `ProcessEvidenceState` | 是 | 当前会话状态 | 仅用于说明证据，不决定历史蓝区间。 |

### 4.2 `CommittedItemSummary`

| 字段 | 逻辑类型 | 必填 | 说明 |
|---|---|---:|---|
| `itemId` | `ItemId` | 是 | 已提交逻辑条目标识。 |
| `sourcePackage` | `PackageName` | 是 | 用于来源和自包名防递归检查。 |
| `sourceLabel` | `String?` | 否 | 优先展示的应用名称；为空时回退到包名。 |
| `title` | `String?` | 否 | 只可进入解锁私有版本；空时省略。 |
| `firstReceivedAt` | `InstantUtc` | 是 | 状态通知的事件时间来源；更新不改变。 |
| `changeKind` | `ItemChangeKind` | 是 | `CREATED`、`UPDATED`、`REMOVED`、`NO_CONTENT_CHANGE`。只有 `CREATED` 增加累计数。 |

### 4.3 `StatusUpdateTrigger`

允许值只有：

- `PROCESS_SESSION_STARTED`
- `LISTENER_STATE_CHANGED`
- `LISTENER_ACCESS_CHANGED`
- `STATUS_PERMISSION_CHANGED`
- `STATUS_CHANNEL_CHANGED`
- `COMMITTED_ITEM_CHANGED`
- `USER_REQUESTED_REFRESH`

不存在 `CLOCK_TICK`、`PERIODIC_HEARTBEAT` 或后台轮询触发器。

## 6. 状态机与业务规则

### 6.1 内容状态判定

按以下优先级计算 `StatusPresentationState`：

1. `listenerAccessState=UNKNOWN` 时为 `STATE_UNKNOWN`。
2. `listenerAccessState=NOT_GRANTED` 时为 `ACCESS_REQUIRED`。
3. 使用权为 `GRANTED` 且连接为 `NEVER_OBSERVED` 时为 `WAITING_FOR_CONNECTION`。
4. 使用权为 `GRANTED` 且连接为 `DISCONNECTED` 时为 `LISTENER_INTERRUPTED`。
5. 使用权为 `GRANTED` 且连接为 `CONNECTED` 时为 `LISTENING`。

`processEvidenceState` 只补充“当前会话/最近确认”说明，不得把 `NEVER_OBSERVED` 或 `DISCONNECTED` 提升为 `LISTENING`。

### 6.2 文案规则

| 状态 | 私有标题 | 私有正文规则 | 点击目标 |
|---|---|---|---|
| `LISTENING` 且有记录 | `正在抢救通知` | `已救回 {committedItemCount} 条 · 最近：{sourceLabelOrPackage} · {title}`；标题为空时省略最后一段。 | `INBOX` |
| `LISTENING` 且无记录 | `正在抢救通知` | `监听已连接 · 尚无记录` | `INBOX` |
| `WAITING_FOR_CONNECTION` | `等待系统连接监听` | 有 `lastPositiveEvidenceAt` 时显示最后确认时间；没有则显示“尚无连接证据”。 | `HEALTH_DETAILS(LISTENER)` |
| `LISTENER_INTERRUPTED` | `救援中断，点此检查` | 显示最后确认时间，不声称断连期间的漏记数量。 | `HEALTH_DETAILS(LISTENER)` |
| `ACCESS_REQUIRED` | `需要通知使用权` | `点此前往系统设置` | `HEALTH_DETAILS(LISTENER_ACCESS)` |
| `STATE_UNKNOWN` | `无法确认监听状态` | `点此检查权限与连接` | `HEALTH_DETAILS(LISTENER)` |

公开锁屏版本的正文规则：

- 有最近记录时只显示 `最近来源：{sourceLabelOrPackage}`；
- 无最近记录时只显示监听状态；
- 永不包含 `{title}`、正文、URI、内容 ID 或动作状态。

文案不得内嵌会随墙上时间自动变旧的“2 分钟前”。`eventTime` 交给 Android 系统呈现；应用只在真实触发器到来时重建文案。

### 6.3 可见性状态机

```text
渠道尚未创建 ──> 幂等创建 running_status
        ├─ POST_NOTIFICATIONS 未允许 ──> PERMISSION_REQUIRED
        ├─ 渠道关闭 ──────────────────> CHANNEL_DISABLED
        ├─ 状态读取失败 ──────────────> VISIBILITY_UNKNOWN
        └─ 权限允许 + 渠道启用
                    ├─ 发布成功 ──────> VISIBLE
                    └─ 发布失败 ──────> POST_FAILED
```

规则：

1. 渠道名称为“运行状态”，重要性使用低打扰级别；创建时关闭声音和震动。用户修改后不删除重建、不偷偷换 ID。
2. `POST_NOTIFICATIONS` 被拒绝或渠道关闭时，应用内分别展示修复入口。核心监听仍按 A01 独立运行。
3. `VISIBLE` 只表示发布条件成立，不表示应用未来持续运行，也不把历史时间轴涂蓝。
4. 若普通通知在进程终止后残留，它的旧文案不得被解释为实时事实；Phase 0 必须决定是否显示最近确认时间、采用合规 FGS，或降低应用外承诺。
5. 如果 FGS 在权限拒绝时仍被系统允许启动，也不能把抽屉中不可见的状态卡记为 A10 已满足。

### 6.4 更新、去重与突发合并

1. 只有已提交 `ItemChange` 可更新“已救回”和最近记录；写入失败或仅在队列中的快照不得显示成功。
2. `CREATED` 更新累计逻辑条目数；`UPDATED` 只更新该条摘要，不增加数量；`REMOVED` 不减少长期条目数；`NO_CONTENT_CHANGE` 不触发摘要刷新。
3. 相同 `StatusNotificationModel` 不调用系统更新。
4. 短时间多个触发器进入一个进程内合并窗口，窗口结束后发布最新已提交模型。合并窗口时长、最大等待时长和 100 条突发下最大刷新数由 Phase 0 锁定。
5. 合并窗口不用系统周期任务、精确闹钟或 `WorkManager`。进程在窗口内终止时，数据库事实仍正确；下次自然启动、监听连接或真实事件重建状态卡。
6. 状态通知自身在 A01/A02 热路径以 OMN 包名自动排除，不能进入累计数或最近记录。

### 6.5 `StatusPresenceDriver` 二选一契约

| 要求 | `ORDINARY_ONGOING` | `FOREGROUND_SERVICE` |
|---|---|---|
| 通知数量 | 仅一条固定状态通知 | 仅一条前台服务状态通知 |
| 触发 | 监听/提交/权限/渠道真实变化 | 同左；服务自身不得产生 timer tick |
| 空闲工作 | 无循环、无轮询 | 无循环、无轮询、无空任务 |
| 健康语义 | 可能残留，必须显示最近确认或降低承诺 | 只能表达前台服务会话，仍不能代替通知使用权和监听连接 |
| 合规门 | Android 普通通知规则 | 必须确认真实 foreground service type、启动限制和未来分发约束 |

两种模式都满足正确性时，若一种模式在全部已锁定资源指标上不高于另一种、且至少一项更低，则选择该模式；若指标互有胜负，列出逐项差值并由用户决定。若只有 FGS 满足产品语义，必须先证明服务类型合法；若两者都无法诚实满足，则输出 `REDIRECT`，不伪造“通知存在即监听正常”。

## 7. 权限与生命周期边界

- **通知使用权撤销**：若进程能观察到，立即生成 `ACCESS_REQUIRED` 模型；若进程已终止，无法更新残留通知的时间点属于未确认区间。
- **`POST_NOTIFICATIONS` 拒绝**：不再反复发起权限弹窗；应用内显示设置入口。监听服务是否连接单独判断。
- **渠道关闭**：发布驱动返回 `CHANNEL_DISABLED`；不得删除重建渠道规避用户选择。
- **监听断连/重连**：断连后下一次真实触发更新为异常；重连后更新为 `LISTENING`。不运行连接轮询。
- **进程重建**：新会话不能沿用旧连接内存态。重建已提交计数和最新条目后，等待新连接事实再显示 `LISTENING`。
- **手机重启**：状态通知何时重建、由何种平台入口触发，以 Phase 0 真机证据锁定；不承诺在系统尚未启动 OMN 前通知已经存在。
- **强制停止**：用户/系统使 OMN stopped 后的通知、组件启动和恢复行为必须真机记录；不得用普通重启结果代替。
- **并发更新**：按 `modelRevision` 只允许新模型覆盖旧模型；较早异步发布完成不得回写覆盖较新结果。

## 8. Given / When / Then 验收条件

1. **正常首次发布**<br>
   Given 通知使用权已授予、监听已连接、通知权限已授予且渠道启用，When 驱动收到当前健康摘要，Then 只发布一条静音 ongoing 状态通知，标题为“正在抢救通知”。

2. **提交后才计数**<br>
   Given 新通知快照尚未提交，When 状态摘要被请求，Then 累计数和最近记录不包含该快照；When 事务成功并产生 `CREATED`，Then 才增加一条。

3. **更新不重复计数**<br>
   Given 逻辑条目已存在，When 同一通知产生 `UPDATED`，Then 累计逻辑条目数不变，状态通知仍使用同一固定 key。

4. **写入失败不伪装成功**<br>
   Given 通知事务失败，When 状态控制器收到失败结果，Then 不增加“已救回”数量，异常详情在应用内可见。

5. **通知权限独立**<br>
   Given 监听为 `CONNECTED`、`POST_NOTIFICATIONS=DENIED`，When 计算状态，Then 内容状态为 `LISTENING`、可见性为 `PERMISSION_REQUIRED`，应用内提示权限问题。

6. **渠道独立**<br>
   Given 权限允许但渠道关闭，When 尝试更新，Then 返回 `CHANNEL_DISABLED`，不把监听改为断开且不新建替代渠道。

7. **锁屏脱敏**<br>
   Given 最近记录含来源、标题和正文，When 系统显示公开锁屏版本，Then 只出现 OMN 状态和来源应用，标题、正文和目标不可见。

8. **断连文案**<br>
   Given 使用权仍授予，When 当前连接收到断连事实，Then 状态卡更新为“救援中断，点此检查”，并跳转监听健康详情。

9. **无相对时间轮询**<br>
   Given 状态卡已发布且没有新通知或状态变化，When 设备息屏 8 小时，Then OMN 不为刷新相对时间产生通知更新、唤醒或写盘。

10. **突发合并**<br>
    Given 版本化数据集交付 100 条突发回调，When 所有事务完成，Then 最终状态卡与最新已提交事实一致，刷新数不超过 Phase 0 锁定预算且不逐回调刷新。

11. **普通通知残留**<br>
    Given 使用 `ORDINARY_ONGOING`，When OMN 进程被系统终止而通知仍残留，Then 测试报告将其标为旧状态而非实时存活证明，UI 历史区间不因此涂蓝。

12. **FGS 约束**<br>
    Given Phase 0 未证明合法服务类型，When 构建 `v0.3`，Then 不启用 `FOREGROUND_SERVICE`；不得以无关类型绕过平台要求。

## 9. 错误状态

| 错误 | 触发条件 | 用户看到什么 | 系统做什么 |
|---|---|---|---|
| `STATUS_PERMISSION_REQUIRED` | 未请求或拒绝通知权限 | 应用内“运行状态通知不可见”及设置入口 | 不影响监听；不循环请求。 |
| `STATUS_CHANNEL_DISABLED` | 渠道关闭 | 应用内“运行状态渠道已关闭”及渠道入口 | 不删除重建渠道。 |
| `STATUS_POST_REJECTED` | 系统发布调用失败 | 应用内“状态通知发布失败”及错误时间 | 记录无正文错误枚举；等待用户刷新或真实状态变化重试。 |
| `STATUS_MODEL_LOAD_FAILED` | 已提交计数/最新条目读取失败 | 状态卡只显示健康状态，不显示虚假计数 | 不使用缓存草稿冒充数据库事实。 |
| `LISTENER_STATE_UNKNOWN` | 权限或连接不可判定 | “无法确认监听状态” | 不显示“正在抢救通知”。 |
| `FGS_START_REJECTED` | 前台服务启动受平台限制 | 应用内显示平台拒绝与恢复入口 | 停止重复启动；不退回伪报服务类型。 |
| `FGS_TYPE_INVALID` | 无合法真实用途类型 | 不启用 FGS；开发报告阻断 | 回到普通通知或 `REDIRECT` 决策。 |
| `DESTINATION_UNAVAILABLE` | 点击目标无法打开 | “无法打开健康详情/收件箱” | 不崩溃；记录错误枚举。 |

错误重试只能由用户动作、真实监听/权限/渠道变化、下一次已提交条目或平台合法生命周期触发；禁止短周期后台重试。

## 10. 交互流程

```text
监听/权限/渠道/提交事实变化
  → 读取五个独立维度与已提交摘要
  → 生成私有 + 公开 StatusNotificationModel
  → 与上次模型比较
      ├─ 相同：不调用系统
      └─ 不同：进入进程内突发合并窗口
                  → StatusPresenceDriver 发布同一固定通知
                  → 记录发布结果

用户点击状态卡
  ├─ 正常监听 → 收件箱
  └─ 权限/连接异常 → 对应健康详情与系统设置入口
```

状态卡本身由 Android 系统呈现；进入应用后的修复控件遵循 Material 3、edge-to-edge、至少 48dp 触控范围和 TalkBack 语义。异常不能只用颜色或图标表达。

## 11. 隐私与性能约束

- 私有版本最多包含来源应用和标题，永不包含完整正文；公开版本不含标题。
- 状态模型、错误日志和性能报告不得记录真实标题、正文、完整 URI、内容 ID、`PendingIntent` 或动作令牌。
- 本功能不得联网，不接入遥测或远程心跳。
- 不使用轮询、唤醒锁、精确闹钟、高频 WorkManager 或前台服务空转。
- 状态更新只由第 4.3 节触发器产生；相同模型不重复发布，突发必须合并。
- `StatusPresenceDriver` 的两种模式使用相同 release 构建工作负载 A/B；A10 不自行编造 PSS、CPU、耗电或刷新次数预算。
- 8 小时无通知与 100 条突发的绝对预算由 Phase 0 按 A14/非功能需求锁定；基线建立后超过 10% 的回归阻断合并。

## 12. 测试要求

### 12.1 自动化测试

- 五个独立事实到 `StatusPresentationState`/`StatusVisibilityState` 的全组合判定。
- 私有/公开文案字段白名单测试，确保锁屏模型无标题、正文或动作。
- `CREATED`、`UPDATED`、`REMOVED`、失败事务的计数不变量。
- 相同模型不发布、较旧 revision 不覆盖新 revision、突发窗口最终模型一致。
- 固定通知 key 与固定渠道 ID，用户关闭渠道后不创建替代 ID。
- 自包名状态通知不进入逻辑条目和累计数。
- 无 timer trigger 的架构检查；合并调度结束后无待运行周期任务。
- 点击正常/异常状态分别导航到收件箱/正确健康 facet。
- Compose 健康修复入口的语义、48dp、最大字体和深浅色测试。

### 12.2 红魔 11 Pro+ 真机测试

- 普通 ongoing 与 FGS 候选拓扑的显示、残留、进程重要性、重启恢复和强制停止行为。
- 通知使用权、`POST_NOTIFICATIONS`、渠道和监听连接逐项切换，确认互不误判。
- 锁屏/解锁实际内容检查；系统通知历史和厂商通知管理行为记录。
- 100 条突发时记录回调、事务和状态通知刷新数。

- release 构建，不以 debug 或模拟器结果锁定承载方式。

## 13. Phase 0 Spike 与决策门

### 13.1 `SP-06 状态通知与前台服务 A/B` 必须回答

1. 普通 ongoing 状态通知在监听正常、进程终止、系统回收、强制停止和重启后分别何时存在或残留？
2. 独立 FGS 是否有与真实用途匹配的合法 foreground service type，Android 16 和未来侧载/分发边界是什么？
3. `POST_NOTIFICATIONS` 被拒绝或渠道关闭时，两种拓扑的后台行为和用户可见性如何？
4. 两种拓扑对漏记、后台 PSS、CPU、唤醒、写盘和耗电的差异是什么？
5. 突发合并窗口、最大等待时长和 100 条场景最大刷新数应锁定为何值？

### 13.2 证据产物

- 两种拓扑同设备、同 release 构建、同权限和同工作负载 A/B 报告；
- 通知残留与真实监听/进程状态对照时间线；
- FGS 类型、清单声明、启动限制和官方规则核对记录；
- 权限/渠道/锁屏矩阵；
- 8 小时息屏和 100 条突发的原始指标与候选预算。

### 13.3 决策门

- **GO / `ORDINARY_ONGOING`**：普通通知能以明确“最近确认”语义满足应用外状态需求，正确性通过且资源占用更低。
- **GO / `FOREGROUND_SERVICE`**：FGS 有合法真实类型；普通模式在通知残留、重启恢复或状态语义中至少一项验收失败而 FGS 全部通过，或两者都通过后用户依据逐项 A/B 数据选择 FGS；FGS 同时满足全部锁定资源预算。
- **REDIRECT**：通知存在无法可靠表达运行状态，或权限/渠道限制要求降低“通知存在即运行”的产品承诺；先回写计划并由用户确认。
- **STOP**：所有候选方案都依赖不合规服务类型或高频后台活动，或在正确性通过后仍至少违反一项用户已确认的绝对资源预算。

A10 只有在一种模式通过上述决策门、绝对预算写入非功能需求且 10% 回归门可执行后，才可在 `v0.3` 标记完成。
