# 详细开发计划变更记录

本文件记录计划事实、范围和决策的变化。实现提交、测试 run 和发布说明应引用相应版本文档，不在这里伪造为计划进度。

## 2026-08-29：`0.1.9-mvp` 显式逐条删除通知记录

- 每条已记录通知的内容底部增加可见的“删除记录”动作，不依赖长按或隐藏滑动，也不把逐条“更多”菜单放回通知内容。
- 删除前显示 Material 3 确认框，明确“删除 1 条记录”、不可恢复、不改变来源监控，以及来源再次发送或更新时记录可能重新出现。
- 删除事务按 `itemId` 精确删除一个通知事实，成功后移除对应当前进程动作句柄，并重算常驻状态通知的记录数量和最新摘要。健康证据继续保留，避免用户整理记录时改写蓝黄运行时间轴；排除策略和查看筛选不受影响。
- Room schema 保持 v1。21 个 JVM 测试套件共 92 项、129 任务无设备总门和全部 APK/测试数据/敏感扫描通过；删除隔离的 Room instrumentation 测试已编译，未对真实日用数据库运行破坏性设备测试。
- `0.1.9-mvp` 已覆盖安装红魔真机，387 条通知记录、350 个移除事实和 22 个监控排除来源均保留，监听与常驻状态通知正常。真机 UI 确认首屏逐条删除入口、确认框、取消与进程存活；本轮未代替用户确认删除任何真实通知。

## 2026-08-29：`0.1.8-mvp` 归档条目按需尝试恢复动作

- “无法跳转的归档”改称“当前无跳转动作归档”，避免把一次进程内没有动作误写成永久无法跳转；归档仍是当前运行时能力的动态视图，不移动或删除通知记录。
- 用户点按归档条目时，监听服务只查询一次系统当前活动通知，并按原有身份、生命周期与 `itemId` 规则处理；若为同一条记录重新取得动作，则从仍可见的 Activity 立即尝试派发。
- 重扫有 2.5 秒上限，不启动轮询、持续重绑或后台重试，也不按标题、正文、来源包猜测目标；没有找到时显示明确失败，不打开来源首页。
- Room schema、通知事实、排序、筛选和采集策略未变。21 个 JVM 测试套件共 92 项、129 任务无设备总门与全部 APK/测试数据/敏感扫描通过；`0.1.8-mvp` 已覆盖安装红魔真机，387 条通知记录、350 个移除事实和 22 个监控排除来源保留，监听与常驻状态通知正常，重复身份/代次组为 0。安装检查时设备处于锁屏通知层，因此归档点击的真机界面与实际落页仍由后续解锁日用验证。

## 2026-08-29：`0.1.7-mvp` 来源抽屉操作与查看排除

- 来源级“更多”菜单从每条通知移到应用抽屉标题行的展开/收起控件旁；单条来源也使用相同标题结构，通知内容区不再重复 App 管理入口。
- 菜单保留“不要再记录/重新记录这个 App”，新增“仅查看此 App”和“不查看此 App”。前者继续控制未来采集，后两项只控制当前查看范围。
- “不查看此 App”使用独立私有偏好黑名单，并在 Room/Paging 查询层按 `AppUserKey` 排除；在查看全部状态下不会把当前已知的其他来源固定成白名单，因此未来新来源仍会正常出现。
- 查看白名单与黑名单互斥并原子保存；顶部筛选入口分别显示查看数量或隐藏数量。Room schema、通知事实、动作、排序与采集热路径未改变。
- 21 个 JVM 测试套件共 91 项、129 任务无设备总门、APK 边界、可安装性、测试数据与敏感扫描通过；`0.1.7-mvp` 已覆盖安装红魔真机，360 条通知记录和 22 个监控排除来源保留，监听及常驻状态通知正常。真机归档页确认来源菜单包含三个动作，且通知级“更多”入口已经清零。

## 2026-08-27：`0.1.6-mvp` 可尝试跳转收件箱与失效归档

- 默认收件箱只显示当前进程仍持有原通知动作的条目；动作按钮改为“尝试打开原内容”，避免把 `PendingIntent.send()` 被系统接受写成已经精确落页。
- 没有原通知动作、进程重建后未从活动通知恢复动作，或尝试时得到明确取消/系统拒绝结果的长期条目进入“无法跳转的归档”；设置页提供归档数量与入口，归档继续支持来源筛选、稳定排序、时间抽屉和分页。
- 归档视图由当前运行时动作 ID 集合动态派生，不写入通知事实、不删除历史、不修改 Room schema。监听补扫重新取得动作时，条目自动回到默认收件箱。
- 既有 B 站样本没有可持久 URI 或内容 ID，因此本版不伪造跳转链接，也移除逐条“仅打开来源应用”降级控件。
- 21 个 JVM 测试套件共 89 项、129 任务无设备总门及全部 APK/测试数据/敏感扫描通过；`0.1.6-mvp` 已覆盖安装红魔真机。305 条历史与 16 个排除来源保留，当前 26 条有运行时动作、279 条进入无法跳转归档；默认收件箱、设置入口与归档页完成即时真机检查，监听和常驻状态通知正常。

## 2026-08-27：`0.1.5-mvp` 统一设置与通知类型过滤

- 收件箱顶部原“不监控”入口改为“设置”；设置页集中管理通知类型、跨应用合并时间间隔和不监控应用，每条历史通知的快速排除入口继续保留。
- 采集入口根据 Android 通知类别、媒体会话标记和 ongoing 标记派生五类通知；媒体播放控件默认关闭，消息与通话、闹钟/提醒/导航、持续运行/进度和其他通知默认开启。设置只影响之后交付的回调，已有记录不删除。
- 跨应用合并时间间隔可选 5、15、30 分钟以及 1、2、6、12、24 小时，默认 15 分钟；当前可见流中未被其他应用打断的连续同源通知仍不受时间跨度限制。
- 类型策略与时间窗保存在应用私有偏好中；监听热路径只读取原子内存快照，不查询 Room 或 PackageManager。Room schema、通知身份、排序键与既有历史保持不变。
- 21 个 JVM 测试套件共 88 项、129 任务无设备总门、APK 边界、可安装性、测试数据与敏感扫描通过；`0.1.5-mvp` 已覆盖安装红魔真机，既有 305 条记录和 16 个排除来源保留，设置页、八档时间窗与排除管理弹窗完成即时真机检查。真实媒体通知是否持续被正确过滤仍由后续日用通知验证。

## 2026-08-25：`0.1.4-mvp` 连续同源跨时间分组与默认展开

- 当前可见流中连续的同一 App 通知不再受 15 分钟窗口限制；只要中间没有其他可见通知，即使相隔数天也进入同一抽屉。跨过其他 App 后仍使用 15 分钟、最多跨 3 条的规则。
- 查看筛选先于分组，因此被筛选隐藏的来源不算中间通知；单 App 筛选下连续历史使用同一规则。
- 抽屉改为默认展开，用户仍可手动收起；展开/收起继续只属于当前 UI 状态，不写入通知事实。
- 为避免单 App 长抽屉在首屏连续预取历史，分页只在用户真正滚到当前已加载内容底部附近时请求下一页。
- 分组策略标识从 `ANCHOR_V1` 升为 `ANCHOR_V2`；Room schema、通知排序键和采集规则均未改变。

## 2026-08-24：`0.1.3-mvp` 从通知直接管理来源监控

- 原“不监控”入口要求用户在超长应用目录里定位来源，不适合从一条具体噪声通知立即采取动作。
- 每条既有通知现在提供标准“更多”菜单，可直接选择“不再记录这个 App”；确认框明确排除只影响未来通知、已有记录保留，并说明当前 schema v1 对同包所有资料生效。
- 已排除来源可从同一历史通知选择“重新记录这个 App”；恢复只影响生效点后的新通知，排除期间未保存的通知不会补回。
- 红魔 11 Pro+ 真机用合成来源验证排除、排除后新通知不入库、历史保留、恢复监控和测试策略回滚；未修改 Room schema，也未删除任何通知记录。

## 2026-08-23：`0.1.2-mvp` 手动监听重连修复

- 原实现让自动重连与用户点击共用 10 秒冷却；自动流程刚尝试过时，用户入口会被应用自身拒绝，且短暂 Snackbar 无法持续说明请求结果。
- `0.1.2-mvp` 为用户请求设置独立的 1 秒防连点，不受自动冷却和自动次数上限影响；断连界面持续显示结果，并提供通知使用权设置兜底入口。
- JVM 测试覆盖自动与用户请求的交互边界；红魔 11 Pro+ 在自动次数已满后受控断连，从页面点击产生 `USER / REQUESTED` 并在 1 秒内恢复监听。该结果不外推为所有 ROM 异常都必然接受 `requestRebind()`。

## 2026-08-23：`0.1.1-mvp` 来源弹窗崩溃修复

- `0.1.0-mvp` 的“查看”和“不监控”弹窗共用 `LazyColumn`，曾把 `AppUserKey` 直接作为 item key；Compose 的 Android 保存状态只接受可写入 `Bundle` 的 key 类型，因此两个入口都会在列表组合时崩溃。
- `0.1.1-mvp` 改为无歧义字符串 key，保留 Android 用户与包名的复合身份，并加入唯一性回归测试。
- 红魔 11 Pro+ 覆盖安装后，两个弹窗均已实际打开和关闭，进程、监听、常驻状态通知及既有数据保持正常；修复后的测试窗口没有新增系统崩溃记录。

## 2026-08-23：首个日用 MVP 收口口径

- 用户明确首版只要求最基础、最核心的功能，允许 bug 与新增需求在真实日用中继续提出和修复。
- 首个侧载 MVP 的发机门改为：目标手机能全量采集未排除通知、查看稳定历史、在原通知划除后从当前进程动作回到原内容、使用来源筛选/排除，并看到常驻状态与基本健康提示。
- 投稿/动态/开播逐类、进程重建或手机重启后的精确跳转、工作资料、长待机、release 签名和完整性能预算仍保留为后续验证项，不因提前发机而写成已支持。
- 该变化只降低首次个人侧载的收口门槛，不授权公开 release、GitHub push、签名材料或数据库 schema 变更。
- 首个侧载版本使用 `0.1.0-mvp` / `versionCode=2`。完整无设备构建门与 APK 校验通过后已覆盖安装到目标红魔；既有 49 个逻辑条目保持，监听自动重绑成功，常驻状态通知可见。

## 2026-08-23：Phase 0 工程与测试基础设施

- P0-001—P0-003 建立并验证 Android 16 原生 Kotlin、Compose、Material 3 单模块工程及固定 Wrapper。
- P0-004 建立版本化合成数据、JVM 夹具契约、独立 instrumentation 测试 APK、受控通知源、APK 隔离扫描和可安装 Debug APK 检查。
- 非 ASCII 工作区能完成编译与打包，但 Gradle Test Executor 实测会破坏测试类路径；用户将工作区改为 ASCII 名称后，标准 JVM 测试恢复通过。项目不再使用 `android.overridePathCheck`。
- P0-004 无设备总门通过；Android 测试 APK 的设备运行保持 `NOT_RUN`，不外推为红魔可靠性结论。
- 生产 APK 仍是 Phase 0 可安装验证壳，没有通知监听、Room schema、常驻状态通知或产品时间轴。

## `plan-v1.0`（2026-08-22，已确认）

### 新增

- 为 A01—A14、B01—B03 建立 17 份独立功能规格。
- 建立 Phase 0 到 `v0.5` 的版本路线图，全部功能各有唯一主交付版本。
- 建立单 `:app` 候选架构、通知摄取/归并/持久化链路、动作双轨、健康证据与确定性时间抽屉模型。
- 建立可测量的非功能需求、T0—T6 测试策略、九个 Spike 协议和分阶段任务表。
- B03 采用“两阶段导出”：先在应用私有空间生成并通过字段白名单/敏感扫描，再请求用户选择外部保存位置。
- A02 增加来源目录覆盖度模型，明确 Android 包可见性限制不得伪装成完整列表。

### 对齐

- 跳转不设置记录年龄 TTL；运行时 `PendingIntent` 不持久化，持久精确目标与应用入口降级严格区分。
- 默认顺序锁定为 `firstReceivedAt DESC, ingestSequence DESC, itemId DESC`。
- 时间抽屉锁定为 15 分钟、最多跨 3 条其他来源、最少 2 条、锚点式非重叠算法。
- 通知使用权、`POST_NOTIFICATIONS`、状态渠道、监听连接和进程证据保持五维独立。
- 蓝色只表示有正面监听证据的 `CONFIRMED_RUNNING`，黄色表示 `UNCONFIRMED`，不虚构停机时刻。
- 常驻状态通知只消费已提交事实；普通 ongoing 与 FGS 在 Phase 0 A/B 后二选一。
- 低资源门覆盖 8 小时息屏、100 条突发、10,000 条历史、数据库增长和 10% 回归。
- v0 长期通知条目不自动删除；诊断与缓存有界值待 Phase 0 锁定。

### 当前状态

- 用户于 2026-08-22 确认进入 Phase 0，G0 已通过。
- 本节描述的是 `plan-v1.0` 标签创建时的历史快照；Android 工程和本地依赖已在后续 Phase 0 提交建立，生产数据库 schema、远端仓库、CI 和公开 release 仍未创建。
- 本版本作为本地 `main` 的 `plan-v1.0` 标签基线；标签不包含远端授权。

# 2026-09-05：`v1.0.0` 产品范围确认

- 用户根据当前版本的红魔真机日用结果，确认其功能和交互已经足以作为 v1 发布；`v1.0.0` 不再追加功能。
- 源码已升级为 `1.0.0` / `versionCode=12`；正式签名 APK 已生成但尚未公开。
- 发布工程采用独立正式签名，不公开 Android Debug 签名包。为保留目标手机中的真实通知记录，已经通过 APK Signature Scheme v3 建立旧 Debug 证书到新正式证书的签名谱系：旧证书只保留 installed-data 迁移能力且关闭 rollback，并已在 Android 16 真机完成覆盖安装验证。
