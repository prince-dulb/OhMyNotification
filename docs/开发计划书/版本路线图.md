# 救救我的通知！版本路线图

状态：`计划草案`

计划版本：`plan-v1.0`

编制日期：2026-08-17（Asia/Shanghai）

本文把 `docs/项目计划书.md` 中的 14 个 `[A]` 功能和 3 个 `[B]` 功能分配到可验收版本。它只定义交付顺序和版本关卡，不替代各功能规格、架构设计、测试策略或真机验证报告。

## 1. 路线图原则

1. **Phase 0 先于产品版本。** 所有会影响项目成立与否的 Android 行为先作为 Spike 获取真机证据。Phase 0 未形成 `GO` 结论时，不进入 `v0.1`，更不能把推测写成已支持能力。
2. **`v0.1` 是最小端到端闭环，不是日用 MVP。** 它只证明“授权监听 → 收到通知 → 归一化并持久化 → 原系统通知被划除 → 在应用内找到记录 → 回到原内容”这一条纵向链路。去重、稳定排序、抽屉、健康时间轴等能力在后续版本完成。
3. **每个产品版本最多主交付 5 个 `[A]` 功能。** 一个功能只指定一个主交付版本；后续版本必须持续回归，不得以“已在早期版本完成”为由停止验证。
4. **性能是贯穿式发布关卡。** Phase 0 建立测量方法与首轮预算；`A14 性能基线与回归门槛` 到 `v0.4` 才算随完整 MVP 正式交付。此前每个可安装版本仍必须提交对应的 release 真机数据。
5. **正确性优先于低占用。** 只有在不漏记、不损坏数据、不误跳转的方案之间，才选择 CPU、内存、唤醒、写盘和耗电更低者。
6. **版本号不等于发布授权。** 完成里程碑、生成侧载构建、创建 Git 标签、推送 GitHub 和公开发布 APK 是不同动作；本路线图不自动授权 `git push` 或公开发布。
7. **宿主扩展不提前实现。** `v0.x` 只保留清楚边界，不建立没有第二个真实需求支撑的通用后台宿主或模块系统。

## 2. 里程碑总览

| 里程碑 | 定位 | 主交付 `[A]` 数 | 主交付 `[B]` 数 | 退出结果 |
|---|---|---:|---:|---|
| Phase 0 | 致命假设 Spike，不是产品版本 | 0 | 0 | 带红魔 11 Pro+ 证据的 `GO / REDIRECT / STOP` 结论与首轮资源预算 |
| `v0.1` | 最小端到端闭环 | 5 | 0 | 单条受支持通知可被可靠采集、持久保存、查看并回开 |
| `v0.2` | 可信的多来源收件箱 | 4 | 0 | 排除、合并、去重、稳定排序和多应用查看边界正确 |
| `v0.3` | 可观察的时间轴体验 | 3 | 0 | 时间窗抽屉、常驻状态通知和健康时间轴可日常理解 |
| `v0.4` | `[A]` 级 MVP 验收版 | 2 | 0 | 14 个 `[A]` 全部通过；B 站三类精确跳转与完整性能关卡通过 |
| `v0.5` | 日用管理与诊断增强 | 0 | 3 | 搜索筛选、v0 保留边界、隐私安全诊断导出及 Phase 2 体验加固通过 |

版本依赖为单向关系：

```text
Phase 0 GO → v0.1 → v0.2 → v0.3 → v0.4 → v0.5
                  最小闭环                全部 A     全部 B
```

任何 Spike 得出 `REDIRECT` 都必须先更新项目计划、架构与本路线图；不得让后续版本绕开失败结论继续前进。

## 3. Phase 0：致命假设 Spike

### 3.1 目标

回答项目是否能在红魔 11 Pro+、Android 16 上成立，并为后续版本锁定有证据的实现边界。Phase 0 可以在详细开发计划获得确认后建立最小验证工程或测试夹具，但不以完成产品界面为目标，也不因此宣称任何 `[A]` 功能已经交付。

### 3.2 Spike 清单

| Spike | 待验证问题 | 必须取得的证据 | 影响的后续版本 |
|---|---|---|---|
| `SP-01（架构 S0）真实通知字段与生命周期` | B 站投稿、动态、开播及可控测试通知实际提供哪些身份、字段、更新、移除和 ID/key 复用序列 | 脱敏字段缺失矩阵；`key/id/tag/user/postTime` 生命周期记录；同标题不同目标和 key 复用反例 | `v0.1`、`v0.2`、`v0.4` |
| `SP-02（架构 S1）原始动作寿命与持有成本` | 原始动作在通知仍在、划除、等待、OMN 进程重建、B 站普通进程结束/强行停止/更新和设备重启后如何失效；长期持有句柄成本多大 | `PendingIntent.send()` 接受结果与实际落页；失败分类和一次性行为；不同句柄数量下的 PSS/Binder 成本；受支持持有方案对照 | `v0.1`、`v0.4` |
| `SP-03（架构 S2）B 站持久精确目标` | 投稿、动态、开播能否从通知中提取可跨 OMN 进程和设备重启保存的稳定 URI 或内容 ID | 三类结构化目标矩阵；进程重建和重启后的实际落页；内容删除、未登录和 B 站更新反例；分类型能力结论 | `v0.1`、`v0.4` |
| `SP-04（架构 S3）摄取队列、事务与归并` | 如何在不阻塞系统回调、不静默丢弃的前提下保持观察顺序、原子提交并区分更新与新代次 | 100 条以上突发的回调耗时、积压、内存、事务数和漏记；写入中止一致性；重复回调、补扫和时钟跳变性质测试 | `v0.1`、`v0.2`、`v0.4` |
| `SP-05（架构 S4）监听可靠性与红魔后台策略` | `NotificationListenerService` 在授权、撤权、断连、重连、长锁屏、系统回收、开机和厂商后台限制下如何表现 | 红魔 11 Pro+ 生命周期和活动通知补扫记录；设备 ABI、权限与厂商设置；可观测漏记窗口和恢复步骤 | `v0.1`、`v0.3`、`v0.4` |
| `SP-06（架构 S5）状态通知与前台服务 A/B` | 监听服务直接维护普通常驻通知是否足够；若使用前台服务，其类型、权限、平台规则和资源成本是否匹配 | 两种拓扑的通知残留、进程重要性、重启恢复、`POST_NOTIFICATIONS`、渠道关闭、锁屏脱敏、合法服务类型、PSS、CPU 和耗电对照 | `v0.3`、`v0.4` |
| `SP-07（架构 S6）健康证据与区间精度` | 在不轮询、不持有唤醒锁、不使用精确闹钟的前提下，哪些事实足以派生蓝色已确认区间和黄色未确认区间 | 连接、断连、正常停止、强制终止、权限切换和长待机事实线；自然证据下的黄色比例；额外唤醒为零的记录 | `v0.3`、`v0.4` |
| `SP-08（架构 S7）排序、抽屉、筛选与分页` | 稳定全序、15 分钟/最多跨 3 条抽屉规则、多应用筛选和分页边界是否确定且可解释 | 相同时间、短/长跨度 `A→B→A`、跨 4 条、页边界、筛选切换和单应用极端突发样本；10,000 条不全量载入证据 | `v0.2`、`v0.3`、`v0.5` |
| `SP-09（架构 S8）持久化、隐私与性能基线` | Room 必要事实、诊断上限和隐私边界如何锁定；纯 Kotlin/AndroidX 路径与完整生产工作负载的成本是否可接受 | release 设备/ABI记录；8 小时无通知、100 条突发、10,000 条历史和持续增长数据；日志/数据库/导出敏感字段扫描；绝对预算和上限 | 所有版本，正式交付在 `v0.4` |

测试中的立即、跨日、重启后或更长观察点只是测量检查点，不是人为的跳转 TTL。归档记录不得因为年龄被 OMN 主动标记失效。

真实通知原文、可执行动作、未脱敏截图和本机路径不得提交到 Git。公开文档只保留脱敏字段、统计结果、复现步骤和结论；必要的原始样本仅在本机非跟踪位置短期保存。

### 3.3 不在范围

- 不完成正式收件箱视觉设计或日用交互。
- 不以 Spike 工程的临时代码质量代表生产架构。
- 不实现账号、云同步、遥测、备份或其他后台模块。
- 不承诺 `PendingIntent` 永久有效，不把 `Parcel` 当作磁盘格式。
- 不为了得到更长蓝色区间而加入高频心跳、轮询、唤醒锁或精确闹钟。

### 3.4 依赖

- 详细开发计划获得用户确认，允许进入 Phase 0 实现和真机验证。
- 红魔 11 Pro+ 可安装个人侧载的 release 验证构建，并授予/撤销通知使用权和通知权限。
- 能在实际使用周期内取得 B 站投稿、动态和开播通知；无法自然触发的场景必须记录等待状态，不能用猜测补齐。
- 测试数据和日志采用脱敏方案，不进入公开仓库。

### 3.5 可测试完成定义

Phase 0 只有在以下项目全部有记录时完成：

1. `SP-01` 至 `SP-09` 九个 Spike 均有步骤、设备信息、样本范围、结果、限制和结论；“尚未观察到”不能写成“已支持”。
2. 原始动作的寿命与持有成本有独立结论；投稿、动态、开播分别得到“持久精确目标”“仅运行时精确动作”或“不支持”的证据结论，并覆盖划除、进程重建、B 站状态变化和设备重启等失效边界。
3. 通知身份、生命周期代次、摄取队列、事务原子性、归一化、去重、稳定排序、筛选、分页和抽屉规则均有正例与反例样本。
4. 状态通知承载方式与健康证据模型有明确选择；若采用前台服务，服务类型和用途符合当前 Android 规则。
5. release 真机测量建立首轮绝对预算和可重复脚本/步骤；预算至少覆盖后台内存、CPU 时间、唤醒、写盘、耗电、数据库增长和状态通知更新次数。
6. 形成一个总决策：
   - `GO`：核心闭环可成立，资源成本可接受，可以进入 `v0.1`；
   - `REDIRECT`：可通过改变产品承诺或技术边界继续，先回写计划并由用户确认；
   - `STOP`：精确回开、平台合规或闲置成本存在致命失败，停止进入产品版本。

### 3.6 真机与性能关卡

- 所有 Android 生命周期、跳转和后台可靠性结论以红魔 11 Pro+ release 构建为准，模拟器仅用于构造可控通知样本。
- 8 小时息屏无通知时，不应出现 OMN 主动的周期性唤醒或数据库写入。
- 100 条突发通知及更新不得漏记；数据库事务只随真实逻辑变化增长，状态通知刷新应显著少于原始回调数。
- 10,000 条历史不得全量常驻内存；后台内存不得随总记录数线性增长。
- “仅监听服务”和“监听 + 前台服务”都满足正确性时，选择真机占用更低者。
- Phase 0 绝对预算一旦锁定，后续同场景无解释的 CPU、唤醒、写盘或后台内存回退超过 10% 即阻止版本通过。

## 4. `v0.1`：最小端到端闭环

主交付 5 个 `[A]`：

- `A01 首次授权与全量监听`
- `A03 通知事件采集`
- `A04 条目归一化`
- `A08 本地持久化`
- `A09 原内容跳转`

### 4.1 目标

交付第一个可安装的纵向切片：对 Phase 0 已证明受支持的一条真实通知，用户可以授权 OMN、收到并保存通知、划除系统通知、在应用内看到记录并回到精确原内容。它证明核心链路能连接起来，但不宣称已经达到多通知日用质量。

### 4.2 范围

- 首次进入时分别展示通知使用权和状态通知权限的状态；本版本只要求完成监听所需授权路径，状态通知本体在 `v0.3` 交付。
- 通过 `NotificationListenerService` 接收系统回调，自动排除 `io.github.prince_dulb.ohmynotification` 自身通知。
- 把不同通知字段归一化为最小可展示条目，并明确缺失标题、正文或动作时的状态。
- 使用 Phase 0 锁定的数据边界完成进程重建后的本地持久化。
- 提供最薄的 Material 3 记录列表和条目点击入口，用于完成闭环；本版本不验收复杂排序、分组或最终视觉。
- 按 Phase 0 结论执行受支持的精确动作或持久目标；失败时显示真实失效原因，不伪装成成功。

### 4.3 不在范围

- 不承诺更新合并、重复治理或并发同时间稳定排序。
- 不提供应用排除列表、多应用查看筛选和时间窗抽屉。
- 不提供常驻状态通知或蓝黄健康时间轴。
- 不声称 B 站投稿、动态、开播三类已经全部通过；完整 B 站验收属于 `v0.4`。
- 不因记录年龄设置动作有效期。

### 4.4 依赖

- Phase 0 总结论为 `GO`，且 `SP-01`、`SP-02`、`SP-03`、`SP-04`、`SP-05`、`SP-09` 已锁定本版本可用边界。
- 若 Phase 0 无法证明至少一种符合核心场景的精确持久目标，`v0.1` 不得以“打开 B 站首页”替代后宣称闭环完成。
- 初始 Room 模型和动作策略需与架构设计、功能规格一致；若实施期间发生 schema 变更或迁移，按项目红线先征得用户同意。

### 4.5 可测试完成定义

1. 全新安装可识别未授权状态、进入系统授权页，并在授权后开始接收系统可见通知。
2. 本应用自己的通知不会进入记录。
3. 对 Phase 0 指定的受支持样本，通知到达后形成一条字段正确的持久记录。
4. 划除原系统通知并重建 OMN 进程后，记录仍可见。
5. 点击记录进入与该通知一致的精确目标；不可用时显示经过验证的失效原因与允许的降级选项。
6. 缺少标题、正文或图标的可控样本不会导致崩溃或生成虚假内容。
7. 自动化测试覆盖归一化、持久化往返和动作策略选择；真机报告覆盖完整闭环。

### 4.6 真机与性能关卡

- 在红魔 11 Pro+ 上使用 release 构建完成“接收 → 划除 → 进程重建 → 查看 → 精确跳转”。
- 完成权限撤销再恢复、监听断连再连接和应用进程重建测试；不得静默停留在“已监听”假状态。
- 8 小时息屏无通知时不得产生周期性数据库写入、轮询或主动唤醒。
- 记录本版本的后台 PSS、CPU 时间、唤醒、写盘、数据库增长和状态通知更新次数；相对 Phase 0 基线无解释回退超过 10% 则不通过。

## 5. `v0.2`：可信的多来源收件箱

主交付 4 个 `[A]`：

- `A02 应用排除列表`
- `A05 更新合并与去重`
- `A06 稳定排序`
- `A12 多应用查看筛选`

### 5.1 目标

把 `v0.1` 的单条纵向证明升级为可以承受真实多应用交错和通知更新的可信收件箱。用户能够控制未来采集范围和当前查看范围，且两者不会相互污染。

### 5.2 范围

- 建立应用排除列表：默认监听所有系统可见通知，本应用始终自动排除，用户排除只影响后续采集。
- 以系统身份、生命周期代次及 Phase 0 证据为基础合并更新；内容指纹只作为辅助，不以标题或正文单独去重。
- 按首次收到时间倒序；更新不把旧条目顶到顶部；时间相同使用稳定次级键。
- 支持一个或多个应用的查看筛选，清除筛选恢复全部历史；筛选不改变采集策略。
- 保持既有记录：把应用加入排除列表不删除历史。

### 5.3 不在范围

- 不做时间窗抽屉和完整健康时间轴。
- 不做关键词或时间筛选。
- 不自动删除通知条目，不把排除操作隐式变成删除。
- 不交付最终常驻状态通知。

### 5.4 依赖

- `v0.1` 的采集、归一化、持久化和跳转回归全部通过。
- `SP-01`、`SP-04` 提供通知生命周期与归并证据；`SP-08` 锁定稳定排序、筛选和分页契约；`SP-09` 明确策略数据与通知数据边界。
- 功能规格必须先定义“新生命周期”与“同一通知更新”的判定顺序及稳定次级键。

### 5.5 可测试完成定义

1. 同一系统通知的发布和多次更新只产生一个逻辑条目，同时保留首次收到时间与最近更新时间。
2. 相同标题/正文但目标不同的两条通知不会被误合并；系统身份复用进入新生命周期时不会覆盖旧条目。
3. 更新旧通知后，该条目不会重新顶到首位；相同首次收到时间的测试数据在重复查询后顺序一致。
4. 排除某应用后，其未来通知正文和动作不持久化；已有历史保持不变。
5. 查看筛选可同时选一个或多个应用，切换或清空筛选不会改变后台监控范围。
6. 自动化测试覆盖去重反例、更新合并、稳定排序、排除规则、查看筛选和应用重启后的策略持久化。

### 5.6 真机与性能关卡

- 在红魔 11 Pro+ 上以 B 站和至少两个其他来源构造交错通知，核对排除、筛选、更新和重启后的结果。
- 100 条包含重复回调和更新的突发样本不得漏记、误合并或重复刷屏。
- 合并后的数据库事务数量应随逻辑变化而非原始回调逐条增长；若未达到，必须记录原因并返回设计检查。
- 列表采用分页或惰性加载；本版本数据量扩大后不得将全量历史长期驻留内存。
- 重跑 8 小时无通知基线并记录全部资源指标；相对上一通过版本无解释回退超过 10% 则不通过。

## 6. `v0.3`：可观察的时间轴体验

主交付 3 个 `[A]`：

- `A07 时间窗应用抽屉`
- `A10 常驻状态通知`
- `A11 健康状态时间轴`

### 6.1 目标

交付项目的核心交互形态：应用内能沿时间轴理解通知和运行证据，应用外能从低打扰状态通知看到监听状态与最近记录，同时保持事件驱动和诚实表达不确定性。

### 6.2 范围

- 在稳定全局时间序基础上，对同一应用、15 分钟内且最多跨越 3 条其他应用记录的条目派生可展开抽屉。
- 抽屉头展示来源、数量、起止时间和最新摘要；展开后逐条显示真实时间、正文与跳转状态。
- 建立独立“运行状态”通知渠道，默认静音、无震动、无悬浮；状态变化、真实通知或必要摘要变化时才更新，并合并突发刷新。
- 常驻状态通知点击进入收件箱；解锁显示来源和标题，锁屏公开内容只显示来源，不显示原正文。
- 根据 Phase 0 证据模型派生蓝色实线“已确认运行”和黄色虚线“未确认运行”；同时提供文字、线型和无障碍描述。
- 对通知使用权、`POST_NOTIFICATIONS`、状态渠道和监听连接分别建模并给出系统设置入口。

### 6.3 不在范围

- 不以黄色区间断言精确停机时刻。
- 不为填满蓝色时间轴加入轮询、高频心跳、唤醒锁或精确闹钟。
- 不做关键词和时间筛选，不做诊断导出。
- 不在本版本改变 15 分钟或跨越 3 条的已确认初始参数；若样本证明不合理，先走计划变更。

### 6.4 依赖

- `v0.2` 的稳定排序、去重和分页查询可作为时间轴事实来源。
- `SP-06` 已选定合规且成本可接受的状态通知承载方式；`SP-07` 已定义健康证据和可达到的区间精度；`SP-08` 已验证分组、筛选和分页算法正反例。
- 若前台服务方案未通过平台规则或资源关卡，必须采用已验证的其他方案并诚实描述其健康含义，不能错报服务类型。

### 6.5 可测试完成定义

1. 短跨度 `A→B→A` 在满足阈值时形成 A 抽屉；长跨度或跨越数量超限时恢复严格全局时间序。
2. 抽屉显示正确起止时间，展开后组内条目顺序、逐条时间和跳转目标与原始记录一致。
3. 状态通知正常、异常和权限不足文案可区分；锁屏不暴露标题或正文。
4. 通知权限被拒绝、渠道关闭、监听断连等状态在应用内分别可见，不把状态通知存在当作唯一存活证明。
5. 突然终止后无法证明的区间显示黄色未确认，恢复后区间边界与最后证据一致。
6. 时间轴和抽屉同时通过颜色、线型、文字和无障碍语义表达；点击目标至少 48dp。
7. 自动化测试覆盖时间窗、跨越数量、展开顺序和健康区间派生；界面测试覆盖深浅色、字体放大和语义树。

### 6.6 真机与性能关卡

- 红魔 11 Pro+ 上覆盖锁屏/解锁、通知权限开关、状态渠道开关、监听重连、长时间息屏和手机重启。
- 100 条突发通知时统计系统回调数与状态通知刷新数；刷新必须满足 Phase 0 的合并预算，不能逐回调刷新。
- 10,000 条历史下时间轴首屏、滚动、筛选和抽屉展开不得触发全表加载或全量重分组。
- 状态通知承载方式按 Phase 0 选择运行；若实际数据推翻选择，停止版本验收并回到 Spike/架构决策。
- 重跑 8 小时无通知基线；相对上一通过版本无解释回退超过 10% 则不通过。

## 10. 所有可安装版本的共同完成关卡

除各版本专属定义外，每个版本还必须同时满足以下条件：

### 10.1 功能与数据

- 该版本主交付功能的规格、实现、自动化测试和真机证据可以互相追溯。
- 既有通知归一化、去重、排序、筛选、持久化和跳转能力无回归。
- 真实通知正文、可执行动作、未脱敏截图、签名材料和本机 SDK 路径不进入 Git、公开日志或诊断默认输出。
- 所有失败状态明确显示，不能把降级打开来源应用写成精确跳转成功。

### 10.2 Android 与界面

- 使用 Android 16 目标环境和 AndroidX 稳定版基线；锁定版本时记录日期和依据。
- release APK 在红魔 11 Pro+ 可安装、启动和完成版本场景；不得包含仅 32 位可用的原生依赖。
- Material 3、edge-to-edge、系统 inset、48dp 触控目标及核心无障碍语义随每版保持，而不是留到最后一次补做。
- 通知权限、通知使用权、状态通知渠道和监听连接分别检测，不用一个布尔值概括全部健康状态。

### 10.3 性能

- 无通知且界面关闭时保持事件驱动，不轮询，不持有唤醒锁，不使用精确闹钟或高频心跳。
- 每版使用 release 构建记录后台 PSS、CPU 时间、唤醒、写盘、数据库增长、状态通知更新次数和长待机耗电。
- 数据库写入只来自真实通知、明确状态变化或用户操作；列表使用分页/惰性加载、稳定键和增量计算。
- 同场景相对最近通过基线无解释回退超过 10% 时，版本不得合并；若变化来自正确性修复，必须记录原因、收益和新的用户确认边界，不能静默放宽门槛。

### 10.4 交付证据

- 完成声明附测试命令、结果摘要、构建类型、设备型号、系统版本、时间和已知限制。
- 真机观察写成事实；推测、未覆盖机型和尚未取得的 B 站通知类型继续标为 `[待验证]`。
- 版本里程碑通过不自动授权发布 APK、创建公开仓库或推送远端。

## 11. 路线图调整规则

以下情况必须先更新计划文档并获得必要确认，再改变实现顺序：

- Phase 0 无法证明满足实际查看周期的精确跳转，或投稿、动态、开播任一类型只能降级到不精确目标。
- 目标手机上的监听可靠性必须依赖不合规的前台服务类型、高频唤醒或不可接受的厂商设置。
- 健康时间轴只能通过违背低闲置成本的方式提高精度。
- Room 初始模型需要改变已确认的数据保留、隐私或动作边界；已发布 schema 需要迁移时按数据库红线处理。
- 任一版本为了赶进度需要超过 5 个新的 `[A]` 主交付，或准备把未通过功能推迟却仍沿用原版本完成声明。
- 出现第二个真实后台需求。此时才为 Phase 3 单独立项，比较共享宿主与独立应用的真实收益；不得直接把新任务塞进现有常驻链路。
