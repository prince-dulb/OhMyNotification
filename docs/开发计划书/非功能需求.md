# 非功能需求

状态：`plan-v1.0 编制中`

本文定义“救救我的通知！”在 Phase 0 至 Phase 2 期间必须共同满足的横切质量要求。功能规格回答“做什么”，本文回答“做到什么程度才可接受”。如本文与 `AGENTS.md` 或 `docs/项目计划书.md` 冲突，以项目规定的文档权威顺序为准。

## 1. 验收口径与基线锁定

### 1.1 要求状态

- `[已确认]`：已由项目规则或立项计划书确定，实施和验收不得自行放宽。
- `[待验证]`：必须在 Phase 0 以红魔 11 Pro+ 真机证据得出结论；验证报告形成后，须把结论和数值预算写回本文或计划变更记录，才可进入 Phase 1。
- “通过”必须同时包含可复现的操作步骤、构建标识、设备环境、原始测量结果和结论。只有主观体感或 debug 构建截图不构成通过证据。

### 1.2 统一测量环境

所有后台可靠性和性能结论必须使用可安装的 `release` 变体，在红魔 11 Pro+ 真机上得出。每次报告至少记录：

| 项目 | 必须记录的内容 |
|---|---|
| 构建身份 | Git commit、应用版本、`applicationId`、构建时间、是否启用代码压缩 |
| 设备身份 | 机型、Android 版本与系统构建号、设备报告的 ABI、可用存储 |
| 系统状态 | 电池电量区间、是否充电、屏幕状态、网络状态、省电模式、温度异常情况 |
| 权限与厂商策略 | 通知使用权、`POST_NOTIFICATIONS`、状态通知渠道、红魔后台/自启动策略 |
| 应用状态 | 首次安装或升级、数据库条目数、诊断事件数、监听方案、是否附加前台服务 |
| 工作负载 | 测试数据集版本、事件数量与顺序、通知更新比例、测试起止时间（带时区） |
| 观测工具 | 命令或工具版本、采样周期、统计口径、原始结果文件位置 |

比较前后版本时，除被测版本外，上表条件必须相同；不能相同的条件必须在报告中列出，结果不得直接用于 10% 回归判定。

短场景至少进行 1 次预热和 3 次有效测量，使用有效测量的中位数比较。8 小时息屏场景每种候选架构至少完成 2 次有效测量；两次结果相差超过 10% 时追加测量，直到能够说明波动来源并形成可重复口径。测试期间出现系统更新、充电状态变化、温控降频或无关应用异常活动时，该次结果标为无效，不用删除原始记录。

### 1.3 Phase 0 数值锁定规则

`[已确认]` 当前不编造 CPU、内存、耗电、加载耗时等绝对预算。Phase 0 按以下规则锁定：

1. 先通过可靠性和数据正确性要求，再比较资源占用；会漏记、误合并、损坏数据或破坏跳转的低占用方案没有参选资格。
2. 对“仅 `NotificationListenerService`”和“通知监听 + 前台服务”执行同一套工作负载。两者都满足正确性时，选择 CPU、后台 PSS、唤醒、写盘和耗电综合成本更低者；若指标互有胜负，记录取舍并由用户决定架构。
3. 将选定架构在固定场景下的中位数记录为 Phase 0 基线，并在本文中补入首版绝对预算。绝对预算必须包含单位、测量窗口、统计方法和适用设备，不能只写“低”“流畅”或“接近零”。
4. 对预期为零的结构性指标，不用百分比掩盖新增工作。例如基线没有周期性唤醒时，后续出现稳定的周期性唤醒即为失败；Phase 0 另行锁定不可避免的系统噪声识别方法。
5. Phase 0 报告未锁定绝对预算前，不得宣称 Phase 1 满足性能要求。

### 1.4 10% 性能回归门

`[已确认]` 基线建立后，在同设备、同构建类型、同配置、同数据集和同测量口径下，以下任一“越低越好”指标的中位数比已锁定基线上升超过 10%，均视为性能回归：

- 8 小时息屏场景的应用 CPU 时间；
- 应用可归因唤醒次数或唤醒时长；
- 数据库写入次数、写入量或数据库增长量；
- 后台 PSS；
- 100 条突发场景的状态通知刷新次数和处理 CPU 时间；
- 10,000 条历史场景的首屏、筛选、分组和滚动基准耗时；
- 测量方法达到可重复条件后的应用耗电。

超过 10% 时不得合并或作为候选发布版交付。只有以下两种处理路径：修复并重新通过；或证明原测量无效后按相同协议重测。若资源增加来自明确的正确性或可靠性收益，必须记录根因、收益、成本和新证据，经用户确认并通过计划变更更新基线，不能静默抬高预算。

### 2.2 固定工作负载

#### 8 小时息屏、无通知

- 测试开始前确认监听已连接、界面退到后台、数据库队列已清空，之后息屏 8 小时且不向设备发送测试通知。
- 分别测量候选后台架构；网络和厂商后台策略保持一致。
- 记录进程与监听状态、CPU 时间、PSS、应用可归因唤醒、数据库写入、状态通知更新、耗电和测试后健康时间轴。
- 结构性通过条件：稳定期没有应用主动产生的周期性轮询、数据库写入、唤醒锁或精确闹钟；不能用高频活动换取连续蓝色区间。
- 绝对 CPU、PSS、写盘和耗电预算按 1.3 节在 Phase 0 锁定。

#### 100 条突发通知及更新

- 使用版本化、可重放且不含真实个人内容的数据集，向监听链路交付共 100 个已知顺序的发布、更新与移除回调；数据集必须包含同一通知的密集更新、不同通知相同标题、不同应用交错以及本应用状态通知。
- 记录输入回调数、成功持久化事件数、逻辑条目数、误合并、重复、事务数、处理时长、峰值 PSS、状态通知刷新数和最终排序。
- 通过条件：全部预期回调都有可核对结果；没有漏记、误合并或自我记录；事务只随真实逻辑变化增长；状态通知刷新经过合并且不等于逐回调刷新。
- 合并时间窗、最大事务数、最大刷新数和处理预算由 Phase 0 在不损害可靠性的前提下锁定。

#### 10,000 条历史记录

- 使用去隐私化生成器构造 10,000 个长期条目，并包含足以覆盖 15 分钟窗口、最多跨越 3 条其他应用记录、同时间戳次级排序、空字段和长文本的样本。
- 验证冷启动后首屏、连续翻页、快速滚动、展开抽屉、多应用筛选、时间筛选和返回列表。
- 记录查询数量与范围、已加载条目数、后台和峰值 PSS、首屏时间、各操作基准耗时、丢帧/卡顿观测及分组正确性。
- 通过条件：不全表载入；后台内存不随总历史条目数线性增长；分页边界不丢失、不重复、不改序；抽屉只对受影响窗口增量计算。
- 交互耗时和 PSS 的绝对预算由 Phase 0 锁定，Phase 2 继续以同一数据集回归。

### 2.3 存储增长

- 每个版本必须记录空库大小、每增加固定数量通知条目后的数据库增量、诊断事件上限触发后的稳定大小以及缓存上限。
- 正文、动作能力摘要和图标引用不得在原始事件与长期条目中无必要重复保存。
- v0 不自动删除长期通知条目；存储不足时必须显示可行动错误，不得静默丢弃旧条目或声称新通知已记录成功。
- 诊断事件与诊断日志的容量/时间上限须在 Phase 0 根据 100 条突发和长期注入结果锁定，并在达到上限时按明确、可测试的规则淘汰诊断数据，不影响长期通知条目。

## 4. 数据安全与隐私

### 4.1 数据边界

- `[已确认]` 通知正文、来源、时间、动作目标和查看行为默认只保存在本设备的应用私有空间；v0 不实现账号、云同步、遥测或服务端备份。
- `[已确认]` v0 依赖 Android 应用沙箱与设备加密，不增加数据库字段加密或应用锁。界面和文档不得把这一选择表述成“数据库已单独加密”。
- 通知数据库、动作目标和含通知信息的偏好数据必须排除出 Android 自动云备份及跨设备自动迁移；未来的本地备份与恢复只能作为单独功能，经用户主动选择后实施。
- 本应用不得请求实现核心功能不需要的网络、联系人、短信、存储或无障碍权限。通知使用权和 `POST_NOTIFICATIONS` 必须分开解释、分开检测。

### 4.2 采集最小化

- 本应用状态通知在进入持久化链路前自动排除。
- 被用户排除应用的新通知不得持久化正文、动作、内容指纹或可还原内容的诊断字段；允许只记录不含来源内容的汇总计数时，须先在功能规格中明确用途。
- 原始诊断事件只保留排查合并与漏记所需的最小字段，不保存第二份完整正文或可执行动作。
- 默认不持久化通知大图；应用图标通过包名获取并使用有界缓存。
- 长期通知条目不自动删除；用户删除必须是独立、明确且可确认目标范围的操作。

### 4.3 显示与导出

- 锁屏状态通知只显示运行状态和最近来源应用，不显示标题、正文或动作目标；解锁状态最多显示来源应用和标题，不显示完整正文。
- 最近通知、错误弹窗、系统日志和崩溃堆栈不得暴露通知正文、验证码、完整 URI、动作令牌或其他可执行目标。
- 诊断导出只在用户主动操作后生成，默认移除正文、标题、完整 URI、`PendingIntent`/动作信息、账户标识和本机路径；导出前展示包含字段与保存位置。
- 测试数据、截图和演示数据库必须使用去隐私化或生成数据。真实通知不得进入 Git、公开 issue、提交信息或公开日志。

### 4.4 Android 组件安全

- Activity、Service、Receiver 和 Provider 默认不导出；平台要求导出的组件必须有明确调用方、权限边界和输入校验。
- 进入应用的外部 `Intent`、URI、包名和通知字段均视为不可信输入；解析失败、超长文本、未知 scheme 或目标缺失不得导致崩溃或越权启动。
- 自建 `PendingIntent` 必须使用最小权限和明确的可变性标记；无须可变时保持 immutable。不得通过序列化 `Parcel` 持久化其他应用的 `PendingIntent`。
- release 构建不得包含调试后门、可写调试 Provider、测试密钥、Token、签名材料或真实本机路径。

| NFR-A11Y-007 | edge-to-edge 界面正确处理状态栏、导航栏、显示切口和输入法 inset；控件不得被系统区域遮挡。 | 各页面横竖屏、手势/三键导航和输入法场景检查。 |
| NFR-A11Y-008 | 动效仅解释抽屉展开、列表变化和状态切换；系统减少动态效果开启时，功能完整且不依赖动画理解状态。 | 开关减少动态效果，重复全部核心交互。 |

Material 3 官方组件优先于自制控件。若自定义控件不可避免，必须补齐状态、焦点、语义、禁用态、按压反馈和触控范围，不接受“视觉上可点”作为无障碍完成标准。

## 6. 国际化、区域格式与时间

- `[已确认]` 数据库时间统一存 UTC；界面按设备当前时区显示。排序和通知身份不得依赖格式化后的本地时间字符串。
- 用户可见日期、时间、数量和相对时间使用 Android locale 与 12/24 小时设置；不得通过字符串拼接制造固定中文语序。
- 设备时区、夏令时或 12/24 小时制变化后，既有条目的绝对时刻和排序保持不变，界面在下次显示时按新设置重新格式化。
- 健康区间和应用抽屉跨越本地日期、时区切换或夏令时边界时，使用 UTC 瞬时值计算跨度；15 分钟窗口不得因墙上时钟回拨而错误延长或反转。
- 诊断报告与计划测试记录使用带时区的 ISO 8601；数据库内部时间和性能持续时间分别使用 UTC 瞬时值与单调时钟，不混用。
- v0 用户界面至少完整提供简体中文资源；应用中文显示名为“救救我的通知！”，英文项目名为“Oh My Notification!”。全部用户文案放入资源文件，代码中不得硬编码，以保留后续本地化能力。
- 包名、应用名、来源应用标签和用户生成通知文本必须支持 Unicode；异常或不可显示字符只能安全替换，不能使采集链路失败。

## 7. 兼容性与平台合规

- `[已确认]` v0 最低支持 Android 16，不为旧系统增加兼容分支；目标 SDK、Compose、Room 和其他 AndroidX 版本在实现开始时按当日官方稳定版锁定并记录日期。
- `[已确认]` 首要验收设备为红魔 11 Pro+，目标设备结果优先于模拟器。模拟器、桌面预览和单元测试只能补充，不能替代后台、权限、重启和耗电真机结论。
- `[已确认]` v0 保持纯 Kotlin/Java/AndroidX，不引入 NDK 或第三方原生库。若未来引入原生依赖，必须先确认目标设备 ABI 并证明 APK 不含仅 32 位实现。
- 界面必须覆盖手机横竖屏、分屏、不同字体与显示缩放；更大窗口按官方自适应列表—详情原则处理。窗口变化不得丢失筛选、滚动位置或已展开抽屉的可解释状态。
- `NotificationListenerService` 生命周期、通知使用权、`POST_NOTIFICATIONS` 与状态通知渠道分别建模。用户拒绝状态通知权限时，核心监听能力和应用内健康说明不得错误地被当成同一权限失败。
- 若采用前台服务，必须声明与真实用途匹配的平台服务类型，并在目标 Android 版本上验证启动限制、通知可见性和重启行为；不得错报 `dataSync` 等无关类型绕过要求。
- 应用来源通知可能缺少标题、正文、图标、`postTime`、点击动作或稳定 URI。缺字段时使用明确降级显示，不崩溃、不伪造字段、不以来源应用能启动冒充精确跳转。
- 核心功能在无网络环境下必须完整工作；来源应用自身需要网络才能打开内容时，应把该失败归因于来源应用或网络，而非把归档记录判为不存在。

## 8. 错误处理与诊断

### 8.1 全局处理原则

1. 错误必须分为权限/配置、监听生命周期、持久化、动作跳转、存储空间、数据解析和未知内部错误，不能统一显示“失败”。
2. 用户信息包含：发生了什么、哪些数据可能受影响、当前是否仍在记录、可执行的下一步。没有正面证据时使用“未确认运行”，不用“已停止”或“没有漏记”等过度断言。
3. 成功反馈只在对应事实成立后出现。数据库写入失败不能增加“已救回”数量，目标 Activity 未实际启动不能显示“已打开”。
4. 单条畸形通知或跳转失败不得终止监听服务、阻塞后续通知或破坏已有数据库；失败输入生成最小诊断事实后隔离处理。
5. 重试必须有上限、退避和取消条件，不得忙等。重试本身不能持有唤醒锁、精确闹钟或高频周期任务。

### 8.2 用户可见错误

| 场景 | 最低用户反馈 | 系统行为 |
|---|---|---|
| 通知使用权未授予或被撤销 | 显示“未在监听”及系统设置入口 | 停止声称记录成功，保留既有数据 |
| `POST_NOTIFICATIONS` 被拒绝 | 说明状态通知不可见及设置入口 | 监听状态单独判断，应用内继续显示健康信息 |
| 状态通知渠道关闭 | 说明应用外状态卡不可见 | 不把渠道关闭误判为监听断开 |
| 监听断开或无正面证据 | 显示最后确认时间和黄色未确认区间 | 记录生命周期事实，等待平台重连或用户操作 |
| 数据库写入失败/存储不足 | 明确说明该条可能未保存及受影响时间 | 不更新成功计数；保留最小错误事实；无无限重试 |
| 跳转目标取消、一次性耗尽或不可解析 | 显示具体失效原因与可用降级动作 | 不崩溃，不删除归档条目，不伪装精确打开 |
| 来源应用未安装或进入 stopped 状态 | 说明原动作可能失效；若仍有安全可解析的应用入口，则提供显式降级选择 | 保留动作和条目；不把 stopped 等同于永久不可启动，用户重新启动/安装来源应用后可再次尝试 |
| 单条通知字段异常 | 该条按可用字段降级展示 | 隔离解析失败，后续通知继续处理 |

### 8.3 诊断数据

- 诊断事件和日志必须本地、有界、可清理，不得无限增长；确切条数/时间上限在 Phase 0 锁定。
- 日志使用结构化事件类型、匿名内部 ID、包名是否保留的明确策略和 UTC 时间；默认不记录标题、正文、完整 URI、动作令牌或用户输入。
- 每次性能与可靠性测试至少能关联：输入事件、逻辑条目、数据库事务、状态通知刷新、监听生命周期和错误类型。
- v0 不接入远程崩溃上报。崩溃后下次启动可提示存在本地诊断信息，但导出必须由用户主动发起并先去隐私化。
- release 构建关闭详细调试日志；为 Phase 0 启用的额外测量开关必须明确标记，且测量构建与候选发布构建的差异须写入报告。

## 9. 可维护性

- 核心规则必须位于可独立测试的领域层：系统通知身份与生命周期代次、条目归一化、更新合并、稳定排序、15 分钟/最多跨越 3 条的抽屉分组、监控排除和健康区间派生不得散落在 Compose UI 或 Android 回调中。
- Android 框架对象不得直接成为长期领域模型或数据库格式；`PendingIntent` 等不能稳定持久化的对象通过受控边界使用，并与可持久目标、能力状态分开建模。
- 所有阈值和策略使用单一、具名且有版本的配置来源。更改分组参数、诊断上限、状态刷新合并窗口或性能预算时，必须同步测试与计划变更记录，不能在多处保留魔法数字。
- 数据模型、DAO、仓储、领域规则、Android 服务和 Compose UI 的依赖方向在架构设计中固定；UI 不直接拼装数据库实体，监听服务不直接承担列表分组。
- 去重、排序、分组、筛选、时间转换和诊断脱敏必须使用固定、去隐私化测试夹具，结果可重复且不依赖设备当前时间、locale 或数据返回顺序。
- 关键不变量必须有代码注释或 KDoc：首次收到时间不因更新变化、排除与查看筛选分离、黄色表示不确定而非已停机、条目年龄不使动作人为过期。
- 新增依赖、后台机制或“宿主 + 模块”抽象必须对应当前已确认需求。没有第二个真实后台模块前，不为假想扩展引入常驻组件或复杂插件框架。
- 构建应通过仓库内 Gradle Wrapper 和固定版本配置复现；本机 SDK 路径只写入未跟踪的本地配置，不进入源码或文档示例的真实值。
- 每项完成声明必须附自动化测试或真机记录。测试失败不得通过注释、跳过、放宽断言或关闭检查来掩盖。
