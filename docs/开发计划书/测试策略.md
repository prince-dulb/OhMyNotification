# 救救我的通知！测试策略

状态：`[已确认] plan-v1.0`

## 1. 目标与总原则

本策略把功能规格中的验收条件转成可重复证据。测试顺序固定为：

1. 先验证领域规则与数据正确性；
2. 再验证 Android 组件、权限和生命周期；
3. 再在红魔 11 Pro+ 上验证真实后台行为和 B 站实际落页；
4. 只有正确性全部通过后，性能数据才有资格参与方案选择或基线锁定。

`[已确认]` 模拟器、合成通知和自动化测试不能替代 B 站投稿、动态、开播三类真实通知的主闭环，也不能替代红魔后台、`PendingIntent` 寿命、状态通知残留和耗电结论。

`[已确认]` debug 构建不能锁定发布性能预算。阻断性真机结论使用 release 或与生产路径一致、差异已记录的 release measurement 构建。

### 1.1 不可妥协的判定

- 漏记、错误排除、重复逻辑条目、不同内容误合并、分页丢项、错误抽屉和自通知递归计数必须为 0。
- “系统接受启动请求”不等于“实际到达原内容”；精确落页必须人工或受控真机核对目标身份。
- 没有证据的运行时段显示黄色 `UNCONFIRMED`，不得通过补写心跳把它伪装成蓝色。
- 空闲新增周期轮询、主动唤醒、周期写盘、精确闹钟、高频 `WorkManager` 或 FGS 空转直接失败。
- 测试失败、无效 run 和不稳定 run 均保留原因；不得删除较差结果后宣称通过。
- 真实通知正文、动作、内容 ID、账号、截图、本机路径和签名材料不得进入 Git、公开报告或普通日志。

## 2. 测试层级

| 层级 | 名称 | 主要对象 | 执行位置 | 能锁定什么 |
|---|---|---|---|---|
| T0 | 静态与架构检查 | 依赖方向、Manifest、备份规则、禁止 API/字段、32 位原生依赖 | Windows 构建机 | 结构性边界；不能证明运行行为 |
| T1 | 纯领域单元/性质测试 | 归一化、归并、排序、分组、筛选、健康区间、统计公式 | JVM | 确定性算法与不变量 |
| T2 | 本地持久化集成 | Room 映射、事务、故障注入、稳定分页、策略修订 | Android instrumentation 或官方测试环境 | 事务和查询契约 |
| T3 | Android 平台契约 | 通知监听、权限、渠道、`PendingIntent`、SAF、进程重建 | 模拟器/参考设备 | 通用平台适配；不能锁厂商行为 |
| T4 | 可控真机集成 | 版本化合成通知源、100 回调、10,000 历史、故障矩阵 | 红魔 11 Pro+ | 目标机正确性与可重复性能 |
| T5 | 真实来源验收 | 官方 B 站投稿、动态、开播及失效边界 | 红魔 11 Pro+ | A13 实际产品闭环 |
| T6 | 性能与长待机 | 8 小时、A/B、增长、重启、回归报告 | 红魔 11 Pro+ release | 绝对预算、10% 门和承载方式 |

低层通过不自动推导高层通过。高层发现的稳定反例必须下沉为 T1—T4 的版本化回归夹具，但真实内容只保留去隐私化结构。

## 3. 测试工具与依赖边界

### 3.1 首选官方能力

`[候选]` 工程创建后优先使用 Kotlin/JUnit、AndroidX Test、Compose UI Test、Room 测试支持、Macrobenchmark/Benchmark、`adb`、Perfetto、`dumpsys` 和 Android 官方备份/权限检查能力。具体版本在 Phase 0 工具链盘点后锁定，不在计划阶段提前安装或编造版本。

生成式性质测试优先用固定种子和项目自有数据生成器实现；只有现有能力明显不足时才评估第三方测试库，并按许可证、体积、维护状态和必要性审查。

### 3.2 可控通知源

Phase 0 需要一个只供测试的通知生产者，能够按清单发布、更新、移除通知并构造受控动作。它不得进入生产 APK，也不得拥有网络、账号或真实用户数据。

具体形态在工程脚手架任务中二选一并记录：

- instrumentation 测试 APK 能稳定以独立来源包交付全部所需回调时，优先复用它；
- 否则建立独立的 test-only Android 应用/模块，并在创建前把目录、产物排除和运行命令写入 `AGENTS.md`。

该测试工具不改变“生产 v0 只有一个 `:app` 模块”的架构结论。

### 3.3 命令锁定

当前仓库尚无 Gradle Wrapper，因此本文件不宣称任何构建命令已经可执行。Android 工程创建后，必须在项目规则和 README 中锁定至少以下命令的实际名称与用途：

- JVM 单元测试；
- instrumentation/Compose/Room 测试；
- lint 与 release 编译；
- 结构性隐私扫描；
- 固定数据集校验；
- 真机性能数据采集与报告汇总。

Windows 入口统一通过仓库内 Wrapper 或仓库脚本，不依赖未记录的全局命令。CI 配置属于项目红线，只有用户明确授权后才创建；本地质量门不等待 CI 才生效。

## 4. 测试数据与夹具

### 4.1 版本化合成数据集

| 数据集 | 固定内容 | 主要用途 |
|---|---|---|
| `notification-fields-v1` | 缺标题/正文、长文本、Unicode、样式字段、非法时间、动作有无 | A03/A04 |
| `lifecycle-merge-v1` | 发布、密集更新、移除、key 复用、同文不同内容、孤立移除 | A05/A08 |
| `ordering-groups-v1` | 同时间戳、15 分钟边界、跨 3/4 条、极端单来源突发 | A06/A07 |
| `burst-100-v1` | 恰好 100 个发布/更新/移除/排除/自通知操作及期望结果 | SP-04/A10/A14 |
| `history-10000-v1` | 恰好 10,000 个去隐私化条目及固定查询、筛选、抽屉操作 | A06/A07/A12/B01/A14 |
| `health-evidence-v1` | 连接、断连、突然终止、撤权、重启、壁钟变化 | A10/A11 |
| `jump-targets-v1` | 允许/拒绝 URI、无处理器、动作取消/消费、来源卸载 | A09 |
| `privacy-sentinels-v1` | 唯一标题、正文、包名、URI、令牌、路径和设备标识哨兵 | NFR/B03 |
| `retention-growth-v1` | 诊断上限、缓存上限、持续增长与用户删除选择 | B02/A14 |

每个数据集必须有版本、SHA-256、生成规则、随机种子、期望结果和变更原因。输入或期望变化即升级版本；不得静默覆盖既有基线数据。

### 4.2 时间与并发

- 领域测试使用可注入 UTC 时钟和单调时钟；禁止依赖测试机器当前时间。
- 同时间戳用稳定序列与 ID 打破平局。
- 并发测试枚举策略切换、摄取、删除、诊断裁剪和导出的关键调度顺序。
- 等待测试使用预先登记的检查点，不把等待时长写成产品 TTL。
- 随机生成测试必须记录种子；失败种子转成固定回归夹具。

### 4.3 真实 B 站样本

- 只在红魔本机非 Git 跟踪位置保存完成验收所需的最小私有证据。
- 公开结果用 `submission-01`、`dynamic-01`、`live-01` 等非可逆别名。
- 真实标题、正文、账号、BV/AV、动态 ID、直播间 ID、完整 URI、动作和截图不进入仓库。
- 从真实反例下沉到仓库的夹具必须重新构造为去隐私化字段形状，不能只做字符串打码。

## 6. Phase 0 Spike 验证协议

| Spike | 必须使用的主要方法 | 最小阻断证据 |
|---|---|---|
| SP-01 真实字段与生命周期 | 三类真实 B 站通知 + 去敏字段投影 + 回调时间线 | 每类字段、身份、更新/移除、缺失与反例 |
| SP-02 原始动作寿命与成本 | 预登记等待点、划除、进程/来源状态、句柄数量梯度 | 派发与实际落页分开；PSS/Binder 成本 |
| SP-03 B 站持久精确目标 | 受控提取、进程重建、设备重启、实际身份核对 | 三类各明确“持久精确/仅运行时/不支持” |
| SP-04 队列、事务与归并 | `burst-100-v1`、故障注入、竞态与补扫 | 输入—决策—事务—最终条目完整对账 |
| SP-05 监听可靠性与红魔策略 | 长锁屏、系统回收、强停、重连、重启、权限切换 | 事件时间线、漏记边界、所需用户设置 |
| SP-06 状态通知/FGS A/B | 相同 release 路径、相同负载和权限的两方案比较 | 合规类型、残留语义、正确性和逐项资源 |
| SP-07 健康证据与区间精度 | 已知动作时间线与派生区间盲对账 | 正面证据集合、黄色比例、无额外唤醒 |
| SP-08 排序、抽屉、筛选、分页 | 多页大小、`history-10000-v1`、组合条件 | 完整 ID/成员序列完全一致，不全量加载 |
| SP-09 持久化、隐私与性能 | 事务/增长、备份检查、哨兵扫描、固定性能场景 | 逻辑模型、上限、工具口径、绝对预算 |

每个 Spike 结果只允许 `GO`、`REDIRECT` 或 `STOP`。`REDIRECT` 必须先回写相关规格、路线图、非功能需求和任务，再由用户确认；不得让代码成为事实上的新计划。

## 7. Android 与设备矩阵

### 7.1 阻断环境

| 环境 | 用途 | 是否可替代红魔结论 |
|---|---|---:|
| Windows 本机 JVM | T0/T1 快速反馈 | 否 |
| Android 16 模拟器/参考环境 | T2/T3 通用平台回归 | 否 |
| 红魔 11 Pro+ 16+1TB、Android 16 | T4/T5/T6 首要验收 | 本身 |

红魔每次阻断 run 记录：系统构建、ABI、B 站版本、OMN commit/build、充电/温控/网络/屏幕、电源模式、通知使用权、`POST_NOTIFICATIONS`、渠道、监听连接、进程证据和厂商后台设置。

### 7.2 兼容性边界

- APK 必须能在不支持 32 位应用的目标机安装和运行。
- v0 默认无 NDK；如依赖带原生库，必须检查 ABI 与来源，且引入前更新计划。
- 工作资料只在设备实际支持时阻断对应用例；不支持时记录 `NOT_APPLICABLE`，不能伪造个人资料替代。
- B 站版本变化可能改变通知结构和路由；A13 每轮记录版本并保留跨版本回归。

## 8. 性能测量与统计

完整指标、公式和预算规则以 A14 为权威。本策略补充执行纪律：

1. 短场景至少 1 次预热、3 次有效 run；8 小时场景每候选至少 2 次。
2. 使用有效 run 中位数；环境污染标为 `INVALID`，原始记录仍保留。
3. 波动超过 A14 门时追加 run 并调查，不挑最好一次。
4. 正确性失败的 run 不进入性能比较。
5. Phase 0 首次基线与绝对预算写回非功能需求后，必须由用户确认才能锁定。
6. 后续同口径任一受管指标中位数回退超过 10% 阻断合并。
7. 耗电口径若不可重复，状态保持未锁定；不得用系统电量整数变化冒充精确数据。

## 9. 隐私与安全测试

### 9.1 双层防线

- 类型层：持久化、日志和导出 DTO 不接受 framework 动作、原始 extras 或敏感领域字段。
- 输出层：使用 `privacy-sentinels-v1` 扫描日志、异常、测试报告、B03 文件和公开候选证据。

任一命中先停止公开流转，再定位字段路径；不得在报告中重复打印命中的敏感原文。

### 9.2 必查配置

- Android 自动备份/设备迁移不包含通知数据库、动作目标和敏感偏好。
- 组件导出、Intent 处理、URI 校验和 `PendingIntent` flags 符合当前 Android 官方要求。
- 不存在未声明必要性的网络能力、可写调试 Provider、广泛存储权限或 `QUERY_ALL_PACKAGES`。
- 若 Phase 0 提议扩大包可见性，必须先更新 A02 与计划并由用户确认。
- release 产物不含调试后门、真实夹具、签名材料或本机路径。

## 10. 界面与无障碍

每个主页面至少覆盖：

- Material 3 组件语义、edge-to-edge 与系统栏；
- 48dp 最小触控目标；
- TalkBack 顺序、角色、状态和可操作名称；
- 最大系统字体、显示缩放、横竖屏和分屏；
- 深浅色、动态配色关闭/开启、对比度；
- “减少动态效果”下抽屉和状态转换；
- 加载、空、错误、权限拒绝、数据不可用和保存失败；
- 蓝/黄、成功/失败、启用/禁用均有非颜色编码。

截图比较只作辅助；可操作性和语义树断言是阻断项。

## 12. 缺陷、重试与证据记录

- 每个失败记录：commit、构建、设备/环境、数据版本/hash、前置状态、最小复现、期望、实际、去敏证据和首次失败层级。
- 自动重试不能把不稳定测试变绿；重试只用于采集波动证据，最终状态仍是失败或不稳定。
- 真机无法取得真实推送时记录 `NOT_OBSERVED`，不写“预计通过”。
- 修复后先在最低可复现层回归，再重跑发现问题的高层场景。
- 公开报告只保留去敏摘要；本机私有原始证据与 Git 跟踪材料分开。

## 13. 本策略完成定义

- A01—A14、B01—B03 每项都有明确自动化与真机覆盖。
- SP-01—SP-09 的输入、方法、证据和决策值明确。
- 8 小时、100 条、10,000 条、B 站三类、状态通知 A/B 和诊断导出都有固定协议。
- 正确性、性能、隐私、无障碍和平台合规门彼此不替代。
- 尚未创建的工具和命令明确标为待脚手架锁定，没有把计划写成已验证事实。
- CI、全局依赖、系统配置、数据库 schema 和公开发布均未由本策略擅自授权。
